## 1. Draft Agent 설계 및 초기 구현

* 정산 담당자의 입력 부담을 줄이기 위해 **거래 정보를 바탕으로 비용 분류·지출 목적·규정 힌트 초안을 자동 완성**하는 역할로 정의
* 초안 생성 후 사용자가 수정 요청을 보낼 수 있도록 **생성 모드와 수정 모드를 구분**하여 처리 흐름 설계
* 응답 형식을 스키마로 강제하여 **정의된 비용 분류 외의 값이 생성될 수 없도록** 구조 확정
* 규정 관련 값은 추측하지 않고 **시스템의 규정 데이터를 실제 조회**하도록 설계하여 근거 없는 값 생성 방지

## 2. RAG 소스 문서 준비 및 파싱 전략 수립

* 사내 규정 문서를 **RAG 대상 형식으로 변환·정리**하여 소스 데이터 준비
* 규정 문서의 구조적 특성을 분석하고 **문서 유형별 파싱 처리 방향과 품질 기준을 전략 문서로 정리**
* 표·계층 구조·머리말 등 **파싱 시 손실되기 쉬운 요소를 사전에 식별**하고 처리 방침 수립

## 3. 파싱·청킹 모듈 1차 구현 및 검색 Tool 연결

* 수립한 전략을 바탕으로 **문서 파싱·정규화·구조 추출·표 처리 모듈을 1차 구현**
* 파싱 결과의 이상 여부를 자체 점검할 수 있도록 **품질 검증 로직을 함께 구성**
* 이후 에이전트가 규정 검색을 호출할 수 있도록 **규정 검색 Tool 인터페이스 연결**

## 1. 룰 판정 입력(EvalContext) 구조 정리

* 룰엔진이 참조하는 판정 입력 항목이 과도하게 늘어난 문제를 확인하고 **101개 → 46개로 정리**

* 이미 결론이 내려진 항목, 다른 항목으로 계산 가능한 항목, 데이터 원천이 없는 항목을 제거 기준으로 적용
* 정리에 맞춰 **시드 룰 그래프와 조립 로직도 함께 수정**하고 검증 테스트 보강

## 1. 규정 문서 파싱 파이프라인 구현

* PDF 파싱 결과에서 반복 확인된 **문서 결함 유형별 교정 로직을 모듈 단위로 구현**
* 페이지 경계에서 읽는 순서가 뒤바뀌는 문제, 항·호 번호가 본문과 분리되는 문제, 표 병합 오류 등을 교정 대상으로 정리
* 교정 적용 후 **번호 누락 95건 → 0건, 법령 항 번호 오류 882건 → 0건**으로 해소되었으며 요소 소실은 발생하지 않음
* 교정 결과가 이후 변경으로 깨지지 않도록 **회귀 테스트 66건을 구성하여 기준선 고정**

## 2. 청킹 전략 수립 및 구현

* 규정 문서의 실제 길이 분포를 측정하여 **문자 수가 아닌 조(條) 단위를 기본 분할 기준으로 확정** (조 블록 중앙값 449자)
* 조가 지나치게 길 경우에만 항·호·문장 순으로 단계적으로 분할하고, **표는 항상 독립 청크로 분리**
* 오버랩 대신 **계층 헤더 정보와 상위 청크 연결**을 부여하여 문맥 손실 없이 중복 저장 최소화
* 고정 길이(800자) 방식은 **조문 경계 훼손 190건·표 파손 29건**이 발생한 반면 본 전략은 **각각 1건·0건**
* 최종 **888개 청크 생성**, 원문 커버리지 100%·유실 0건으로 청킹 회귀 테스트 175건과 함께 확정

## 3. 임베딩 후보 비교 실험 및 인덱싱 모듈 구현

* 조문 단위 정답을 기준으로 하는 **검색 평가용 정답셋 30건(6개 질의 유형)** 을 구축
* 동일 코퍼스(799 청크)·동일 정답셋 조건에서 **임베딩 후보 7종(상용 4 + 로컬 3)을 비교 실험**하고 결과를 지표로 정리
* 문서 입력 시 **계층 헤더를 함께 임베딩하는 방식이 본문만 사용하는 경우보다 전 모델에서 우수**함을 확인 (평균 MRR +0.050)
* 실험 결과를 실제 파이프라인에 적용할 수 있도록 **임베딩 인코더 및 인덱싱 모듈 구현**

## 4. 회계 검토 및 룰 생성/수정 에이전트 설계

## 1. RAG 검색 품질 측정 및 실행 환경 정비

* 규정 문서 파싱·청킹·임베딩 결과를 대상으로 **검색 랭킹 품질 측정 진행**

* AI 서버 설정을 **도커 실행 환경에 맞게 정비**하고 규정·설계 문서 경로 체계 정리
* 벡터 저장소 적재(Chroma upsert)가 남아 있어 **검색 경로 일원화는 후속 과제로 확인**

## 2. Rule Agent(룰 생성) v0 구현

* 규정 문서 검색 → **LLM 룰 노드 초안 생성 → 그래프 조립 → DRAFT 저장**으로 이어지는 룰 생성 흐름 구현
* **그래프 위상은 LLM이 아닌 파이썬이 결정론적으로 조립**하도록 분리하여 구조 검증 실패 요인 최소화
* 초기 구현에서 **LLM이 조건식(JSON-Logic)을 문자열로 직접 생성하며 문법 오류가 반복 발생**하는 문제 확인
* 프롬프트 예시 보강만으로는 해결되지 않아, **조건을 구조화된 스키마로 입력받고 파이썬이 조립하는 방식으로 전환** → 파싱 실패 자체가 발생하지 않는 구조로 개선
* 실 데이터 재검증 결과 **거부된 노드 0건**으로 룰 초안 저장 직전 단계까지 도달, 남은 이슈는 **저장 API 권한 처리**로 특정

## 3. 관리자용 AI 실험실 페이지 구축

* 관리자가 AI 기능을 정산 흐름과 무관하게 단독 실행할 수 있는 **AI 실험실 페이지 구축 완료**
* **운영과 동일한 코드를 호출**하되, 결과가 아니라 **프롬프트·모델 출력·토큰·지연시간·검색 점수 등 근거를 함께 노출**
* Draft Agent 실행, RAG 검색, 임베딩 비교, 적재 현황 등 **기능별 탭 구성** 및 미구현 기능은 예정 상태로 표시
* 별도 권한을 부여받은 관리자만 접근하도록 **화면 접근 권한 분리**

### ✅ 진행 결과

* **검색 랭킹 품질 측정 진행** 및 도커 실행 환경·문서 체계 정비

# 📋 일간 보고 (08/14)

## 1. 임베딩 모델 선정 및 리트리빙 전략 확정

* 전일 비교 실험 결과를 검토하여 **`text-embedding-3-large` @ 1024차원으로 임베딩 모델 확정**
* 네이티브 3072차원 대비 **검색 품질 차이는 잡음 수준이나 저장 용량은 67% 절감**되어 1024차원 채택
* 확정 기준 검색 성능은 **MRR 0.906 / Recall@1 0.817 / 표 검색 Recall@5 1.00** 수준으로 측정
* 리트리빙은 **계층 헤더 주입 + 부모 청크 확장 + 이웃 링크** 구조로 확정하고, 표는 항상 독립 청크로 분리해 한도 기준 검색 정확도 확보
* 인용 단위를 **조문 ID**로 고정하여 청킹 기준이 바뀌어도 **근거 추적성이 유지되도록 설계**

## 2. Risk Review(검토) Agent 구조 설계

* 검토 Agent를 **① 비지도 이상탐지로 이상 후보 선별 → ② 이상 후보 한정 RAG 내규 검증**의 2단계 구조로 설계
* 1단계는 기 구축된 **15개 피처 파이프라인 및 보정 임계값**을 활용하고, 2단계에서 규정 근거와 권장 의견을 출처와 함께 제시
* 룰엔진(결정론적 판정) 이후 단계로 배치하여 **룰 판정과 AI 검토 의견의 역할을 분리**
* 검토 결과는 참고 의견이며, **최종 확정은 회계 담당자가 수행하는 원칙 유지**

## 3. 프론트 연동 및 관리자 실험 환경

* **룰 콘솔 화면 3개 탭 전 구간 API 연동 완료** — 룰 초안 편집·시뮬레이션·활성 승인 및 버전 롤백
* 회계 검토 화면에 **RAG 검증 보고서와 판정 근거 스냅샷 연동**
* 관리자용 AI 실험실에서 **Draft Agent 단독 실행 및 RAG 검색 결과 확인** 가능하도록 구성
* 사용자 요청은 Django를 경유하고 **AI 서버는 내부 전용으로 유지**하는 구조 준수

## 4. RAG 파이프라인 구조 정리

* **파싱 → 청킹 → 임베딩 → 검색** 단계별 결과와 품질 지표를 문서로 정리
* 본 프로젝트의 RAG 출력은 단순 답변이 아니라 **룰 초안 생성과 검토 근거 제시**임을 명확히 정리
* 금액·일수 등 수치 기반 질의가 상대적 약점으로 확인되어 **하이브리드 검색·리랭커를 향후 개선 후보로 기록**

### ✅ 진행 결과

* **임베딩 모델 및 리트리빙 전략 확정**, 정답셋 기반 검색 품질 실측 완료
* **검토 Agent 2단계 구조 설계** 및 룰엔진과의 역할 분리 정리
* 룰 콘솔·회계 검토 화면 **연동 및 관리자 실험 환경 확보**
