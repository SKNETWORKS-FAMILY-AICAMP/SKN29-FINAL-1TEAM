## 주제 선정 배경 및 기획의도

### 기업 입장에서의 문제 정의

> 관통하는 한 문장: **"정산은 부가가치가 낮은데도 조직 전체의 시간을 잡아먹는다."**

| # | 문제 | 페인포인트 | 구체적 증상 |
|---|---|---|---|
| ① | **입력이 번거로워 임직원 생산성이 깎인다** | 임직원·팀장 | 영수증 챙기기 → 비용분류 고르기 → 사유 쓰기가 본업보다 번거로움 → 월말 몰아치기 제출, 반려 → 재작업 반복. 팀장은 팀원 지출을 건건이 열어보며 반나절 소모 |
| ② | **검토가 전건 수작업이라 리스크를 못 걸러낸다** | 회계 담당자 | 수백 건을 규정과 대조하며 전수 검토 → 시간 대부분이 "정상 건 확인"에 소모되고, 정작 작은 실수·부정사용은 사람 눈을 빠져나감 |
| ③ | **예산 편성·정책 결정의 근거가 없다** | 회계/운영 상부 | 예산이 어디서 새는지, 어떤 규정이 반복 위반되는지 데이터가 없어 감(感)으로 판단 |

세 문제는 **서로 다른 성격**이라는 점이 중요하다 — ①은 입력 자동화, ②는 판정 자동화 + 우선순위화, ③은 데이터 축적·시각화 문제다.
하나의 기술로 풀리지 않고, **규칙 기반 + 통계 기반 + 생성형 AI가 역할을 나눠야** 한다는 것이 기획의 출발점이다.

### 왜 지금, 왜 AI인가

- **판단이 필요한 반복 업무** — 전통적 RPA(단순 규칙)로는 애매한 건을 못 넘기고, 순수 수작업은 비효율. 그 사이에 낀 전형적인 **Hybrid AI 적용 대상**.
- **영수증 판독**: LLM 비전 모델의 발전으로 별도 OCR 엔진 없이 실용 정확도 확보 가능.
- **내규 검증**: 사내 규정이 텍스트 문서라 RAG로 "근거 제시"가 바로 적용 가능.
- **데이터 제약**: 실제 기업의 정산 데이터·내규는 외부 공개가 없으므로 → 가상기업 **"타이거 주식회사"** 페르소나(조직도·직급체계·법인카드 사용규정 `TIGER-REG-2026-003`)를 직접 설계하고 합성 데이터로 **검증 가능한 문제**로 재구성.

## 우리 서비스의 해결방안

> 발표 포인트: **기능 하나하나가 앞의 문제 정의 ①②③ 중 어디에 대응하는지**, 그리고 **AI가 어디까지 하고 사람이 어디서 결정하는지**를 항상 같이 말한다.

### 문제 → 기능 연결 (연결성 강조)

| 문제 | 해결 기능 | 무엇이 달라지나 | 담당 컴포넌트 |
|---|---|---|---|
| ① 입력이 번거롭다 | **초안 작성 Agent** — 카드 사용내역 + 영수증 비전 판독으로 정산 초안 자동 완성, 비용분류 자동 제안, 규정 힌트 사전 안내 | 임직원은 "자료 첨부 + 대강의 설명 + 클릭 몇 번"으로 제출 완료. 사전 안내로 **반려 자체가 줄어듦** | S-01 내 지출 / Draft Agent(비전) |
| ① 입력이 번거롭다 | **자동 보완요청(RPA)** — 증빙 누락·목적 미기재 등은 사람 손을 타기 전에 시스템이 먼저 되돌려줌 | 회계팀이 "증빙 주세요" 하러 다니지 않아도 됨 → 안정적·일관된 품질 | Rule 엔진 · 상태머신(`RETURNED`) |
| ② 검토가 전건 수작업 | **Rule Agent(결정론적 룰 그래프)** — 규정에 명시된 한도·조건은 1차 자동 판정 | 확실한 건이 검토 큐에서 빠짐 → 회계팀은 애매한 건에 집중 | 룰 그래프 엔진 |
| ② 검토가 전건 수작업 | **Risk Review Agent 2단** — ① 비지도 이상탐지로 후보 선별 → ② RAG로 내규 근거를 찾아 검증 | 검토 화면이 **위험도 순으로 정렬**되고, 각 건에 **AI 권장처리 + 이유 + 규정 근거**가 붙음 → 판단 피로도 감소 | ML(Isolation Forest) + RAG(Chroma) |
| ② 검토가 전건 수작업 | **Rule 콘솔(비개발자용)** — 회계팀이 자연어로 룰을 만들고, 과거 내역으로 시뮬레이션 검증한 뒤 활성화 | RPA 룰 변경에 **개발자가 필요 없음**. 규정 개정 → 즉시 반영 | S-04 Rule 콘솔 |
| ③ 결정 근거가 없다 | **거버넌스 대시보드** — 예산 소진율·자동처리율·위반 패턴 지표화, 정책 인사이트 추천 | 예산 편성·정책 결정이 **데이터 기반**으로 이동 | S-06 대시보드 |

### AI가 하는 일 / 사람이 결정하는 일 (Human-in-the-Loop)

시스템 전체를 관통하는 원칙: **"AI는 제안만, 확정은 사람"**.

| 단계 | AI가 하는 일 | 사람이 하는 일(안전장치) |
|---|---|---|
| 입력 | 영수증 판독·분류 제안·사유 초안 | 제출 전 본인이 확인·수정 |
| 1차 판정 | 룰 그래프가 결정론적으로 판정(PASS/RETURN/REVIEW/REJECT) | 룰 자체를 사람이 만들고 **시뮬레이션으로 검증한 뒤 활성화** |
| 위험 선별 | 이상탐지 점수 + RAG 근거로 우선순위·권장처리 제시 | 회계 담당자가 근거를 보고 **최종 판단** |
| 확정 | — | **자동 통과 건도 사람 확정 없이는 `CONFIRMED` 불가** |
| 정책 | 지표·인사이트 추천 | 예산·정책은 **차단이 아니라 지표·추천으로만** 반영 |

부가 안전장치 3가지 — 발표에서 "신뢰성" 슬라이드로 묶어 쓰기 좋다.

1. **재현 가능한 판정**: 조건은 임의 코드가 아니라 **JSON-Logic류 DSL**, 판정 시점의 입력(EvalContext)을 통째로 스냅샷 저장 → 언제든 재현·감사 가능.
2. **활성화 게이트**: 사이클(순환 라우팅)·미정의 데이터 경로가 있는 룰 그래프는 **Active 전환 자체가 거부**됨.
3. **권한 분리**: 룰 열람(`rule_view`)과 룰 활성(`rule_activate`)이 분리되어, 만든 사람과 활성화하는 사람이 다를 수 있음 + 감사로그 기록.

## 프로젝트 구조

### 시스템 아키텍처 개요

```
[브라우저]
    │
 nginx (리버스 프록시)  ── / → web(React) ── /api → core(Django)
    │
    ├─ web    : React + Vite + TypeScript (SPA) — 역할별 6개 화면
    ├─ core   : Django + DRF — System of Record(SoR)
    │             도메인 CRUD · 정산 상태머신 · Capability RBAC · 룰 그래프/엔진 · ERP 전표(안) · 감사로그
    │             └── PostgreSQL (확정 데이터의 단일 원천)
    └─ ai     : FastAPI — AI Orchestrator (내부 전용, 사용자 트래픽 직접 노출 안 함)
                  3-Agent(Draft/Rule/Risk) · FastMCP Tool · RAG 파이프라인 · 이상탐지 추론
                  └── Chroma (벡터 DB: 규정·판례·세무 참조)
```

**아키텍처 원칙 (발표에서 "설계 판단" 슬라이드로)**

| 원칙 | 내용 | 왜 |
|---|---|---|
| SoR 단일화 | 확정 데이터는 Postgres(Django) 하나. AI는 항상 "제안"만 생성 | 감사 가능성·책임 소재 명확화 |
| 접근 경로 분리 | 관계형 = Django 경유 / 벡터 = Chroma 직접. **LLM·Tool의 직접 SQL 금지** | 데이터 무결성, 프롬프트 인젝션 차단 |
| FastAPI는 내부 전용 | 사용자 트래픽은 Django만 받음 | 인증·인가 경로 일원화 |
| 동기 REST(MVP) | 무거운 작업은 관리자 온디맨드 배치 | MVP 복잡도 통제 |

## 기대효과

> 두 가지 버전을 함께 둔다. **슬라이드에는 A(기획 관점)** 를 쓰고, Q&A·부록용 근거는 **B(엔지니어링 관점)** 에서 꺼내 쓴다.

### A. 기획 관점 버전 — 발표용 (권장)

#### "누구의 무엇이 어떻게 달라지는가"

| 대상 | 지금 (As-Is) | 도입 후 (To-Be) | 체감 가치 |
|---|---|---|---|
| **임직원** | 영수증 챙기고 · 분류 고르고 · 사유 쓰다가 월말에 몰아치기. 반려되면 처음부터 다시 | 영수증 사진 한 장 + 한 줄 설명이면 나머지는 AI가 채운다. 규정에 걸릴 것 같으면 **제출 전에** 알려준다 | 정산 때문에 본업이 끊기지 않는다 |
| **팀장** | 팀원 지출을 건건이 열어봐야 뭐가 문제인지 안다 | 문제 있는 건만 위로 올라오고, 나머지는 한 번에 넘긴다 | 취합이 아니라 **판단**만 하면 된다 |
| **회계 담당자** | 수백 건을 규정과 대조하며 전수 검토. 대부분 정상인데 다 봐야 한다 | 확실한 건은 자동 처리되고, 애매한 건만 **위험도 순서로 + 판단 근거와 함께** 올라온다 | 검토가 "훑기"에서 "판단"으로 바뀐다 |
| **회계·운영 상부** | 예산이 어디서 새는지, 규정이 지켜지는지 감으로 판단 | 자동처리율·예산 소진·위반 패턴이 대시보드 지표로 쌓인다 | 정책을 **근거로** 결정한다 |
| **감사·내부통제** | "이 건이 왜 통과됐나"를 사후에 설명하기 어렵다 | 모든 판정에 어떤 규정·어떤 경로로 결론이 났는지 기록이 남는다 | 문제가 생겨도 **추적 가능**하다 |

#### 조직 차원에서 남기는 것 — 세 문장

1. **시간을 돌려준다.** 정산에 관여하는 모든 역할(임직원 → 팀장 → 회계 → 상부)의 시간을 동시에 줄인다. 한 사람의 편의를 위해 다른 사람에게 일을 떠넘기지 않는 구조다.
2. **리스크를 줄인다.** 사람 눈으로는 걸러지지 않던 두 유형 — 서류상 문제없어 보이는 규정 위반, 그리고 거래 패턴 자체가 신호인 반복·분할 결제 — 을 각각 규칙과 이상탐지로 잡아낸다. (국정감사에서 드러난 GIST·KAIST 사례가 정확히 이 두 유형이다)
3. **데이터가 쌓인다.** 지금까지 흩어져 사라지던 "왜 반려했는가"가 데이터로 축적되어, 다음 해 예산 편성과 규정 개정의 근거가 된다.

#### 숫자로 말하면

| 지표 | 기대 수준 | 비고 |
|---|---|---|
| 회계팀이 직접 봐야 하는 건수 | **절반 이하로 축소** | 현재 시드 데이터 시뮬레이션 기준 자동처리율 57.5% — 룰을 정교화할수록 올라간다 |
| AI 운영 비용 | **전수 처리 대비 6~10배 절감** | 모든 건을 LLM으로 검증하지 않고, 이상탐지가 추린 소수 후보에만 정밀 검증을 집중 |
| 규정 변경 반영 리드타임 | **개발 요청 → 즉시 반영** | 회계팀이 직접 룰을 만들고 과거 내역으로 검증한 뒤 활성화 |

> 위 수치는 합성 데이터·시드 기준의 **참고값**이며, 실데이터 도입 시 재측정이 필요하다. (발표에서도 이 단서를 함께 말할 것)

#### 확장 관점 — "우리 회사 전용"으로 끝나지 않는 이유

- **첫날부터 쓸 수 있다.** 과거 검토 이력(정답 데이터)이 한 건도 없는 신규 도입 기업에서도 동작하도록 설계했다. 운영하면서 판단 이력이 쌓이면 더 똑똑해진다.
- **규정이 코드에 박혀 있지 않다.** 회사 규정은 문서(RAG)로, 판정 기준은 룰 그래프로 분리돼 있어 **코드 수정 없이 다른 회사·다른 규정에 이식**할 수 있다.
- **정산을 넘어선 확장 여지.** 같은 구조(규칙 + 이상탐지 + 근거 제시 + 사람 확정)는 구매·계약·경비 등 "규정 대조가 반복되는 모든 업무"에 그대로 적용 가능하다.

### B. 엔지니어링 관점 버전 — 근거·측정 방법 (Q&A·부록용)

| 구분 | 기대효과 | 근거·측정 방법 |
|---|---|---|
| 정량 | **회계팀 검토 물량 감소** — 확실한 건이 룰로 자동 처리되어 사람이 볼 건수 자체가 줄어듦 | Rule 콘솔 시뮬레이션이 **자동처리율·검토 감소량**을 실제 과거 내역으로 산출(현재 시드 데이터 기준 자동처리율 57.5% 측정) |
| 정량 | **LLM 처리 비용 절감** — 전수를 RAG/LLM으로 돌리지 않고 ML로 상위 후보만 넘김 | 평가 데이터 469,902건 기준, RAG로 넘기는 물량이 전체의 **약 3~4%**(상위 3% 컷오프 시 하루 약 42건). 컷오프를 10~15%로 넓혀도 전수 대비 **6.5~10배** 절감 |
| 정량 | **입력·반려 왕복 감소** | 초안 자동 완성 + 제출 전 규정 힌트 → 반려율 감소(데모 시나리오로 before/after 비교, **(작성 예정)**) |
| 정성 | **판단 근거의 가시화** | 모든 판정에 평가 경로(어느 룰 노드를 지나 어떤 결론이 났는지)와 규정 근거가 남음 → 감사 대응·내부 설득 비용 감소 |
| 정성 | **비개발자 운영 가능** | 규정 개정 시 회계팀이 직접 룰을 만들고 시뮬레이션 후 활성화 → 개발 리드타임 제거 |
| 확장 | **도입 초기(라벨 0건)에도 동작** | 비지도 이상탐지로 시작 → 운영하며 `decision_labels`가 쌓이면 지도학습·하이브리드로 전환 가능한 구조 |
| 확장 | **다른 조직에 이식 가능** | 규정은 RAG 문서로, 판정 기준은 룰 그래프로 분리 → 코드 수정 없이 회사별 규정 반영 |

#### ② 프론트 개발 · 핵심 모델 · API 설계 및 연동

> 목표: **전체 시스템 구성을 먼저 잡아두고, 메인 모델·핵심 로직은 실제로 구현하되 나머지 기능은 스캐폴딩 상태로 두어 각 파트가 언제든 자기 작업을 끼워넣을 수 있게 만든다.**
> (담당: 김진욱 — 아래는 실제 작업 결과)

**(a) 시스템 골격 선(先) 확정**

- 모노레포 4축(`web` / `core` / `ai` / `infra/nginx`) + `docker-compose`로 로컬에서 전체 스택이 한 번에 뜨는 상태를 먼저 만들었다(db·chroma·core·ai·web·nginx).
- 아키텍처 원칙(SoR 단일화 · 벡터는 Chroma 직접 · FastAPI 내부 전용 · 동기 REST)을 문서(기술명세서)에 못박고, 그 제약대로 코드 경계를 나눴다 → 이후 각 파트가 **경계 협의 없이 병렬 작업** 가능.
- FastAPI 쪽은 3-Agent·MCP Tool·RAG·ML 추론의 **인터페이스와 라우터만 스캐폴딩**으로 열어두어, AI 담당자가 곧바로 구현을 채울 수 있게 했다.

**(b) 핵심 도메인 모델 실구현 — 8개 도메인 / 22개 테이블**

- `accounts`(팀·사용자·Capability) · `cards` · `transactions`(거래·영수증·가맹점업종 캐시) · `settlements`(정산·이벤트·팀예산) · `policies`(규정문서·룰 그래프 일체) · `risk`(리스크 리뷰·결정 라벨) · `erp`(전표안) · `common`(감사로그).
- **정산 상태머신 4단계**를 서비스 레이어로 구현: 개인 보유(`DRAFT`) → 팀 취합(`TEAM_*`) → 회계 제출·룰엔진(`SUBMITTED`/`RPA_JUDGED`) → 회계 검토·확정(`PENDING_CONFIRM`/`RETURNED`/`IN_REVIEW`/`REJECT`/`CONFIRMED`/`ERP_VOUCHER_DRAFTED`). **팀 수준 반려와 회계 수준 반려를 별개 상태로 분리**한 것이 설계 포인트.
- 감사 추적을 위해 거래 삭제 보호(`PROTECT`)·이력 보존(`SET_NULL`)·`AuditLog` 기록을 모델 제약 수준에서 강제.
- **Capability RBAC**: 역할 문자열이 아니라 기능 단위 권한 5종(`team_aggregate`·`accounting_review`·`rule_view`·`rule_activate`·`governance_view`)으로 판정. 유효능력 = 역할 기본값 ∪ 개인 추가부여. DRF 권한 클래스로 백엔드에서 강제하고, `/api/me`로 내려 프론트는 `useCan()`으로 버튼까지 게이트.

**(c) 룰 도메인 — "룰 = 그래프" 모델과 결정론적 엔진**

- 단건 룰이 아니라 **룰 그래프(RuleGraph)** 를 최종 상태 도메인으로 잡았다. 노드(`condition` + `action`) + 라우팅(`MATCH`/`NO_MATCH`)으로 조립되고, **ACTIVE·버전관리·시뮬레이션·롤백이 전부 그래프 단위**.
- **엔진 3단**: ① `EvalContext` 조립(모든 데이터 접근을 이 단계에 격리) → ② 그래프 선택(GLOBAL 필수 게이트 → 비용분류 scope) → ③ 결정론적 순회(외부 I/O 0). 조건식은 **JSON-Logic류 DSL**(임의 코드 실행 금지)로 제한하고, 판정 입력을 `rule_hits.eval_context`에 스냅샷으로 저장해 재현·감사 가능하게 했다.
- **활성화 하드 게이트**: 사이클(순환 라우팅)·미정의 EvalContext 경로·잘못된 액션이 있으면 ACTIVE 전환을 거부. 런타임에서도 구조 오류 시 안전하게 `REVIEW`로 폴백.

**(d) Rule 콘솔(S-04) — 프론트 ↔ 백엔드 전 구간 실연동**

| 탭 | 구현 내용 |
|---|---|
| 초안 그래프 | 실 API의 그래프/노드 트리, 노드 상세 편집(제목·설명·DSL·액션·라우팅), **DSL을 자연어로 풀어 보여주기**, 자동 저장, ACTIVE 그래프 수정 시 자동 새 버전 생성, 원본과 같아지면 초안 자동 폐기 |
| 시뮬레이션 | **모든 노드가 검증대기인 그래프만** 대상. 그래프 구조를 위→아래 **스크롤 플로우차트**로 시각화(라우팅·수렴·종료·순환 감지) + 노드 상세 읽기. **커스텀 검증셋(테스트케이스)** 을 직접 편집하거나 대화형으로 수정 → 실행하면 **실제 룰 엔진**으로 검증셋 + 직전 달 실제 내역을 판정하고, 통계·AI 의견(마크다운)·결과 리스트를 보고서로 저장 |
| Active 관리 | 승인대기 목록(**스코프당 1건**), 펼치면 KPI·검토보고서, 룰 활성 권한자만 ACTIVE 전환. 현재 활성 그래프 전체 KPI 대시보드 + 스코프별 목록 → 버전 이력 모달에서 **롤백** |

- 시뮬레이션 결과는 `RuleTestCase` / `RuleSimulationRun` / `RuleSimulationResult` 3개 모델로 영속화 — **어떤 그래프의 어떤 버전이, 어떤 구조 스냅샷 상태에서 돌았는지**까지 저장하고, 이후 그래프가 바뀌면 화면에 "낡은 결과"로 표시.
- 활성화 요청 시 **검토자 코멘트(보고서 형식)** 를 남기게 하고, 그래프 모델에 **검토자·활성자**를 각각 추적.

#### ③ 가상 기업 내부문서 생성 (RAG 소스)

- 실제 기업 내규는 외부 공개가 없으므로, **가상기업 "타이거 주식회사"** 의 문서 세트를 직접 설계: 법인카드 사용규정(`TIGER-REG-2026-003`), 조직도, 직급체계, 부서소개, 조직설계 상세기획서.
- **공무원 규정 체계**의 조문 구조와 **드라마 「미생」 등에서 공개된 기업 문서 형식·컨셉**을 차용하고, 그 외 다양한 실제 자료를 참고해 현실성 있는 규정으로 작성.
- Rule Base 고도화에 맞춰 **출장·회식·기업업무추진비** 규정을 추가해 시나리오별 판단 근거를 보강.
- 이 문서 세트가 곧 ① RAG 검색 대상이자 ② 룰 명세(활성 58개 RULE)의 출처가 되어, **규정 → 룰 → 판정**의 추적성이 확보됨.

#### ④ 사용내역 1차판정 모델링 — 데이터·모델 선정 및 결과 비교

> (담당: 한경찬 — 근거 문서: `llm_wiki/비지도모델_비교실험_결과보고서.md`, `ml/ml_final_report.md`)
> **한 줄 결론**: 성격이 다른 비지도 알고리즘 **8종을 같은 데이터·같은 피처셋·같은 방식으로 채점한 결과, Isolation Forest를 넘어선 모델은 없었다.**

**(a) ML의 역할부터 정의했다 — "정확한 판정"이 아니라 "1차 필터"**

- 전체 거래에서 **검토가 필요해 보이는 후보를 넓게(recall 우선) 추리는 것**이 ML의 임무. 정밀한 규정 위반 판단은 뒤단의 RAG가 맡는다.
- 이 역할 분담 덕분에 ML 단계는 완벽할 필요가 없고, 대신 **빠르고(대용량 동기 처리) 놓치지 않아야(recall)** 한다 → 이 두 조건이 이후 모델 선택 기준이 됐다.

**(b) 왜 지도학습이 아니라 비지도인가 — 제품 요구사항에서 나온 결론**

- 지도학습의 정답이 될 `decision_labels`(회계 담당자의 실제 승인/보완/반려 결정)는 **시스템이 배포·운영된 뒤에만 쌓인다** → 어떤 회사든 도입 시점엔 예외 없이 0건(콜드스타트).
- 카드사 부정사용 이력이나 기존 반려 기록은 회사 내규마다 기준이 달라 그대로 정답으로 쓰면 도메인 시프트가 발생.
- 즉 "라벨이 하나도 없는 첫 도입 고객에게도 동작해야 한다"는 **제품 요구사항** 때문에 비지도가 유일한 출발점. (라벨이 쌓인 뒤 지도·하이브리드 전환은 후속 단계)

**(c) 비지도 8종 비교 — 계열이 다른 대표 알고리즘을 골랐다**

| 계열 | 아이디어 | 모델 | 스케일링 |
|---|---|---|---|
| 트리 분기(고립) | 무작위로 잘랐을 때 **빨리 혼자 남는** 데이터가 이상치 | **Isolation Forest** | 불필요 |
| 항목별 극단값(CDF) | 각 항목이 분포의 **꼬리 쪽에 얼마나 치우쳤는지** 합산 | COPOD, ECOD | 불필요 |
| 거리·부분공간 | 무리에서 **얼마나 떨어져 있는지** / 핵심 축으로 **재구성이 안 되는 정도** | INNE, CBLOF, PCA, GMM | 필수 |
| 히스토그램·투영 | 여러 방향 투영의 히스토그램을 종합 | LODA | 필수 |

**(d) 결과 — test set 1회 채점 (469,902건 · 이상거래 16,394건)**

| 모델 | PR-AUC | recall@top1% | recall@top3% | recall@top10% |
|---|---:|---:|---:|---:|
| **Isolation Forest (채택)** | **0.5865** | **0.249** | **0.526** | **0.790** |
| COPOD | 0.5330 | 0.238 | 0.480 | 0.765 |
| ECOD | 0.4294 | 0.206 | 0.400 | 0.694 |
| CBLOF | 0.3858 | 0.158 | 0.442 | 0.774 |
| PCA | 0.3833 | 0.157 | 0.439 | 0.770 |
| INNE | 0.3762 | 0.123 | 0.393 | 0.798 |
| GMM | 0.3418 | 0.094 | 0.430 | 0.715 |
| LODA | 0.0283 | 0.010 | 0.016 | 0.047 |

- 순위: **IF > COPOD > ECOD > CBLOF ≈ PCA > INNE > GMM > LODA**
- 계열별로 보면 패턴이 뚜렷하다 — **스케일 무관 계열(IF·COPOD·ECOD)이 상위, 거리·부분공간 계열은 전부 하위권**.
- ⚠️ LODA는 무작위 기준선(PR-AUC ≈ 0.035)보다도 낮아 **점수 부호 반전 가능성**이 있어 재확인 중. **(작성 예정 — 부호 확인 후 표 확정)**

**(e) 한 번의 채점을 믿지 않고 5-fold로 재검증했다 (train 내부, 카드 단위 분할)**

| 모델 | PR-AUC (평균 ± 표준편차) | recall@top10% |
|---|---:|---:|
| **IF** | **0.589 ± 0.049** | **0.793 ± 0.016** |
| COPOD | 0.567 ± 0.055 | 0.766 ± 0.015 |
| INNE | 0.453 ± 0.069 | 0.790 ± 0.015 |
| GMM | 0.328 ± 0.035 | 0.738 ± 0.110 |

- test 1회에서 INNE·GMM이 특정 구간(top5~10%)에서 IF를 근소하게 앞선 적이 있었으나, **반복 검증하니 모델 자체의 변동폭 안에 들어가는 노이즈**로 확인 → IF 우위가 우연이 아님을 확인.
- **GMM은 성능도 낮고 fold 간 편차가 가장 커(top10% 표준편차 0.110) 운영 예측 가능성이 떨어진다** → 배제.
- fold 평균(0.589)과 시간 기준 test 결과(0.5865)가 거의 일치 → 평가 자체의 신뢰성 확인.

**(f) 시도하지 않은 것과 그 이유 (탐색 종료 근거)**

- **One-Class SVM**: 기본 구현이 데이터 규모에 대해 최소 O(n²)로 확장 → 약 174만 건 학습이 **운영상 비현실적**(별도 서브샘플 실험에서도 전체 채점에 20분 이상 소요)이라 확장성 문제로 배제.
- **DBSCAN**: 이번에 실험한 "거리·부분공간" 계열과 성격이 같아 추가 시도의 기대 이득이 낮다고 판단.
- → 여기서 **비지도 알고리즘 탐색은 종료**, IF로 확정.

**(g) 채택하지 않았지만 기록해둔 대안 — COPOD**

- 성능은 IF보다 낮지만(fold 0.567 vs 0.589), **"왜 이 거래가 이상한지"를 항목별로 쪼개 설명하는 기능이 내장**돼 있다. IF에는 없는 특성이라, **설명가능성이 요구사항이 되는 시점의 1순위 대안**으로 남겨둔다.
- ⚠️ "성능 차이가 유의한가"는 fold별 쌍대 차이로 재계산 예정 — **(작성 예정)**

**(h) 전처리·실험 품질 관리 (재현성 기록)**

- **시간 기준 분할(Time-based Split)** 채택 — 시계열 파생 피처 사용 시 랜덤 분할이 만드는 데이터 누수를 차단.
- **가맹점 파생 피처 제외** — 피처셋 버전 불일치를 바로잡자 오히려 성능이 하락했는데, 이는 가맹점 피처가 **look-ahead 오염 신호**를 담아 성능을 인위적으로 부풀렸을 가능성이 높음을 시사 → 제외 결정의 타당성을 역으로 확인.
- **스케일링 필요 여부 정정** — INNE·LODA를 "불필요"로 잘못 판단했다가 바로잡음(스케일링 전 INNE PR-AUC 0.07 → 후 0.38).
- **PCA `weighted=True` 오류**, **CBLOF 클러스터 분리 실패** 등 구현상 함정도 원인까지 규명해 기록.
- **(작성 예정)**: 최종 피처 목록(15개 중 모델 입력 13개인 이유), 운영 컷오프 산정 근거, 피처 기여도 예시.

**(i) 이 실험이 답하지 못하는 것 (한계 명시)**

- 이 비교는 **"비지도 알고리즘 중 어느 것이 나은가"만** 답한다. 참고용 지도학습 실험과의 성능 격차는, 사용한 라벨(`이상거래여부`)이 실제 정산 검토 기준과 얼마나 겹치는지를 별도로 검증해야 판단할 수 있는 **완전히 다른 트랙**이다.

# 자체 평가의견

> 세 관점(A·B·C)으로 구성한다. **A·B는 강점**, **C는 한계·리스크**로 균형을 맞추는 구성이다.

### 관점 A. 문제 정의 → 기술 선택의 정합성 (가장 강한 어필 포인트)

- 기술을 먼저 정하고 문제를 끼워맞춘 게 아니라, **문제 유형별로 다른 기술을 배치**했다는 점을 어필.
  - 규정에 명시된 조건 → 결정론적 룰(신뢰성·재현성)
  - 패턴 이상 → 비지도 이상탐지(효율)
  - 규정 해석 필요 → RAG(맥락·근거)
  - 입력 부담 → LLM 비전(자동화)
- 국정감사 사례(허위 회의록 = 규정 대조로 못 잡음 / 카드 19개·6,500건 = 패턴 신호)가 **2단 구조의 필요성을 실제로 입증**한다는 논리 연결이 강점.

### 관점 B. "AI 제안 + 사람 확정" 안전 설계

- 자동화율을 자랑하는 대신 **틀렸을 때 어떻게 막는지**를 보여주는 방향.
- 근거: 사람 확정 없이는 `CONFIRMED` 불가 · 룰 활성화 하드 게이트(사이클·미정의 경로 거부) · 판정 입력 스냅샷 저장으로 재현 가능 · 룰 열람/활성 권한 분리 · 예산은 차단이 아닌 지표.
- 금융/회계 도메인에서 **감사 가능성(auditability)** 을 설계 요건으로 다뤘다는 점이 차별점.

### 관점 C. 한계와 리스크 — 솔직하게 밝혀 신뢰를 얻는다

> 작성 원칙: ① 무엇이 한계인지 ② 왜 그렇게 됐는지(변명이 아니라 판단 근거) ③ 언제·어떻게 해소할지 —
> 세 박자를 한 세트로 쓰면 "약점 고백"이 아니라 "리스크를 관리하고 있다"는 신호가 된다.
