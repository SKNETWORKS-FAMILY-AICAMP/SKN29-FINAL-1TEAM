# 시연영상 시나리오 기획 v4

> 목적: 기능 나열이 아니라, "이런 문제 겪어보셨죠?" 라는 공감 훅으로 시작해서 실제 화면 속 해결 과정을 보여주는 홍보+데모 하이브리드 영상
> 중심 상황: 월말 법인카드 정산 마감 D-2
> 핵심 구조: `공감(질문/문제 제기) → 모션그래픽 전환 → 우리 화면으로 컷 전환 → 실제 기능 클릭 → 처리 결과 확인 → 다음 인물로 인계`
> 목표 길이: 약 3분(180~190초). 인트로는 8초 내외로 짧게 치고, 그 다음부터는 유즈케이스 전개(사원→팀장→회계→리드)가 곧바로 이어짐 — 참고: 드롭샷매치 CLAP 소개영상(50초, UI 기반 인포그래픽/타이포 모션, 짧은 러닝타임 안에 기능을 순서대로 전달하는 톤)

## 1. V3 대비 달라지는 점

| V3 | V4 |
|---|---|
| 유즈케이스 나열(사원→팀장→회계→리드) 구조 | 동일한 인물 순서를 유지하되, **각 구간이 "질문/공감"으로 열림** |
| 곧바로 화면부터 시작 | **인트로는 8초 내외로 짧게 공감+정체성만 던지고, 이후는 유즈케이스 전개가 바로 이어짐** (CLAP 소개영상 참고: 도입은 짧게, 전개는 UI 기반으로) |
| 기능 소개가 중심 | **"이 사람이 지금 뭐가 답답한가"가 먼저, 기능은 그 답으로 등장** |
| 마지막에 슬로건만 짧게 | **아웃트로에서 문제→해결을 다시 요약**하며 브랜드 마무리 |
| 화면 전환이 컷 위주 | **질문 자막/내레이션 → 모션그래픽 전환 → 화면 진입**의 리듬을 전 구간에 통일 적용 |

### 연출 원칙 (V3 원칙 유지 + 추가)

1. 한 장면에서 하나의 문제만 제시한다.
2. **문제는 반드시 "질문형" 카피 또는 내레이션으로 먼저 던진 뒤 화면으로 들어간다.** (예: "이 지출, 영수증이 있었나 없었나...") 기능명부터 등장시키지 않는다.
3. 질문 → 화면 전환 사이에는 짧은 모션그래픽(0.5~1초)을 넣어 "지금부터 우리 서비스가 답한다"는 톤 전환을 만든다.
4. 문제를 보여준 직후 실제 버튼을 클릭한다.
5. 클릭 뒤 목록, 상태, 건수 또는 화면이 어떻게 바뀌는지 반드시 보여준다.
6. 버튼 이름은 실제 화면 표기를 그대로 사용한다.
7. 실제 데이터에 따라 달라지는 이름, 금액, 건수는 촬영 화면의 값을 사용한다.
8. 카드사 실시간 연동이나 외부 ERP 전송으로 오해할 표현은 사용하지 않는다.
9. 인트로·아웃트로는 화면 캡처가 아니라 모션그래픽/타이포 중심으로 구성해 데모 파트와 톤을 분리한다.

## 2. 전체 흐름 (기승전결)

```
[기 - 공감+정체성]  반복되는 정산 업무, 지치지 않나요? → 그래서 Tiger.inc를 만들었습니다 (8초, 한 호흡)
      ↓
[전 - 데모 4막]     사원 → 팀장 → 회계 담당자 → 회계 리드
                   (각 막마다: 질문 → 전환 → 시연 → 결과 → 인계)
      ↓
[결 - 요약]        문제 → 기능 → 가치를 다시 훑고 슬로건으로 마무리
```

| 팀장 | "우리 팀 지출, 뭐부터 봐야 하지?" | 이상건만 보기 + 자동 보완요청 |

### 인트로 (0:00~0:08) — 화면 캡처 없이 모션그래픽 중심, 한 호흡으로

> CLAP 소개영상처럼 도입은 짧게 끊고 바로 전개로 넘어갑니다. 공감과 정체성을 각각 3~4초씩, 총 8초 안에 붙여서 보여준 뒤 곧바로 사원 파트로 컷합니다. **별도의 "브릿지/예고" 구간을 두지 않습니다** — 사원 파트의 첫 질문("이 결제, 영수증 챙겨놨던가...?")이 자체적으로 전환 역할을 합니다. 철학(Rule First, AI Assisted)이나 Agent 개념도 여기서 설명하지 않고, 데모 중 해당 기능이 실제 등장하는 순간에 캡션으로만 짧게 붙입니다.

| 구간 | 시간 | 연출 | 카피(자막) | 내레이션 |

| 공감 | 0:00~0:04 | 어두운 배경, 영수증/엑셀/메신저 알림 아이콘이 빠르게 쌓였다 흩어지는 모션 | `반복되는 법인카드 정산,` `지치지 않으셨나요?` | "매달 반복되는 정산, 익숙하지만 지치는 업무입니다." |

## 6. 촬영 전 확인이 필요한 실제 데이터 (V3와 동일 + 인트로 추가 항목)

- 로그인할 사원, 팀장, 회계 담당자, 룰 활성 권한자 계정
- S-01에서 불러올 수 있는 표본 데이터의 남은 회차와 건수
- 증빙 `누락` 상태이며 상세 편집이 가능한 지출 건
- S-02의 이상 건 수와 정상 건 수
- S-03에서 AI 권장이 `보완요청`인 건과 고위험 상세 보고서가 준비된 건
- `확정 대기`에서 확정 후 전표(안)을 확인할 수 있는 건
- Rule Agent 생성에 사용할 실제 규정 문서명과 검색어
- 대화형 수정에 입력할 실제 조건 문장
- 시뮬레이션이 완료되는 데 걸리는 실제 시간
- Active 요청자와 `rule_activate` 권한을 가진 승인자 계정

## 7. 최종 내레이션 초안 (v4)

> 매달 반복되는 영수증 정리, 취합, 검토, 승인. 익숙하지만 지치는 업무입니다.
>
> 그래서 저희는 정산의 흐름을 하나로 이었습니다.
>
> 사원은 내역 불러오기로 결제 내역을 정리하는 것부터 시작합니다.
>
> 증빙이 없는 건만 바로 골라낼 수 있습니다.
>
> 초안 작성 Agent가 내용을 정리하면, 사원은 확인하고 필요한 부분만 고칩니다.
>
> 준비된 건은 한 번에 팀에 제출합니다.
>
> 팀장은 이상 건만 모아 먼저 확인합니다.
>
> 이상건 자동 보완요청을 누르면, 문제 건은 사유와 함께 담당자에게 돌아갑니다.
>
> 문제 건을 제외한 나머지는 회계로 일괄 제출됩니다.
>
> 자동 처리되지 않은 건만 위험도 순으로 모입니다.
>
> AI 권장이 보완요청인 건은 필터만으로 모아 사유를 확인한 뒤 일괄 처리합니다.
>
> 어떤 특징이 이상 신호가 되었는지, 어떤 규정이 근거인지 함께 확인합니다.
>
> 승인은 반드시 근거를 확인한 뒤 건별로 수행합니다.
>
> 검토가 끝난 건도 사람이 한 번 더 확정하고, 이후 내부 전표 초안이 자동 생성됩니다.
>
> 회계 리드는 등록된 규정 문서를 바탕으로 Rule Agent에게 룰 초안을 맡깁니다.
>
> 대화로 조건을 조정한 뒤, 실제 데이터에 먼저 적용해 결과를 확인합니다.
>
> 시뮬레이션을 마친 룰도 권한자의 최종 승인을 받아야 운영 기준이 됩니다.
>
> 각자의 문제는 화면 속 기능으로 해결되고, 모든 결정은 하나의 정산 흐름으로 이어집니다.
>
> 기준은 명확한 룰이 정하고, AI는 판단을 돕되, 최종 확인은 언제나 사람이 합니다.
