## §0. 조사 결론 (구현 전 사실 확인)

### 0.1 "다시 실행" 버튼 — 버그 아님, 실동작
- `SimulationTab.tsx:97-109` `run()`이 재실행 시에도 항상 `POST /rules/{id}/simulate`를 새로 호출한다(경량 캐시 경로 없음).
- `simulation.py:343` `run_and_save()`가 `graph_snapshot(graph)`로 **그 시점의 실제 노드/라우팅**을 다시 읽고 `RuleSimulationRun` **신규 row**를 생성한다(`runId` 자동증가, `#86→#87`).
- `stale` 배지는 `run.snapshot_hash != current_hash`로 계산(`simulation.py:399-420`) — 재실행 직후엔 방금 만든 run 해시가 곧 현재 해시라 `stale=False`가 되어 배지가 사라지는 것도 정상 동작.
- **혼란 원인**: 그래프 구조를 실제로 안 고치면 재실행해도 여전히 0.0%가 나와 "바뀐 게 없다"고 오해하기 쉽다. → §1-2(empty state)와 §3(원인 노출)로 완화.

### 0.2 "권장 처리" — LLM 아님, 결정론적 규칙
- `simulation.py:471-504` `_grades()`: 구조 평가(`poor`/`warn`/`good`)와 실행결과 평가(`poor`/`warn`/`good`) 각각을 별도 규칙으로 산정 → `worst = max(structure, result)`를 그대로 "권장 처리"로 채택, 3종 고정 문구로 매핑.
- LLM(`narrate.py`)은 이 확정된 등급을 facts로 받아 **서술문만** 작성한다. 등급 자체는 재계산하지 않는다(`narrate.py:6-8` 주석에 명시).
- 화면엔 구조/실행결과/권장처리 3개 카드가 각자 `note`를 갖고 있어 원인이 나뉘어 보이지만, "권장 처리" 카드의 `note` 자체는 원인 미표기(고정 3문구뿐).

## §2. 검증셋 품질

> ✅ **구현 완료(§11.3·§11.5) — 아래 원 설계와 실제 구현은 메커니즘이 다르다.** 핵심 차이:
> 원 설계는 "노드당 최소1+분기당 최소1"·"LLM에게 부족 카테고리 보충 요청"을 가정했지만,
> 실제로는 결정론적 후보 생성(노드당 최대 5종, `predictable`/`discovery` 이원화)만으로
> 충분히 5건 이상 나왔고 LLM 보충 루프는 필요 없었다. 아래는 원 설계(역사 기록) — 실제
> 최종 동작은 §11.3(2-1)·§11.5(2-2)를 볼 것.

### 2-1. 최소 5건 + 엣지케이스 설계
**현재(당시)**: `POST /rules/{id}/testcases/auto`가 그래프 조건을 역산(`_solve`)해 노드당 최소 케이스를 만드는데, 실측으로 2건까지 나올 수 있음(스크린샷: 테스트 수치 0/2). → **원인은 이후 §11.3에서 밝혀짐**: 이 미달의 진짜 원인은 카테고리 부족이 아니라 도달 불가 노드·종단 fallback 노드에 후보 예산을 낭비하고 있었던 것.

**원 설계 대비 실제 구현(요약, 상세는 §11.3·§12.4)**:
- ~~노드당 최소 1건 + 분기당 최소 1건~~ → **그래프 전체 최소 5건**(`MIN_TOTAL_TARGET`) +
  노드당 최대 5종(`MAX_CANDIDATES_PER_NODE`). ~~전체 상한 10건(`MAX_TOTAL_CANDIDATES`)~~ —
  2026-08-18에 "15건이 많다"는 피드백으로 도입했다가, 2026-08-19 "상한은 제거하는 게
  맞다"로 재요청되어 **철회**(§12.4). 지금은 상한 없이 노드당 최대 5종만으로 전체 규모를
  통제한다 — 노드가 많은 그래프는 정직하게 검증셋도 커진다.
- 엣지케이스 4카테고리 중 3종을 명시적으로 구현: ①경계값(`definite`/`boundary`, 원래 있던 것)
  ②**분기 반대편**(`opposite`/`opposite_boundary`) ③**결측**(`missing_fact`, 조건 참조 필드를
  통째로 비움). ④**복합 조건은 별도 카테고리로 안 만들었다** — AND 노드의 `definite`/
  `boundary`가 `_solve`의 "and" 처리에서 이미 모든 하위 조건을 동시에 만족시키는 값을
  계산하므로(코드로 확인) 자연히 커버된다. 별도 카테고리를 안 만든 게 누락이 아니라
  기존 메커니즘이 이미 그 요구를 충족한다는 뜻.
- ~~LLM에게 "카테고리가 비어있다" 알려 재생성 요청~~ → **LLM 관여 없음**. `predictable`
  (경계값류)은 결정론적 자체검증, `discovery`(반대편·결측류)는 "예측 없이 한 번 돌려서
  실제로 나온 값을 그대로 기록"하는 방식 — 둘 다 LLM이 아니라 결정론적 로직+실제 엔진
  호출로 해결된다(LLM은 여전히 표시용 라벨링에만 관여, §10.1).
- 소스 부족 시 안내: 설계대로 `belowTarget`/`minTarget` 필드로 "그래프 구조상 최소 5건을
  채울 소스가 없다"를 사실대로 보고(지어내지 않음) — 이 부분은 설계와 실제가 일치.

### 2-2. 피드백 루프 — 사유를 상세히 남기는 프롬프트
**현재(당시)**: §12 자체검증 루프(생성→`simulate_graph` 재검증→불일치 시 재생성)가 동작은 하지만, "무슨 문제가 있어서 어떻게 고쳤는지"에 대한 상세 로그/설명이 부족.

- 화면 노출 위치도 다름: ~~"검증셋 자동생성 결과 모달"~~ → 그 모달(`TestCaseModal.tsx`)

## §3. "권장 처리" 원인 노출

> ✅ **구현 완료(§10.3)** — 아래 설계 그대로 구현됨(divergence 없음). `cause` 필드명·
> 배지 위치·narrate 연동까지 설계와 일치.
> 🔁 **2026-08-19 추가 변경(§12.1)**: "권장 처리"가 여기서는 여전히 100% 결정론(구조/실행결과
> 중 더 나쁜 쪽)이었는데, 사용자가 "LLM이 조금 들어가서 판단해도 될 것 같다"고 재요청 —
> `narrate.py`가 서술과 **함께** action(level/note)도 재판단하도록 확장했다. 단 안전 하한은
> 서버가 강제한다(구조 poor면 LLM 응답과 무관하게 poor 유지). 상세는 §12.1.

**설계**: `_grades()`의 반환값에 원인 태그를 추가한다.
```python
# 기존: action = ("poor", "그래프를 수정한 뒤 다시 시뮬레이션하세요.")
# 변경:
action = ("poor", "그래프를 수정한 뒤 다시 시뮬레이션하세요.", cause=["structure"])  # 또는 ["result"], ["structure","result"]
```
- 프론트 "권장 처리" 카드에 `cause`에 따라 "구조 문제 때문" / "테스트 결과 때문" / "둘 다" 배지를 추가로 표시.
- `narrate.py` 프롬프트에도 이 `cause`를 facts로 넘겨 서술문이 "구조를 먼저 고쳐야 시뮬레이션이 의미 있다" 같은 우선순위를 언급하게 한다(구조 오류가 있으면 테스트 결과는 애초에 신뢰 불가 — 이 순서를 사용자가 알아야 함).

## §4. 그래프 수정 부분 컨텍스트 추가 (대화형 수정 에이전트)

> ✅ **구현 완료(§11.6)**. 확인 결과 "그래프 구조 컨텍스트"는 이미 §13.2에서 구현돼 있었다
> (전체 노드/라우팅 텍스트 덤프, `_build_user_prompt`/`_format_graph`) — 이 문서 작성
> 시점엔 "확인 필요"로만 적어뒀는데 실제로 열어보니 이미 있었다. 빠진 건 "시뮬레이션
> 결과 컨텍스트" 하나뿐이었고 그것만 추가했다.

현재 대화형 수정(§13.2에서 `node_key` 힌트 + 이전 대화 이력 재구성까지는 고쳤음)에 추가로 필요한 컨텍스트:
- **시뮬레이션 결과 컨텍스트**: 최근 실행의 `grades`/`stats`/위험변경 목록을 대화형 수정 세션에 주입 — "이 노드가 위험건 3건을 만들고 있다"는 사실을 사용자가 매번 설명하지 않아도 Agent가 알고 있게. → `django_client.get_latest_simulation()` + `_format_simulation()`으로 구현(§11.6).
- **그래프 구조 컨텍스트**: 현재 노드 목록·라우팅·도달불가 노드 목록을 매 턴 넘겨(이미 일부 되어 있을 가능성 높음 — §13.2 구현 확인 필요) 사용자가 "3번째 노드"처럼 지칭해도 매핑 가능하게. → **확인 결과 이미 구현돼 있었음**(`_format_graph`가 노드 전체 + 라우팅을 매 턴 덤프). 다만 `unreachable`(도달불가) 목록을 별도로 뽑아 강조하진 않는다 — 필요해지면 후속 개선.
- 설계만 명시하고 실제 프롬프트 조립 코드는 §13.2 구현(`converse` 엔드포인트, `apps/ai/app/agents/rule_agent_v0/`)에 이어붙이는 방식으로 후속 세션에서 구현. → 완료.

## §5. 모델 티어링 (gpt-5-mini / gpt-4o-mini)

> ✅ **구현 완료(§10.1) — 아래 표는 원 설계(사전 추정)다. 실제 코드 조사 결과 5행 중
> 2개가 틀렸다** — "검증셋 케이스 텍스트"와 "조건 역산 보조 텍스트화"는 애초에 서로 다른
> 두 호출이 아니라 **같은 호출 하나**(`_label_candidates`)였고, 그 호출이 하는 일도
> "기대판정 확정"이 아니라 **표시용 라벨링뿐**(판정은 `_solve`+결정론적 재검증이 정함)
> 이었다. 최종 확정 티어링(코드로 검증됨):

| 호출 지점 | 실제 위치 | 최종 모델 | 근거 |
|---|---|---|---|
| 룰 그래프 생성(규정→노드) | `agent.py::_run_generation_loop` | **gpt-5-mini**(`model_heavy`) | 실제 산출물(그래프 노드) 생성, 깊은 판단 필요 |
| 시뮬레이션 보고서 서술 | `narrate.py::narrate_report` | **gpt-5-mini**(`model_heavy`) | 사용자가 최종적으로 읽는 산출물, §6 상세 설명과 직결 |
| 대화형 수정 — 자연어 해석·필드 매핑 | `chat.py::converse` | **gpt-5-mini**(`model_heavy`) | §13.6/13.9에서 이미 "이상값 감지"·"정성적 판단 오남용 방지" 같은 깊은 판단 필요 확인됨 |
| 검증셋 표시용 라벨링(label/merchant/금액) | `testcases.py::_label_candidates` | **gpt-4o-mini**(`model`, 경량 유지) | 판정과 무관한 서술 전용 — 실패해도 기본값 대체, 틀려도 판정 로직 안 깨짐(원 설계의 "틀리면 신뢰도 깨짐" 우려는 이 호출엔 해당 안 됨) |

- ~~검증셋 케이스 텍스트 초안 / 조건 역산 보조 텍스트화 (2행)~~ → **애초에 별개 호출이
  아니었다.** 코드 조사로 밝혀짐 — `_label_candidates` 하나가 이 둘을 다 포괄한다.
- **실측 버그**: gpt-5-mini류는 커스텀 `temperature`를 지원하지 않아(기본 1만 허용) 전환
  직후 3개 호출이 전부 조용히 실패하고 있었다(§10.1에 상세). `temperature` 파라미터 제거로
  해결. 이후 지연시간 문제(20~40초)가 추가로 발견돼 `reasoning_effort='low'`를 기본값으로
  도입(§11 이전 대화 로그 — medium 대비 거의 절반으로 단축, 품질 차이 뚜렷하지 않음).
- gpt-4o-mini(경량) 호출은 출력 스키마를 엄격 고정(`json_schema` strict)해 자유도를 낮췄다 —
  원 설계의 "few-shot·에스컬레이션 폴백" 제안은 필요 없었다(실패 시 결정론적 기본값으로
  대체하는 것만으로 충분).

## §7. "최근 내역 결과" 3단계 전이 — 이미 구현된 부분과 다듬을 부분

> ✅ **구현 완료(§10.2)** — "다듬을 부분"에 적힌 3개 항목 전부 구현됨: `SYSTEM_FLAG_KO`
> 딕셔너리, 1줄요약+"자세히 보기" 토글 구조, `reversal`(완전 반전) 신규 등급.

**이미 구현됨** (`simulation.py:159-188` `_change_comment`, `SimulationReport.tsx:130-184`):
- REVIEW→PASS 등 일반 개선은 `intended`(경량, 파란 톤 "💬 정상 변경").
- RETURN/REJECT→PASS(반려였는데 통과로 뒤집힘) 등 심각한 반전은 이미 `risk`(강조, "⚠ 위험 변경")로 분류되고, 화면 기본 필터도 `risk`로 시작.

**다듬을 부분(당시 신규 설계 → 전부 구현 완료)**:
- `_change_comment`의 문구가 기술적("근거 플래그: PERSONAL_USE_SUSPECTED, 평가 경로 GLOBAL→R-003→...")이라 비개발자에게 어려움. → 플래그 코드를 사람이 읽는 한글 사유로 매핑하는 사전(`FLAG_KO` 같은 딕셔너리)을 만들어 `because` 절을 대체. → `SYSTEM_FLAG_KO`+`_flag_label()`로 구현(엔진 고정 플래그만 번역, 룰 작성자 임의 코드는 원문 유지).
- "핵심 문장 먼저, 기술 디테일은 접어서" 구조로 재작성: 1줄 요약(굵게) + "자세히 보기" 토글에 노드/플래그/경로 원문. → `RuleSimulationResult.ai_comment_detail`(마이그레이션 0017) + 프론트 `HistoryRow` 토글로 구현.
- risk/intended 두 갈래로는 세분화가 부족하다는 사용자 지적 반영 — **반려→통과** 같은 "완전 반전"은 risk 안에서도 별도 강조(예: 빨간 테두리 + "⚠⚠ 완전 반전" 배지)로 한 단계 더 구분. → `commentVerdict`에 `reversal` 신규 등급으로 구현.

## §8. 후순위 백로그 — 2026-08-19 방향 전환("문서 통합" 폐기, "API 노출"로 대체)

> 🔁 **원 계획(정적 마크다운 문서로 통합) 폐기.** §13을 구현하며 사용자가 직접 지적—
> "모델에서 받아올 수 있게 구현했는데, 그럼 문서를 통합할 필요는 없지 않나?" 정확한
> 지적이다: decision/severity도 원래 "문서화 부재"가 아니라 "하드코딩 4곳" 문제였고,
> 해결책은 문서가 아니라 API 단일 소스화였다(§13). 만약 그때 "문서로 통합"했다면
> 하드코딩 사본이 하나(마크다운) 더 늘었을 뿐 드리프트 문제는 그대로였을 것 — **정적
> 문서는 코드가 바뀔 때마다 손으로 갱신해야 하는 또 다른 하드코딩 사본에 불과하다.**

**남은 항목 재분류(원래 하나로 뭉쳐 있던 걸 세 성격으로 나눔)**:
1. **열거 가능한 카탈로그** — API로 노출하면 끝, 문서 불필요.
   - ✅ decision/severity: §13에서 완료.
   - ✅ EvalContext 필드 목록(dot-path): 이미 `eval-context-schema` API로 노출 중(이전부터).
   - 🔲 **DSL 연산자**(`dsl.py::OPERATORS`): 아직 API로 안 나감 — `agent.py`의
     `_CONDITION_NODE_SCHEMA`가 연산자 목록을 자체적으로 하드코딩하고 있어 decision/severity와
     같은 유형의 잠재적 드리프트가 있다(이번엔 안 고침 — 후속 후보로 기록만).
2. **필드 설명/근거** — 정적 문서가 아니라 **API 응답에 설명 필드 추가**가 같은 원칙에 맞음.
   - 🔲 `eval_context.py`의 한글 주석("왜 이 필드가 남았는지")이 dot-path 문자열 목록에만
     묻혀 있고 API가 안 실어 나름 — LLM은 필드가 "존재한다"만 알고 "왜/무슨 뜻인지"는 모른다.
     되살릴 때는 `_SCHEMA_FIELDS`를 `{path: description}` 구조로 바꿔 설명을 **문자열
     데이터**로 격상(지금은 파이썬 주석이라 애초에 API가 못 읽음)하고 그 확장된 응답을
     그대로 노출하는 방향 — 별도 문서를 새로 안 만든다.
3. **엔진 동작 원리**(None=모름 계약, GLOBAL 게이트 우선순위 등) — 이건 데이터가 아니라
   "여러 시스템이 어떻게 상호작용하는지"에 대한 서술이라 애초에 "모델에서 끌어올" 대상이
   아니다. 각 시스템 프롬프트(`chat.py`/`narrate.py`)에 필요한 부분만 국소적으로 이미
   들어가 있다 — 대문서로 몰아넣는 게 오히려 새 정적 사본을 만드는 것과 같아 보류.

여전히 사용자 지시대로 **본격 착수는 안 함** — 위 재분류·원칙 정리까지만(2026-08-19).
다음 착수 후보는 1번의 DSL 연산자 노출(가장 작고 §13과 같은 패턴이라 리스크 낮음).

## §10. 구현 결과 (2026-08-18, §9의 1~4번)

### 10.1 모델 티어링 — 코드 조사로 표가 바뀜
실제 호출부를 열어보니 §5의 가정과 달랐다: `testcases.py`의 LLM 호출은 검증셋의 **기대 판정을
정하지 않는다** — 판정은 전부 `_solve`+결정론적 재검증(§12)이 정하고, 이 호출은 화면에 보일
라벨·가맹점명·표시용 금액만 지어낸다(실패해도 기본값 대체, 판정 로직 무관). 반면 `agent.py`
(규정→룰 그래프 생성)·`chat.py`(대화형 수정)·`narrate.py`(시뮬레이션 보고서 서술)는 전부 실제
산출물을 만들거나 깊은 판단이 들어간다. 그래서 최종 티어링은:
- **`model_heavy`(`gpt-5-mini`)**: `agent.py`(룰 생성), `chat.py`(대화형 수정), `narrate.py`(보고서)
- **`model`(`gpt-4o-mini`, 기존 경량)**: `testcases.py`(표시용 라벨링만)

`settings.py`에 `model_heavy` 필드 신설, `docker-compose.yml`·`.env.example`에 `RULE_AGENT_MODEL_HEAVY` 추가.

**실측 버그 발견·수정**: `gpt-5-mini`류 추론 모델은 **커스텀 `temperature`를 지원하지 않는다**
(기본값 1만 허용, 다른 값을 주면 400 `Unsupported value`). 세 호출 모두 `temperature=0.2~0.4`를
그대로 넘기고 있어서 **전환 직후 전부 조용히 실패**하고 있었다(호출부가 전부 `except Exception`
폴백을 갖고 있어 에러가 겉으로 안 드러났다 — narrate는 템플릿 서술로, chat/agent는 별도 확인
필요). 세 호출에서 `temperature` 파라미터를 제거해 해결(경량 `testcases.py`는 그대로 유지 —
`gpt-4o-mini`는 커스텀 temperature를 지원한다). 실브라우저 재현으로 최종 확인: 수정 전엔 시뮬레이션
보고서가 "플레이스홀더 보고서" 태그와 함께 룰 기반 템플릿으로만 떴고, 수정 후엔 실제 LLM이 쓴
서술(`## 개요`, `## 그래프 구성 평가`, `## 실행결과`, `## 주의깊게 살펴봐야 할 부분` 전부 사실
기반 문장)로 바뀌고 플레이스홀더 태그가 사라졌다(run #90→#92 대조).

### 10.2 최근 내역 결과 문구 다듬기
`simulation.py`에 `SYSTEM_FLAG_KO`(엔진 고정 플래그 4종만 번역 — 룰 작성자가 붙이는 임의 코드는
회사 규정마다 달라 사전 번역 불가, 원문 유지)와 `_flag_label()` 추가. `_change_comment()`를
"한 줄 요약(쉬운 문장)"과 "자세히(플래그·평가경로, 기술 상세)"로 분리 — `RuleSimulationResult`에
`ai_comment_detail` 필드 신설(마이그레이션 `0017`), 프론트 `HistoryRow`에 "자세히 보기" 토글 추가.
`commentVerdict`에 `reversal`(반려/보완요청 → 통과로 완전히 뒤집힌 최우선 확인 대상) 등급을
새로 도입해 기존 `risk`보다 한 단계 더 강조(테두리 두께·굵은 텍스트). `risk` 판정 로직에 `reversal`을
빠뜨리면 위험건 필터에서 누락되는 실수를 코드 리뷰 중 자체 발견해 `verdict in ("risk", "reversal")`로 수정.

### 10.3 권장 처리 원인 노출
`_grades()`가 반환하는 `action`에 `cause`(`["structure"]`/`["result"]`/둘 다) 필드 추가, `note`도
"원인: 그래프 구조. ..." 형태로 원인을 명시하도록 재작성. 프론트 `GradeTile`에 원인 배지 렌더링
추가. 실측(그래프 81, 도달불가 노드 1개 + 위험변경 4건 케이스): "권장 처리" 카드에 "원인 · 구조
문제" 배지가 정확히 뜸.

### 10.4 empty state
`SimulationTab.tsx`에 `revealed` 상태 신설 — 그래프 진입 시 과거 실행 이력이 있어도 즉시 펼치지
않고 `SimulationCollapsedSummary`(요약 1줄 + 펼치기/재실행/자동생성 버튼)만 보여준다. "펼쳐서
보기"를 누르거나 새로 실행(또는 자동생성)하면 그때 `SimulationReportView`(전체 통계·Agent 의견·
결과 리스트)로 전환. 실행 이력이 아예 없으면 기존 `SimulationEmptyState` 그대로.

### 10.5 검증

## §11. 구현 결과 (2026-08-19, §9의 5~7번 + 후속 요청 3건)

같은 세션에서 사용자가 실사용하며 추가로 낸 요청 3건(타임아웃·펼쳐보기 제거·검증셋
버튼 통합, 최소 5건 미달, 상한 10건, append→replace, §5/§7 잔여)을 §9 순서 그대로 마저
구현했다. 이 절은 최종 상태만 기록한다(중간 경과는 대화 로그 참조).

### 11.1 타임아웃 원인 2건 (검증셋 자동생성이 30~60초+ 걸리던 문제)
- **내부 검증 호출에도 매번 서술(narrate) 생성**: 자체검증 루프가 노드마다 `/simulate`를
  최대 2회 내부 호출하는데 아무도 그 서술을 안 읽으면서도 심층 모델을 태우고 있었다.
  → `simulate_graph(graph_id, narrate=False)`로 내부 호출만 서술 생략(`views.py`의
  `simulate` 액션에 `narrate` 플래그 추가).
- **AI→Django 내부 호출 타임아웃(20초)이 Django의 서술 예산(60초)보다 짧음**: narrate=True
  호출이 Django 쪽에서 아직 응답 중인데 AI 쪽 `core_auth.TIMEOUT`(20초 고정)이 먼저
  끊어버렸다. → `simulate_graph()`가 narrate=True일 때만 75초로 개별 오버라이드.

### 11.2 "펼쳐서 보기" 제거 → "검증셋 자동생성" 버튼도 제거(§1-1 완결)
사용자가 두 차례에 걸쳐 단순화를 요청 — 먼저 컷 사이 중간 단계("펼쳐서 보기")를 없앴고,
이어서 "검증셋 자동생성"과 "시뮬레이션 실행"을 완전히 하나로 합쳤다. 지금은 **"시뮬레이션
실행하기"/"다시 실행" 버튼 하나만** 존재하며, 누르면 검증셋을 그래프 현재 조건으로 새로
만들고(§11.4의 replace) 곧바로 시뮬레이션까지 실행해 전체 보고서를 보여준다. `SimulationCollapsedSummary`
컴포넌트·`endpoints.simulateRule`/`ruleTestCases`·프론트 `testCases` 상태·`TestCaseModal.tsx`
(자연어 mock 편집 모달, 사용자 확인 결과 "실제 만든 화면이지만 자동생성이 유일 경로가 된 뒤로 불필요")
전부 제거. 화면에 남는 유일한 진입점은 실행 버튼과, 실행 후 결과 리스트뿐이다.

### 11.3 검증셋 최소 5건 미달 문제 — 실제 원인은 후보 생성 낭비였다
2건에서 멈춘 원인을 실측으로 추적: (a) 도달 불가 노드(R-N1)에 후보를 만들어도 항상
자체검증 실패, (b) 조건이 항상 참인 종단(fallback) 노드(T-PASS)는 노드 하나만 봐서는
도달 경로를 못 만들어 역시 항상 실패 — 두 경우 다 "실패할 걸 알면서" 후보 예산을
태우고 있었다. `_reachable_node_keys()`(BFS)로 도달 불가 노드를 사전에 건너뛰고,
`condition is True`인 종단 노드도 건너뛰도록 `_candidates_for_node()`를 고쳤다.
그 뒤 §2-1 엣지케이스 4종 중 실제 구현된 3종(경계값 반대편·결측 — "복합조건"은 백로그)을
추가해 노드당 최대 5종까지 후보를 만들고, `predictable`(정의/경계값 — 자체검증)과
`discovery`(분기반대편/결측 — 예측 불가라 실제로 한 번 돌려 나온 값을 그대로 기록)로
나눠 처리한다.

**부수 발견 — 그래프 81(출장비) 자체의 실제 결함**: 엣지케이스 생성이 "한도 미달인데도
RETURN이 나온다"는 그래프 콘텐츠 버그를 실사용으로 드러냈다. 원인은 `engine.py:173`의
종단 처리(다음 노드 없는 라우팅에 도달하면 매칭 여부와 무관하게 **직전 노드의 decision을
그대로 반환**)와, 이 그래프의 MATCH/NO_MATCH 라우팅이 뒤바뀌어 있던 것 + 종단 노드
`T-PASS`의 decision이 `PASS`가 아니라 `RETURN`으로 잘못 저장된 것의 조합. 사용자 확인 후
라우팅 스왑 + `T-PASS.decision`을 `PASS`로 수정(DB 직접 수정, 코드 버그 아님).

### 11.4 append → replace, 그리고 상한 10건
- **replace 전환**: 수동 검증셋 모달을 없앤 뒤로 "검증셋 자동생성"이 유일한 생성 경로가
  됐으므로, 매번 "지금 그래프 기준으로 있어야 할 검증셋"을 새로 만드는 게 맞다고 판단.
  `existing` 병합·`_facts_signature` 기반 dedup·`ALREADY_COVERED` 상태를 전부 제거하고
  매 호출마다 전체를 새로 만들어 그대로 저장(Django `PUT`은 원래도 전체 교체라 프론트/AI
  양쪽에서 "기존 것과 합치기"만 걷어내면 됐다). 실측: 같은 그래프에 반복 실행해도 건수가
  안 쌓이고 고정됨(idempotent) 확인.
  **부수 발견**: replace 전환 직후 예전(append 시절) 자동생성 결과가 여러 그래프(37번
  15건 등)에 그대로 남아있었는데, 이건 seed 데이터가 아니라 "구버전 코드로 만들어진 실행
  결과"였다(seed_rules.py는 룰 그래프만 만들고 테스트케이스는 안 만든다 — 회식비 v2(37번)
  검증) — 재실행으로 정리.
- **전체 상한 10건**: 노드가 많은 그래프(4노드 예시)에서 15건까지 나온 게 과하다는 피드백
  으로 `MAX_TOTAL_CANDIDATES=10` 도입. predictable은 안 자르고(노드 커버리지 핵심)
  discovery만 노드별로 라운드로빈으로 골고루 덜어낸다(`trimmedForCap`로 몇 건 잘렸는지
  화면에 표기).

### 11.5 §2-2 — 검증셋 생성 피드백 루프 사유 로그
구현 중 검토하다 실제 버그를 하나 더 발견: predictable 자체검증의 "1회 재시도"가 후보
facts를 전혀 안 바꾼 채 결정론적 엔진에 다시 넣는 것이었다 — 즉 재시도해도 항상 첫
시도와 똑같은 결과가 나오는 죽은 코드(주석은 "마진을 좁혀 재시도"라 적혀 있었지만
실제로 그렇게 구현된 적이 없었다). 재시도 루프를 단회 검증으로 바꾸고, 그 대신 실패
사유(우선순위 높은 다른 노드가 가로챘는지 / decision 설정 자체가 다른지)와 discovery
후보가 무엇으로 확정됐는지를 `generationLog`에 구조화해 담는다. 프론트는 genNote 옆에
"이번 생성에서 발견한 사항 N건 보기" 아코디언으로 노출(원 설계는 별도 모달을 가정했으나
그 모달이 이미 삭제된 뒤라 시뮬레이션 탭 인라인으로 대체).

### 11.6 §4 — 대화형 수정에 시뮬레이션 결과 컨텍스트 주입
그래프 구조 컨텍스트는 이미 `_build_user_prompt()`가 전체 노드/라우팅 덤프로 주고 있어서
(§13.2 구현 확인 결과) 새로 할 게 없었다. 빠진 건 시뮬레이션 결과뿐이었다 —
`django_client.get_latest_simulation()`(신규, `GET /rules/{id}/simulation/` 래퍼) 추가,
`_format_simulation()`이 권장 처리·통계·위험 변경건 예시 최대 3건만 추려 프롬프트에
얹는다(전체 덤프 안 함 — 대화형 수정에 실제 쓸모있는 건 "지금 뭐가 문제인가"뿐).
시스템 프롬프트에도 "애매한 질문 받으면 되묻기 전에 이 결과부터 확인" 규칙 추가.
직접 호출로 확인: `converse()` 프롬프트에 실제 그래프의 권장 처리 사유·위험 변경건
3건이 들어감.

### 11.7 §6 — 보고서 설명 상세화
`_narrative_facts()`에 `testExamples`(합격/불합격 대표 1건씩)·`riskyExamples`(위험 변경

'숙박비 1박 한도 초과'는 path ["T-102"] 경로를 거쳐 "RETURN"으로 판정되었습니다"처럼
실제 사례를 인용하는 것을 확인(수정 전엔 집계 수치만 나열).

## §12. 구현 결과 (2026-08-19, 실사용 재요청 4건)

실사용하며 사용자가 이전 결정 3개를 재검토 요청 + 새 요청 1개. §1-2·§2-1·§3 본문에도
상태 갱신 링크를 남겼다 — 이 절은 각각의 구현 상세.

### 12.1 "권장 처리"에 LLM 판단 반영(§3 확장)
`_grades()`의 구조/실행결과 등급 산정 로직 자체는 그대로 결정론 유지(바꿀 이유가 없음 —
"둘 다 독립된 안전검사"라는 원래 취지가 여전히 유효). 바뀐 건 그 위에 얹는 **action(권장
처리) 등급**만 — 기계적으로 `max(structure, result)`만 쓰던 걸, `narrate.py`가 서술문을
쓰면서 `facts` 전체(구조·통계·위험변경 사례·대표 케이스)를 종합해 action.level/note를
**재판단**하도록 확장했다.

- **안전 하한은 서버가 강제**: `simulation.py::apply_action_assessment()`가 `grades.structure.
  level == "poor"`면 LLM이 무슨 값을 줬든 `level`을 `poor`로 되돌린다. 프롬프트 지시("구조가
  poor면 반드시 poor 유지")만으로는 LLM이 무시하거나 실수할 수 있어 코드로 한 번 더 검증한다
  — "그래프가 구조적으로 깨진 상태를 활성화해도 된다"고 판단하는 일은 어떤 경우에도 일어나지
  않아야 하는 안전 불변식이라 프롬프트만 믿지 않았다.
- **구조 응답 형식 변경**: `narrate_report()`가 문자열 대신 `{"report": str, "action":
  {"level", "note"}}`를 `response_format=json_schema`(strict)로 받는다. FastAPI
  `/agent/rule-v0/narrate-report`·Django `views.py::simulate()`·`RuleSimulationResult`
  저장 경로까지 이 구조에 맞춰 갱신.
- **화면 표시**: `Grade`에 `aiAdjusted?: boolean` 추가, "권장 처리" 카드에 그 등급이
  Agent 재판단인지 표시하는 "🤖 Agent 판단" 배지(`cause` 배지와 나란히).
- **실측**: 그래프 81(구조 poor) → action이 여전히 `poor`로 강제되지만 `note`는 LLM이 쓴
  구체적 문장("구조적으로 진입점에서 도달 불가 노드(R-N1)가 발견되어...")으로 대체됨,
  `aiAdjusted: true`. 그래프 37(구조 good, 결과 warn) → action `warn`, LLM이 "M-005 관련
  판단 근거와 REVIEW로 빠지는 임계값을 확인한 뒤 활성화를 결정하세요"처럼 기계적 문구보다
  구체적인 근거를 씀.

### 12.2 검증셋 표시용 라벨링 — 설명(코드 변경 없음)
`testcases.py::_label_candidates()`. 후보(`_solve()`가 계산한 숫자 조건값)에 사람이 읽을
가맹점명·케이스 라벨·표시용 금액만 붙이는 LLM(gpt-4o-mini, 경량) 호출. 판정(기대값)은 이미
`_solve()`가 결정론적으로 정한 뒤라 이 호출이 실패해도 표시용 기본값으로 대체될 뿐 판정
로직엔 영향이 없다 — 그래서 여기만 유일하게 경량 모델을 유지한다(§10.1의 최종 티어링 표
참조).

### 12.3 시뮬레이션 보고서 — 이전 결과 있으면 즉시 표시(§1-2 재차 뒤집힘)
`SimulationTab.tsx`에서 `revealed` 상태를 완전히 제거했다. `report`(최근 실행 결과)가
있으면 그 자체가 "보여줄 게 있다"는 뜻이라 별도 플래그가 불필요 — 그래프 선택 즉시
`ruleSimulation()` 조회 결과가 있으면 `SimulationReportView`를 바로 렌더링한다. 실행
이력이 전혀 없는 그래프에서만 `SimulationEmptyState`("아직 시뮬레이션을 실행하지
않았습니다" + "시뮬레이션 실행하기" 버튼)가 보인다. `SimulationEmptyState`의 `lastRun`
prop(과거엔 "이전 실행 결과 있음" 문구 분기에 썼음)도 이제 도달 불가능한 코드라 함께
제거. 실측: 회식비 그래프 선택 시 클릭 없이 곧바로 "다시 실행" 버튼 + 결과 리스트(15건)
표시 확인.

### 12.4 검증셋 상한 제거(§2-1 재차 뒤집힘)
`MAX_TOTAL_CANDIDATES`(10)와 그 트리밍 로직(라운드로빈으로 discovery만 깎던 코드) 전체
삭제. API 응답의 `trimmedForCap`/`maxTarget` 필드, 프론트 대응 메시지도 함께 제거. 노드당
최대 5종(`MAX_CANDIDATES_PER_NODE`)만으로 전체 규모를 통제 — 노드가 많은 그래프는 검증셋도
정직하게 커진다. 실측: 회식비 그래프(4개 조건 노드) 재생성 시 10건 상한 없이 15건 그대로
생성됨.

### 12.5 검증
- Django 회귀 149건, 프론트 `tsc -b && vite build` — 4개 변경 반영 후 통과.
- 직접 호출로 §12.1 하한 강제 확인(그래프 81 구조poor→action poor 강제, 그래프 37
  구조good→LLM 재량 판단 확인), §12.4 상한 해제 확인(회식비 15건).
- Playwright로 §12.3 실측(그래프 선택 즉시 결과 표시, 실행 버튼 없이).

## §13. 구현 결과 (2026-08-19, §8 후속 — decision/severity 단일 소스화)

§8(DSL·EvalContext 전수조사)은 여전히 후순위지만, 그 조사 과정에서 나온 구체적 갭 하나
(action 카탈로그 중복)를 사용자가 "구현되게 만들 수 있나"로 요청해 이번에 처리했다.
DSL 연산자 카탈로그(`dsl.py::OPERATORS`) 노출과 EvalContext 스키마의 설명 주석 노출은
여전히 미착수 — 이 절에서 다룬 건 decision/severity뿐이다.

### 13.1 조사로 드러난 실제 중복 현황
- **decision**: Django `engine.py:11`에 진짜 소스(`DECISIONS = {"PASS","REJECT","REVIEW","RETURN"}`,
  순회 검증에 실제로 쓰임)가 있는데, `agent.py`가 이를 import하지 않고 `["PASS","REJECT","RETURN","REVIEW"]`로
  독립적으로 재입력했고, `chat.py`가 또 별도로(`["PASS","REJECT","RETURN","REVIEW"]`) 재입력했고,
  프론트 `DraftTab.tsx`가 `<option>` 4개(+`PASS_THROUGH`)를 하드코딩 — **한 값을 4곳에서
  독립적으로 유지**하고 있었다.
- **severity**: Django 어디에도 정의가 없다(`RuleNode.action`은 무제약 JSONField, engine.py
  로직이 severity를 아예 안 읽음). `agent.py`·`DraftTab.tsx` 2곳에 각자 하드코딩 — 이쪽은
  "진짜 소스가 원래 없던" 경우.

### 13.2 구현
- Django `engine.py`에 `PASS_THROUGH` 상수 + `DECISIONS_CATALOG`(순서 있는 튜플, PASS_THROUGH
  포함)·`SEVERITIES_CATALOG` 신설 — **이 모듈이 유일한 소스**.
- `rule_agent_v0_views.py::ActionSchemaView`(`GET /api/internal/rule-agent-v0/action-schema/`,
  AllowAny, AI 서비스용) + `RuleGraphViewSet.action_schema`(`GET /api/rules/action-schema/`,
  `rule_view` capability, 브라우저용) — 같은 payload(`action_schema_payload()`)를 재사용.
- AI 서비스: `django_client.get_action_schema()` 신설(`get_eval_context_schema()`와 같은
  패턴 — 실패 시 옛 하드코딩 값과 동일한 기본값으로 폴백). `agent.py`의 모듈 레벨
  `DECISIONS`/`SEVERITIES`/`SEVERITY_PRIORITY` 상수를 지연 초기화 함수(`_action_schema()`
  캐시 + `decisions()`/`severities()`/`severity_priority()`)로 교체 — `_openai()`와 같은
  지연 초기화 패턴(import 시점에 Django가 안 떠 있어도 라우터가 안 죽음). `_RESPONSE_SCHEMA`/
  `_SUBMIT_NODES_TOOL`(생성 흐름)과 `chat.py`의 `_UPDATE_NODE_TOOL`/`_CREATE_NODE_TOOL`/
  `_ALL_TOOLS`(대화형 수정)도 모듈 상수에서 **호출 시점에 조립하는 함수**로 전환(동적 enum을
  담아야 해서). `testcases.py`의 죽은 `SEVERITIES` import도 함께 정리.
  - `_response_schema()`(생성 흐름)의 decision enum은 의도적으로 여전히 서브셋
    (`REJECT`/`RETURN`/`REVIEW`만) — v0 설계상 생성 흐름은 PASS 종단 노드를 만들지
    않는다(모듈 docstring). 전체 카탈로그를 그대로 쓴 게 아니라 카탈로그에서 서브셋을
    뽑는 관계라는 걸 주석으로 명시.
- 프론트: `endpoints.ruleActionSchema()` 추가, `DraftTab.tsx`가 마운트 시 fetch해
  `decisionOptions`/`severityOptions` state로 보관(실패 시 옛 하드코딩 기본값 폴백) →
  `NodeDetail` 서브컴포넌트에 props로 전달, `<option>` 하드코딩 나열을 `.map()`으로 교체.

### 13.3 검증
- Django 회귀 149건, 프론트 `tsc -b && vite build` 통과.
- `GET /api/internal/rule-agent-v0/action-schema/` 직접 호출로 payload 확인
  (`decisions: [PASS, REJECT, RETURN, REVIEW, PASS_THROUGH]`, `severities: [...]`).
- AI 컨테이너 재기동 후 `agent.decisions()`/`agent.severities()`가 실제로 이 값을
  fetch해오는 것 확인, `chat.converse()` 정상 동작(회귀 없음) 확인.
- Playwright로 `DraftTab.tsx`의 "결정 선택" 드롭다운이 서버 값(`PASS, REJECT, RETURN,
  REVIEW, PASS_THROUGH`)으로 채워지는 것 확인.
