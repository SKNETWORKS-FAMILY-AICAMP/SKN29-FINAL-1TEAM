# 기본 게이트(DEFAULT GATE) 설계

_최종 갱신: 2026-08-22 · 상태: 구현 완료 (`seed_clean`)_

> **제품이 미리 준비해 제공하는 룰은 `DEFAULT GATE` 하나뿐**이다. 카테고리별 세부 룰은
> 고객이 자사 규정 문서를 올리면 Rule Agent가 만든다. 이 문서는 그 하나가 어떻게 생겼고
> 왜 그렇게 생겼는지를 적는다.

관련: [[rule-engine]] · [[rule-flags]] · [[settlement-ui-rules]] · [[category-vocabulary]]

⚠️ 게이트는 **DB에 저장된 그래프**다 — 코드를 고쳐도 `seed_clean`을 다시 돌리기 전엔 반영되지 않는다.

---

## 1. 방향: 통과가 기본이 아니다

처음엔 "걸리는 것만 걸고 나머지 PASS"였다. 그러면 게이트가 못 보는 축(심야·이상 패턴·회사
규정)이 전부 조용히 승인 대기로 흘렀다 — 갓 설치한 회사에서 아는 게 거의 없는데 **모르는 것을
통과로 접은** 셈이다.

**지금**:

| | |
|---|---|
| 기본 | `REVIEW` — 다만 **사유(플래그)를 달아서** 넘긴다(검토자가 빈손으로 받지 않는다) |
| `PASS` | **화이트리스트** — 증빙·목적·분류가 모두 있고, 업종 확인됨, 위험업종 아님, 30만원 미만(`AUTO_PASS_MAX_AMOUNT`) |
| `RETURN`·`REJECT` | **내지 않는다** |

`RETURN`을 쓰지 않는 이유: 지출자에게 일을 되돌려보내는 결정이라, **회사가 무엇을 요구하는지
정해지기 전에** 내릴 결정이 아니다. 회계가 큐에서 보고 필요하면 그때 보완요청한다.

## 2. 왜 정책 판단을 넣지 않는가

회사 규정이 없는 상태라 한도·기한 같은 판단을 넣을 수 없다. `policy.*`는 회사 별표에서 오는데
신규 설치엔 없으므로, 참조하는 순간 **미해소 가드가 전건 REVIEW로 강등**해 게이트가 무용지물이 된다.

거는 축은 **어느 회사에나 해당하는 것**뿐이다:
법령·세법 위험 업종(사행성·유흥·노래연습장) · 고액 · 증빙/목적/분류 미기재 · 실사용자 미등록.

심야·주말·이상 패턴은 **일부러 뺐다** — Risk Review의 일이고 회사마다 정상 범위가 다르다.
PG사 결제 여부도 뺐다: 판정에 쓸 사실이 없다(`tx.payment_method`는 조립기가 `"법인카드"` 고정으로
넣고 원장에도 PG 식별자가 없다).

## 3. 사유가 전부 붙는다 — `PASS_THROUGH` 체인

사유마다 단말로 끊으면 **첫 하나만** 남는다. `PASS_THROUGH` 노드가 사유를 쌓아 마지막 판정
노드까지 보낸다 — 금지업종 · 업종 미확정 · 증빙 누락 · 목적 누락 · 분류 미기재 · 실사용자 미등록 ·
고액 7종.

**자동 통과 조건이 사유 노드와 중복 기술되는 건 불가피하다**: 플래그는 상태머신을 움직이지
않는다는 불변식([[rule-flags]]) 때문에 엔진이 「지금까지 붙은 플래그」를 조건으로 읽을 수 없다.
그게 설계 의도다.

## 4. 미해소 가드를 분기로 우회한다

미해소 가드는 노드가 **참조한** 경로의 `null`을 보고 강등한다. 그래서 금지업종 노드가
`merchant.merchant_type`을 참조하는 한, 업종 미확정 건은 실제로 금지업종이 아니어도 전부
강등된다(신규 설치엔 가맹점 캐시가 비어 있어 그게 대다수다).

| 분기 노드 | 하는 일 |
|---|---|
| `n_industry_known` | 업종 확인 여부만 보고 **확인된 건만** 금지업종 노드로 보낸다 |
| `n_autopass_gate` | 자동통과 노드도 업종 아는 건만 — 안 그러면 업종 미확정 건에 `UNRESOLVED_FACT:merchant.merchant_type`가 붙어 이미 더 정확한 `MERCHANT_UNRESOLVED`와 중복된다 |

**참조 필드는 조립기가 항상 채우는 것만** 고른다. 공용카드 실사용자 미등록(`None`)은 룰로 막지
않고 **엔진 가드에 맡긴다** — 같은 규칙을 두 곳에 적으면 한쪽이 뒤처진다.

## 5. 승인대기 건은 Risk Review를 안 거친다

`risk_review.schedule()`이 `IN_REVIEW`만 예약한다(설계 그대로). 화면이 그걸 `0.00`으로 그려
「이상 없음」으로 읽히던 것을 `SettlementSerializer.riskReviewed` + `RulePassedNotice`로 고쳤다
— 「룰 판정으로 통과된 건 — 이상탐지·RAG 검증을 거치지 않았습니다」 + 판정 경로
([[settlement-ui-rules]] §2).

## 6. `seed` vs `seed_clean`

| | 목적 |
|---|---|
| `seed` | 시연 데이터 한가득(정산 87건·룰 4계열·규정 하이라이트). 화면을 채워 보여줄 때 |
| `seed_clean` | **막 설치한 회사** 상태(사용자·팀·카드 + `DEFAULT GATE` 1개, 정산·규정문서·과목별 룰 0건). 규정 업로드 → 룰 생성 흐름을 처음부터 시연할 때 |

로그인 계정은 동일(kim/lead/acc/acclead/exec, pass1234). `seed_clean`은 기존 데이터를 지우므로
`--dry-run`으로 먼저 확인한다. 팀 예산은 **한도만** 넣는다(사용액은 집계라 정산 0건이면 자연히 0).
