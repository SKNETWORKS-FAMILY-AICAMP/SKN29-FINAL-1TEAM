# 정산 화면·흐름 불변식

_최종 갱신: 2026-08-22 · 상태: 구현 반영_

> CLAUDE.md 상태 보드에 흩어져 있던 **화면·흐름 규약**을 모았다. 개별 작업 기록이 아니라
> **다시 어기면 같은 결함이 재발하는 규칙들**이다. 새 화면·새 버튼을 만들 때 먼저 읽는다.

## 1. 상태를 추정하지 말고 기록한다

**결과가 없다」는 여러 상황이다.** 결과 유무만 보면 서로 다른 상태가 한 덩어리로 뭉친다.

| 축 | 기록하는 곳 | 뭉쳤을 때 생긴 실제 결함 |
|---|---|---|
| 이상탐지·RAG 검증 | `Settlement.risk_review_state` (NOT_STARTED/RUNNING/DONE/FAILED) + `risk_review_error` | 검토 중인 건에 "룰 판정으로 통과된 건입니다"가 뜨고, ②RAG 카드가 **아직 나오지도 않은 결론**을 이미 난 것처럼 보여줬다 |
| 첨부 판독 | `Attachment.extraction_status` | — (처음부터 상태를 기록한 쪽) |

- 예약과 동시에 `RUNNING`을 **커밋 전에** 기록한다(실행은 커밋 후라 그 사이 화면이 목록을 읽는다).
- 기존 결과 보유 건은 마이그레이션에서 `DONE`으로 백필한다(안 하면 과거 건이 「미실시」로 표시된다).
- **진행 중일 때만 폴링**한다. 끝났는데 계속 두드리면 서버만 친다.
- 경과 시간으로 추정하지 않는다.

## 2. 빈 자리를 값으로 채우지 않는다

- 점수 없음 = `-`, 검토 중 = `…`. **`0.00`을 쓰지 않는다** — 그게 「이상 없음」으로 읽힌다.
- 판정 전을 「정상」으로 접지 않는다. "아직 판정이 돌지 않았다"고 명시한다(검사 안 한 것 ≠ 통과).
- 빈 상태에서도 **레이아웃은 한 벌**이다. 건이 없을 때만 다른 골격을 그리면, 건이 생기는
  순간 화면이 펴지면서 눌러야 할 자리가 바뀐다. 자리표시자로 같은 골격을 채우고 버튼은 비활성.
- 빈 상태 문구는 한 곳에서 만들어 목록·상세·액션이 같은 말을 하게 한다. **「필터 결과 없음」을
  별도로 구분**한다(목록엔 건이 있는데 필터로 비었을 때 아무 말도 없으면 고장으로 읽힌다).

## 3. 이상 건 = 보완요청(RETURN) · 반려(REJECT) **둘뿐**

`REVIEW`는 룰이 판단하지 못해 회계에 넘긴 것이라 **팀이 붙들 일이 아니다.** 정상 건과 함께
올려보내고 사유는 회계 검토 화면에서 본다.

- 표시·필터·카운트·제출 차단이 **전부 `needsAttention` 하나**를 본다. 축을 둘로 나눠 봤다가
  (`needsAttention` 표시용 / `blocksTeamSubmit` 차단용) 화면 문구까지 갈라져 되돌렸다.
- **`judgementFlags`는 이상 건 여부와 분리**한다(`PASS`가 아니면 사유를 돌려준다). 사유 자체를
  없는 것으로 만들면 검토 화면·상세 패널이 근거를 잃는다. 팀 행의 **사유 칩만** 이상 건으로 제한.

## 4. 결정 버튼

- **세 화면(팀 목록 행 · 상세 모달 · 회계 검토)이 같은 세트**를 쓴다. 팀 취합 = `[제출][보완요청][반려]`.
- 사유 모달은 **하나**(`DecisionReasonModal`). 제출은 사유 없이, 보완·반려는 모달을 거친다.
- 팀 뷰에서 회계 결정 세트(승인·확정)를 **절대 띄우지 않는다**(`canReview && !isTeamView`).
- **실패를 삼키지 않는다.** 403이 나도 아무 일이 안 일어나면 버튼이 죽은 것처럼 보인다 —
  서버 사유를 그대로 표시한다.
- **일괄 승인은 없다.** 승인은 되돌리기 어려운 방향이라 화면을 열어 근거를 보고 건별로 내린다.
  보완요청·반려는 사람에게 돌아가 다시 검토될 여지가 남아 일괄을 유지한다.

## 5. 사유를 받는 기준 = 기계 판단과 다를 때

- 승인도 사유를 받는다 — 단, **`AI 권고(우선)·룰 판정`과 다를 때만**. 권고대로 승인하는 건
  설명할 게 없다.
- **다름 판정은 서버가 한다**(`decision_reasons.divergence` → `decision_cases.expected_decision`).
  사유를 받는 기준과 사례를 남기는 기준이 갈리면 안 된다.
- 모달 상단에 **무엇과 다른 판단인지** 먼저 띄운다(왜 받는지 모르면 형식적으로 채워진다).
  하단에 **처리자와 함께 기록된다**는 사실을 명시한다 — 이 글은 결정 사례로 인용된다.
- 승인대기(`PENDING_CONFIRM`)도 `RETURNED`/`REJECT`로 되돌릴 수 있다. 되돌리면 이력에
  `[룰 통과 → 회계 재분류]`(`services.RULE_OVERRIDE_MARK`)가 붙는다 — 구분해 남기지 않으면
  **룰 정밀도 집계가 사람 판단을 룰의 성과로 착각**한다. `IN_REVIEW`에서의 결정은 원래 맡겨진
  판단이라 표시하지 않는다.
- 선택지는 **서버가 정본**(`domain/settlements/decision_reasons.py`). 화면 칩과 LLM enum이 같은
  목록을 봐야 한다. LLM이 목록 밖 사유를 내면 core가 버리고 폴백 매핑으로 정규화(본문은 살린다).

## 6. 사전을 프론트가 복사하지 않는다

플래그 라벨을 프론트가 복사해 갖고 있다가 **백엔드 27개 vs 프론트 9개**로 갈렸다. 지금은
`flags.label_map()`/`describe()`가 한글 표기(`severityLabel`·`ownerLabel`·`categoryLabel`)와
`description`·`isSystem`까지 실어 보낸다. 비용분류 어휘도 같은 이유로 서버가 내려준다
([[category-vocabulary]]).

## 7. 저장하는 건 사람의 결정뿐 — 나머지는 파생

| 화면 | 저장 | 파생 |
|---|---|---|
| 예산(S-08) | 한도만 | 사용액 = 팀·월·`REJECT` 제외 `Settlement` 집계 |
| 카드(S-09) | 배정·정지 사유 | 사용액 = 그 달 `Transaction` 집계 / 「회수·중지 필요」 = 퇴사(`owner.is_active=False`)·반복 이상사용(최근 30일 동일 가맹점 10회↑) |
| 규정 조항(S-05) | 사람의 `SKIP` + 사유 | `LINKED`·`NEEDS_REVIEW` |

컬럼으로 굳히면 원인이 사라진 뒤에도 표시가 남아 **조용히 어긋난다**(퇴사 처리 뒤에도 「회수 필요」).

**예산 불변식 2개**: ① 팀 총한도(`category=''`) = 과목 한도의 합 ② 과목 사용 합 = 총 사용액.
모든 과목에 행을 만든다(하나라도 빠지면 그 과목 지출이 총액에는 잡히는데 항목 카드엔 안 보인다).

## 8. 화면 데이터 스코프

「이번 달」 경계는 `web/src/lib/period.ts` **한 곳**에서만 정의한다(하드코딩 월 상수 금지).

| 화면 | 범위 |
|---|---|
| S-01 내 지출 | 오늘이 속한 달 · 내 것 ∪ 같은 팀의 `claimPending` |
| S-02 팀 통계·예산 | 팀 · 이번 달 · `REJECT` 제외 **전 상태** |
| S-02 취합 목록 | 팀 · 이번 달 · `TEAM_*` 만 |
| S-03 이전 처리 | 이번 달 회계 결정 완료 건(`REVIEW_DECIDED_STATUSES`) |

## 9. 대상은 id로 고른다

모달이 **이름 문자열**로 대상을 고르면 동명이인일 때 엉뚱한 사람에게 붙는다. 카드도 마찬가지 —
화면이 카드 **구분**만 보내고 서버가 `filter(card_type=...).first()`로 붙이던 시절엔 **남의
개인카드가 내 지출에 붙을 수 있었다**(카드 귀속은 판정 사실이라 그대로 오판이 된다).

`_resolve_card()`가 `cardId`를 받고 **본인 범위를 서버에서도 확인**한다 — 목록만 좁히고 저장을
안 막으면 요청을 손댄 값이 들어간다.

## 10. 증빙·첨부

- **영수증은 등록 필수**다. 증빙 없이 등록되면 판정이 곧바로 잡고 담당자는 되돌려보낼 뿐이라,
  그 왕복을 등록 단계에서 없앤다.
- 같은 파일을 **두 자리**에 건다: `Receipt`(거래-영수증 매칭 = 판정이 보는 사실) +
  `Attachment(RECEIPT)`(판독 대상).
- **업로드가 곧 판독 트리거**다. 올린 뒤 따로 「분석」 버튼을 두면 아무도 안 누른다.
- 순서는 **파일 → 종류 → 확인**이다. 종류를 먼저 고르게 하면 문서를 안 보고 기본값(영수증)으로
  올리기 쉽고, 종류가 틀리면 `vision/document.py`의 `TARGETS`가 **엉뚱한 항목을 뽑으라는 지시**를
  열어 없는 사실이 만들어진다(회의록에서 출장 지역등급). 확인 전에 **무엇이 판독될지** 보여준다.
- 추출 결과는 **dot-path 그대로** 표시한다. 요약하면 판정이 무엇을 읽었는지 대조할 수 없다.
- 첨부 판독 완료(성공·실패 모두)는 상위에 알린다 — `DONE`만 기다리면 실패 시 화면이 영영
  「판독 중」으로 남는다.

## 11. 화면이 값을 지어내지 않는다

- ERP 전표 번호를 화면이 만들거나 목록에서 숫자를 주워 쓰지 않는다 →
  `GET /api/erp/vouchers/by-settlement/{id}`. 없으면 **404를 그대로 알린다**(빈 껍데기를 그리면
  "있는데 비었다"로 읽힌다). 못 찾을 때 `myExpenses[0]`을 보여주던 폴백은 제거했다.
- 진행률을 꾸며내지 않는다. 실제 호출을 기다리되 너무 빨리 끝나면 최소 표시 시간만 채운다.
- AI 코멘트는 **서버가 실제로 읽어낸 사실 개수**만 말한다(예전엔 업로드하는 순간
  "인식했습니다"를 찍어 놓고 아무것도 읽지 않았다).

## 11a. 실사용자 — 「등록」과 「수집」은 정반대다

같은 필드(`Settlement.actual_user` / `actual_user_recorded`)인데 **채우는 규칙이 경로마다 반대**다.
헷갈리면 판정 사실을 지어내거나(한쪽) 정상 건을 검토로 보낸다(다른 쪽).

| 경로 | 실사용자 | 왜 |
|---|---|---|
| **화면 등록**(S-01 `create`) | **등록자로 채운다** | 로그인한 본인이 자기 지출을 올리는 **행위 자체가 「내가 썼다」는 기록**이다. 카드 구분과 무관하다 — 팀·공용카드를 골랐어도 그걸 고른 사람이 실사용자다 |
| **내역 불러오기**(`erp_import`) | 개인배정 카드만 채우고 **팀·공용은 비운다** | 카드사 원장에서 긁어와 **주인을 모른다**. `claim()`(「내가 사용했어요」)으로 사람이 해소한다 |

2026-08-24까지 `create`가 이 필드를 **아예 안 넣고 있었다.** 그래서 본인이 팀·공용카드로 올린
건이 전부 `None`(모름)으로 남아 기본 게이트의 `ACTUAL_USER_REQUIRED`에 걸리고 자동 통과에서
빠졌다. 기존 데이터는 `settlements/0014`가 백필한다(**`submitted_by`가 있는 건만** — 없는 건은
수집한 미귀속 건이라 손대면 사실을 지어내는 것이 된다).

**조립기의 보정은 두 필드에 같이 적용한다.** 개인카드는 남의 것을 붙일 수 없으므로
(`_resolve_card`가 서버에서 본인 범위를 확인한다) 소유자가 곧 지출자인데, 예전엔
`card.actual_user_recorded`만 `True`로 보정받고 `card.actual_user_is_spender`는 `None`으로
남아 **같은 건의 두 사실이 서로 다른 말을 했다.**

## 12. AI 제안과 사람 확정은 다른 컬럼

`ai_category`(AI가 뭐라 했나) / `category`(사람이 확정) 2컬럼을 유지한다 — 제안↔확정을 대조해야
AI 정확도를 재고 post-MVP 지도학습 피드백을 만들 수 있다.

- **사람이 저장하는 순간 `ai_suggested=False`**로 딱지를 뗀다. 남겨두면 `category.confidence`가
  계속 0.5로 내려가 확인된 건이 저신뢰로 다시 걸린다.
- 「내역 불러오기」는 의도적으로 `category=""`, `ai_category=<제안>`으로 만든다 — 제안이 곧바로
  판정 입력이 되면 사람 확인 단계가 사라진다.
- 상태 전이(올림·제출) **전에** 화면 값을 먼저 저장한다(`persistEdits`). 조회 전용(남의 건)이면
  건너뛴다 — 팀장이 팀원 건을 제출할 때 남의 입력을 덮어쓰면 안 된다.
- 가드: 회계 검토 시작 후 수정 불가 / 남의 건 403 / 빈 분류로 확정값을 지우지 않음 /
  **날짜만 고쳐도 결제 시각은 유지**(정오로 밀리면 심야 판정이 조용히 뒤집힌다).
