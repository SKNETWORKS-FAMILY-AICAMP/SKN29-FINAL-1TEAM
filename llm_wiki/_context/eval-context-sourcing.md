# EvalContext 데이터 출처 실현 가능성 점검

> **파생 컨텍스트.** 판정에 필요한 사실(EvalContext)을 **어디서 구해올 수 있는가**를 필드별로
> 등급화한 문서다. 규정 임계값(`policy.*`) 쪽 설계는 `_context/policy-domain.md`,
> 필드 정의 자체는 `docs/RULE_명세서.md` §2가 SoT다.
>
> 최종 갱신: 2026-08-11 · 근거: 실측(§1·§8·§12) + 요구사항 FR-DA-* + Draft Agent API 계약
>
> ⚠️ **§0~§11(구 버전)은 다이어트 이전(스키마 v2, 101 필드) 조사 기록 전문을 2026-08-25에
> 아래 배경 요약으로 압축했다.** 원문 삭제 사유: 결론(A/B/C/D 등급 분류 → 101→46 다이어트)이
> §12에 실행 기록으로 이미 남아 있어 조사 과정 전체를 들고 있을 필요가 없어졌다.
> 현행 구조와 남은 과제는 **§12·§13**에 있다.

## 배경 요약 (다이어트 이전 조사, 원문 삭제됨)

미해소 가드를 `policy.*`에서 전 구간으로 확장하자(2026-08-11) 판정 행 120건 중 **112건(93%)**
이 미해소로 `REVIEW` 강등되는 규모가 드러났다. `policy.*` 13종은 전부 해소되는데도 막힌 건
임계값과 비교할 **사실**(참석 인원·사전승인 여부·카드 구분 등)이 SoR에 없었기 때문 — 계약은
`None`="거짓"이 아니라 "모름"이고, 모르면 판정을 신뢰할 수 없으니 `REVIEW`로 강등한다는 것.

막힌 필드를 4등급으로 나눴다: **A**(데이터는 있는데 조립기가 안 읽음, 15개) · **B**(설계상
커버·컬럼/입력칸만 없음, 12개) · **C**(도메인 모델 신설 필요, 13개) · **D**(MVP에서 빼는 게
현실적, 38개). A+B(합쳐서 컬럼 6개 + 입력칸 6개)만 채워도 강등이 93%→약 8%로 줄 것으로
추정됐다.

부수적으로 확인한 것 둘:
1. **진짜 병목은 카테고리 그래프가 아니라 GLOBAL 게이트였다** — 식대 8건을 최소 그래프(근무시간·
   심야·상한·업종 4조건)로만 돌리면 101개 중 42개만 채워도 미해소 0건인데, 같은 컨텍스트가
   GLOBAL을 거치면 미해소 4건이 뜬다. 조건 없는 필수 게이트가 해당 없는 거래에도 무관한 사실을
   요구한 것 — "필드를 채우는 것보다 안 물어보는 게 싸다"는 원칙의 근거.
2. **B등급 상당수는 "입력칸"이 아니라 "문서 추출" 대상이었다** — 사전승인·참석자 명단·출장계획서
   류는 사람이 타이핑할 게 아니라 이미 있는 `chunk_pdf` 파이프라인·OpenAI 비전으로 첨부에서
   뽑아야 하는 값. "관측했고 부재를 확인했으면 명시값(0/False), 관측 자체를 안 했으면 `None`"
   계약을 추출에도 그대로 적용하기로 함.

스키마 자체를 축소 재설계할지도 검토했으나 기각했다 — `empty_eval_context()`의 미사용 `None`
필드는 런타임 비용이 0이고, 비용은 그래프가 실제로 참조하는 순간에만 발생한다. 필드 100개를
20개로 줄여도 "어떤 룰을 유지할지" 결정은 동일하게 필요해 스키마 축소는 순수 추가비용. 대신
**그래프(룰 조건)를 축소**하는 쪽을 택했고, 이 판단이 §12의 "101→46 다이어트" 실행으로 이어졌다.

## 12. 스키마 v3 다이어트 실행 기록 (2026-08-11)

§10에서 "스키마가 아니라 그래프를 축소하자"고 결론냈지만, 실제로 남은 필드를 훑어보니
**스키마 자체에도 애초에 있으면 안 되는 것**이 섞여 있었다. 판정 결과를 입력으로 받는 필드다.

### 삭제 기준 — **EvalContext는 '단어', 그래프는 '문장'**

필드가 남으려면 셋 다 만족해야 한다:
① 관찰(observation)이지 판정(verdict)이 아니다 ② 다른 필드로부터 DSL 연산자로 조합할 수 없다
③ 현실적인 출처가 있다.

| 사유 | 삭제한 것 | 대체 |
|---|---|---|
| **(a) 판정 필드** — 결론을 입력받고 있었다 | `derived.personal_use_suspected`, `derived.category_specific_*`, `evidence.purpose_is_generic` | **그래프에서 조합한다** |
| **(b) 조합 가능** — 중복 | `evidence.participant_list_missing` 등 `*_missing` 계열 7종 | 대상 필드의 값으로 판정 (`participant_count == 0`) |
| **(c) 원천 없고 부차적** | `tx.service_charge_ratio`, `tx.is_holiday`, `merchant.merchant_grade`, `tx.day_of_week`, `user.dept` | — (제거) |
| **(d) 과세분화** | 출장 상세 9종·참석자 상세 5종·승인 상세 5종·세부유형 3종·집계 2종 | 원천(모델) 확보 후 되살린다 |

**대표 사례** — `derived.personal_use_suspected`(GLOBAL R-006):

```jsonc
// before — 「사적사용 의심」이라는 결론을 그대로 입력받았다
{"and": [{"==": [{"var": "derived.is_late_night"}, true]},
         {"==": [{"var": "derived.personal_use_suspected"}, true]}]}

// after — 확인 가능한 사실 3개의 조합으로 바꿨다
{"and": [{"==": [{"var": "derived.is_late_night"}, true]},
         {"or": [{"==": [{"var": "derived.is_weekend"}, true]},
                 {"==": [{"var": "merchant.merchant_info_resolved"}, false]}]}]}
```

조합 규칙이 룰 화면에 그대로 보이므로 **회계 담당자가 근거를 따질 수 있다.** 판정 필드로 두면
"AI가 의심한다더라"가 되어 감사할 수 없다.

### 결과 — 101 → 46 필드

| 섹션 | v2 → v3 | 섹션 | v2 → v3 |
|---|---|---|---|
| tx | 7 → **4** | trip | 12 → **3** |
| card | 2 → 2 | dining | 4 → **2** |
| user | 4 → **3** | history | 5 → **3** |
| merchant | 4 → **3** | policy | 13 → **8** |
| category | 7 → **3** | derived | 7 → **3** |
| evidence | 11 → **3** | tables | 5 → **동적** |
| approval | 6 → **1** | meta | 5 → 5 |
| participants | 9 → **3** | | |

- `tables`는 **고정 목록을 없앴다** — 감사용 원본이라 DSL이 참조하지 않으므로, 조립기가 실제
  사용한 별표만 동적으로 담는다. 별표가 늘어도 스키마 변경이 없다.
- `policy` 8종: 비교 대상이 함께 남아 있는 것만 유지(`business_class_min_hours`·`night_meal_limit`·
  `approver_daily_limit`·`position_required_level`은 짝이 사라져 제거). `history_window_months`는
  DSL 비교 대상이 아니라 조립기 파라미터라 `ctx`에서 뺐다.
- 새 별표 1종 추가: `forbidden_merchant_table` — 금지업종 **목록**을 DSL `in` 리터럴로 박으면
  규정 개정을 못 따라가므로, `merchant.forbidden` 불린으로 선해소한다(policy와 같은 패턴).

### 다이어트 후 실측 — 강등률은 그대로, **그러나 성격이 달라졌다**

## 12a. 조립 충돌 해소 규칙 (2026-08-11 구현)

같은 경로에 **서로 다른 값이 도착한다.** 회의록은 4명, 참석자명단은 6명, 사용자는 9명.
예전 구현은 나중 값이 조용히 이겼다 — 조용한 손실이다. 지금은 출처 순위와 기록으로 처리한다.

### 출처 순위

| 순위 | 출처 | 예 |
|---:|---|---|
| 3 | **`RANK_SOR`** — 원장 사실·산술 파생 | 카드 전표 금액, 결제 시각, 영수증 매칭 여부, 1인당 환산 |
| 2 | **`RANK_INPUT`** — 화면 입력(사람이 확정) | `Settlement.headcount`·`pre_approved` 등 |
| 1 | **`RANK_EXTRACT`** — 첨부 문서 추출 | `Attachment.extracted` |

### 규칙

1. **높은 순위가 이긴다.** 값이 다르면 진 쪽을 충돌로 기록한다(판정은 이긴 값으로 진행).
2. **같은 순위에서 값이 다르면 어느 쪽도 쓰지 않는다.** `None`으로 남기고 충돌을 기록한다
   → 미해소 가드가 `REVIEW`로 보낸다.
   *두 문서가 4명/6명이라면 "둘 중 아무거나"가 아니라 "사람이 봐야 한다"가 맞다.*
3. **`None`(모름)은 아무것도 덮지 않는다.** 빈 컬럼이 추출값을 지우지 않는다.
4. **상위 순위가 오면 동순위 충돌이 해소된다.** 사용자가 7명이라고 확정하면 문서 4/6 충돌은 풀린다.

### 기록

`ctx["conflicts"]`(감사용 동적 섹션, DSL 미참조)에 남아 `rule_hits` 스냅샷으로 보존된다.

```jsonc
"conflicts": {
  "participants.participant_count": {
    "kept": 9, "kept_from": "input", "resolution": "input_wins",
    "dropped": [{ "value": 4, "from": "attachment:12(MEETING_MINUTES)" }]
  }
}
```

`resolution`: `sor_wins` · `input_wins` · `dropped_as_unknown`

### 함께 고친 결함 — 파생 순서

`tx.per_person_amount`를 정산 컬럼에서 미리 계산하면, 인원이 **첨부에서만** 온 경우 `None`으로
덮어써 추출값을 지웠다. 지금은 **합쳐진 인원으로 병합 이후에** 파생한다(`derive_after_merge`).

> **미해결로 남긴 것**: `Attachment.field_confidence`를 아직 쓰지 않는다. 동순위 충돌을
> 신뢰도로 가릴지(높은 쪽 채택) 지금처럼 보수적으로 버릴지는 §13 #9 참조.

## 12b. 별표 폴백 — 표마다 다르다 (`strict_keys`)

`user.position`이 SoR에 없어 직책별 한도가 와일드카드(`"*"`)로 떨어지는 건 **괜찮다**
(회사 기본 한도가 의미 있다). 하지만 **업종을 모르는데 `merchant.forbidden = False`** 로 떨어지면
금지업종 결제를 조용히 통과시킨다. 같은 폴백이 표에 따라 안전하기도, 위험하기도 하다.

| `PolicyTable.strict_keys` | 축 값을 **모를 때** | 축 값을 **알지만 표에 없을 때** | 쓰는 표 |
|---|---|---|---|
| `False` (기본) | `"*"` 폴백 | `"*"` 폴백 | 한도표 — 기본값이 의미 있다 |
| `True` | **해소 안 함(`None`)** | `"*"` 폴백 | 금지업종표 — 모르면 단정 못 한다 |

"알지만 목록에 없음"은 두 모드 모두 `"*"`로 폴백한다 — **금지 목록에 없는 업종 = 금지 아님**은
관측 결과이므로 단정해도 된다.

- **조립기 코드는 완성돼 있다.** 못 채우는 건 코드 문제가 아니라 **SoR에 원천이 없어서**다.

  **적용 조건을 붙여 안 물어보는 것**이 싸다.
- 많은 값은 입력칸이 아니라 **첨부 문서에서 추출**해야 한다(배경 요약 참조). `chunk_pdf`·비전 판독 인프라는

  관측 안 함 → `None`" 계약을 적용한다.
- **스키마 축소 재설계는 하지 않는다**(§10). 스키마는 어휘 사전이라 커도 무해하고, 실제 비용은
  그래프가 참조하는 순간 발생한다. 축소는 **`MVP_CORE_PATHS` 선언 + ACTIVE 게이트**로 얻는다.
- D 38개는 스키마에 남기되 룰에서 참조를 빼는 게 정직하다 — 안 그러면 영원히 REVIEW로 쌓인다.

## 16. v6 결정 — **파생 불린을 두지 않는다. 상수는 룰에 허용한다** (2026-08-23)

### 16.1 무엇을 정했나

조립기가 `is_late_night`(22~06)·`is_working_hours`(09~18)처럼 **판단 기준을 코드에 박고**
불린으로 접어 주던 것을 그만둔다. 그래프가 `tx.payment_time >= "22:00"`으로 직접 비교한다.

**룰 조건에 상수가 박히는 것을 허용한다**(팀 결정). 그동안 상수를 피하려 조립기·별표로
밀어냈는데, 근거를 다시 보면 그 비용이 이득보다 크다:

- 내규 개정은 **잦지 않다**. 개정 때 고칠 대상이 **조립기 코드(재배포)** 가 아니라 **룰 그래프**인
  편이 낫다 — 룰은 화면에서 고치고 승인 이력이 남는다.
- 룰은 **Rule Agent가 관리한다.** 조항에서 숫자를 읽어 조건으로 옮기는 게 그 일이고,
  값이 조항에 있는데 굳이 별표를 거칠 이유가 없다.
- 조립기에 박힌 상수는 **어디에도 안 보인다** — 룰 콘솔에도, 판정 스냅샷에도 안 뜬다.
  룰 조건에 있으면 최소한 사람이 읽고 고칠 수 있는 자리에 있다.

> 이 결정은 **`policy.*`(별표)를 없애자는 게 아니다.** 한도표처럼 축이 있고 개정이 표
> 단위로 오는 값은 그대로 별표다(§3.1). 바뀐 건 "코드에 박느니 별표로"가 아니라
> **"코드에 박느니 룰에"** 다.

### 16.2 삭제 4건

| 삭제 | 대체 |
|---|---|
| `derived.is_late_night` | `tx.payment_time >= "22:00" or payment_time < "06:00"` |
| `user.is_working_hours` | `not is_weekend and "09:00" <= payment_time < "18:00"` |

`payment_time`은 제로패딩 `HH:MM`이라 **문자열 비교가 곧 시각 순서**다. DSL의
`_same_comparable_type`이 같은 str끼리를 허용하므로 그대로 동작한다(실측 확인).

### 16.3 남기는 예외 셋 — 취향이 아니라 DSL의 구조적 한계

**① null 여부** (`merchant.merchant_info_resolved`)
미해소 가드는 **참조 경로의 `None`을 보고 값 평가 전에** REVIEW로 강등한다

**② 별표 선해소** (`merchant.forbidden`)

## 17. DSL null 의미론 통일 + `is_null` (2026-08-23)

### 17.1 전에는 연산자마다 달랐다

| 연산 | 한쪽이 None일 때 (구) |
|---|---|
| `==` | 둘 다 None이면 **참** (`left is right`) |
| `!=` | 한쪽만 None이면 **참** ⚠️ |
| `>` `>=` `<` `<=` · `in` | 거짓 |
| `not(var)` | **참** (`not bool(None)`) ⚠️ |

예외를 룰 작성자와 LLM이 매번 기억해야 했고, 카탈로그가 경고 두 줄을 실어야 했다.
**틀리는 방향이 「조용한 위반 판정」이었다** — 모름이 참이 되니까.

### 17.2 지금 — 한 문장

> **모름은 어느 방향으로도 참을 만들지 않는다. `is_null`만이 예외다.**

비교 6종·`in`은 피연산자에 None이 있으면 거짓, `not(x)`도 x가 None이면 거짓(모름의 부정도
참이 아니다). 논리 연산자는 그대로(None은 falsy).

### 17.3 실측으로 확인한 두 사례

**고친 것 — T-21 `{"not": {"var": "evidence.has_valid_receipt"}}`**
증빙 여부를 **모르는** 건에 `not(False)` → 참 → `EVIDENCE_MISSING` 플래그로 「적격증빙 누락」
보완요청이 나갔다. 가드가 뒤에서 REVIEW로 덮어 실피해는 없었지만, **검토 화면이 「증빙 없음」을
사유로 보여줬다** — 실제로는 확인을 안 한 것인데. 의도가 「없음」이므로 `== False`로 명시했다.

**깨진 것 — DEFAULT GATE의 `{"!=": [{"var": "category.value"}, None]}`**
`!= null`이 「값이 있는가」의 관용구였고 하필 제품이 유일하게 기본 제공하는 게이트가 썼다.
새 의미론에서 항상 거짓이 되므로 `{"not": {"is_null": ...}}`로 이관했다. **그래서 `is_null`은
선택이 아니라 필수다** — 의미를 통일하면 null 테스트 수단이 문법적으로도 사라진다.

### 17.4 진짜 작업은 연산자가 아니라 **가드 면제**였다

`{"==": [{"var": "x"}, null]}`은 **예전에도 문법적으로 유효**했다(`_validate`가 None 리터럴을
허용한다). 막고 있던 건 연산자 부재가 아니라 미해소 가드다 — 참조 경로가 None이면 조건 평가와
무관하게 최종 판정을 REVIEW로 덮는다. 그래서 `is_null`을 넣는 것만으로는 아무 뜻이 없다.

`dsl.guarded_vars()` 신설 — `is_null`이 감싼 경로를 가드 대상에서 뺀다. **같은 경로가
`is_null` 밖에도 나오면 유지한다**(`is_null(x) or x == "카페"`에서 뒤쪽은 여전히 x를 알아야
한다 — 애매하면 안전한 쪽). `engine.referenced_vars_by_node`가 `extract_vars` 대신 이걸 쓴다.
**ACTIVE 전환 게이트(`validate_graph_vars`)는 그대로 `extract_vars` 전부를 본다** — 면제는
가드에만 적용되고, 경로가 스키마에 있어야 하는 건 변함없다.

### 17.5 Rule Agent에도 연다 — 처음 판단을 뒤집었다

**처음엔 「사람 전용」으로 두려 했다.** 근거는 이랬다: `is_null`이 붙은 경로는 가드가 면제되니,
모델이 「사전승인 안 받음」을 `is_null(approval.pre_approval_obtained)`로 쓰면 — 그 필드는 화면
미입력 시 None이라 흔하다 — **미입력이 곧 위반 판정이 되고 가드가 못 막는다**고.

**그 근거가 틀렸다.** Rule Agent가 만드는 노드는 `REJECT / RETURN / REVIEW`만 낼 수 있다 —
structured output enum과 `_sanitize_nodes` 양쪽이 강제한다(v0 설계: "이 생성 흐름이 만드는
노드는 항상 비-PASS 종단"). 게다가 엔진은 REJECT도 `RETURNED`로 보낸다(최종반려는 사람만).
**즉 세 판정 모두 사람에게 간다** — 가드가 막으려던 「모름을 근거로 조용히 통과」가 애초에
구조적으로 불가능하다. 오용의 최악은 「과하게 사람에게 보냄」이고, 그건 가드가 밀던 방향과 같다.

그래서 툴 스키마 `op` enum에 `is_null`을 넣고, `_build_condition`에 단항 분기를 뒀다(우변을
채워 보내도 무시 — 단항이라 쓸 자리가 없다. `negate:true`면 「값이 있다」).

프롬프트에는 **「없음」과 「모름」의 구분**을 명시했다 — 「받지 않았다」는 `== false`,
「적혀 있지 않다」는 `is_null`. 그리고 **모르는 경우를 따로 처리할 필요가 없다**는 것도
알려준다(다른 비교는 모르면 자동으로 안 걸리고 시스템이 검토로 넘긴다) — `is_null`은
**모름 자체를 사유로 삼고 싶을 때만** 쓰라고.

### 17.6 함께 정리

`in` 우변의 `null` 리터럴을 **문법에서 거부**한다. 허용해도 좌변 None에서 먼저 끊겨 아무것도
안 맞는데, 조용히 안 맞으니 "왜 안 걸리지"를 만든다.

📏 회귀 core **468 통과**(신규 `test_null_semantics.py` 10건 — 면제 범위·엔진 통합·스키마 검증
비면제까지). 마이그레이션 없음.

## 18. 참석 인원 — 신고와 확인을 다른 사실로 가른다 (2026-08-23)

### 18.1 문제 — 같은 경로에서 다투게 두면 출처를 물을 수 없다

화면 입력(`RANK_INPUT`)과 첨부 추출(`RANK_EXTRACT`)이 `participants.participant_count`
하나를 놓고 순위로 겨뤘고, **사람이 적은 값이 늘 이겼다.** 그래서 룰은 "이 인원이 문서로
확인된 것인가"를 **물을 방법이 없었다** — 출처는 `ctx.conflicts`에만, 그것도 **값이 다를
때만** 남고, `conflicts.*`는 스키마에 없어 룰이 참조할 수 없다.

정확도 요구가 다른 두 판정이 같은 사실을 쓰는 게 문제의 핵심이다. 식대 1인당 한도는 본인
신고로 충분하지만, **청탁금지 법정 한도는 신고값으로 나누면 인원을 부풀리는 것만으로
한도를 피할 수 있다.**

### 18.2 조치 — 출처가 곧 필드다

| 필드 | 채우는 곳 |
|---|---|
| `participants.participant_count` | **화면 입력만** (본인 신고) |
| `participants.verified_participant_count` | **첨부 추출만** (회의록·참석자명단) |
| `participants.external_participant_count` / `verified_external_count` | 같은 방식 |
| `tx.per_person_amount` / `tx.verified_per_person_amount` | 각각의 인원으로 파생 |

추출값은 `EXTRACT_PATH_REMAP`이 확인 필드로 접는다 — 판독기(`vision/document.py`)는 새 경로로
뽑지만 **이미 저장된 `Attachment.extracted`는 옛 경로**를 들고 있어서다. 재판독 없이 살아나야
지금까지 읽어둔 명단이 사라지지 않는다.

📏 실측(총액 120,000원):

| 상황 | 신고 인원 | 확인 인원 | 신고 1인당 | 확인 1인당 |
|---|---|---|---|---|
| 추출만 (회의록 4명) | `None` | `4` | `None` | `30,000` |
| 화면 입력만 (6명) | `6` | `None` | `20,000` | `None` |
| 둘 다 · 값 다름 | `6` | `4` | `20,000` | `30,000` |
| 문서끼리 다름 (4 vs 6) | `None` | `None` | `None` | `None` |
| 저신뢰 추출 (0.4) | `None` | `None` | `None` | `None` |

### 18.3 함께 바뀐 의미 둘

**사람이 적어도 문서 충돌은 해소되지 않는다.** 예전엔 입력이 상위 순위라 문서끼리의 불일치를
덮고 확인값이 되살아났다. **그건 「확인됨」의 뜻을 흐린다** — 사람이 적었다고 명단이 확인된
것은 아니다. 이제 확인값은 여전히 모름이고, 그걸 요구하는 룰은 검토로 간다.

**청탁금지 룰(E-003)이 확인 기준으로 옮겼다.** 명단이 없으면 `verified_per_person_amount`가
null이라 판정이 검토로 넘어간다 — 조건이 「걸린」 것이 아니라 **「판단할 수 없어 사람에게
보낸」** 것이다(그래프는 끝까지 가고 최종 판정만 가드가 덮는다. 회귀로 고정).

### 18.4 어느 쪽을 쓸지는 룰이 정한다

시스템이 강제하지 않는다 — 회사마다 다르다. 카탈로그 `desc`에 지침을 실어 Rule Agent가
고르게 한다: 신고값은 "승인이 느슨한 지출(식대·복리후생)에만", 확인값은 "정확한 인원이
필요한 판정". S-01 입력칸에도 같은 안내를 적었다 — 안 적으면 **인원을 적었으니 됐다고 믿고
명단을 안 올린다.**

### 18.5 남은 것

- `participants.has_kickback_law_target`은 아직 병합형이다(입력·추출이 같은 불린을 다툰다).
  같은 구분이 필요해지면 같은 방식으로 가른다.
- **`ctx.conflicts`가 화면에 안 보인다.** 인원은 이제 다투지 않지만 금액(영수증 vs 카드
  전표) 등은 그대로 충돌한다. 스냅샷에는 있는데 프론트가 안 읽는다(grep 0건) — 검토자가
  「영수증 45.2만 ↔ 전표 45만」을 못 본다.
