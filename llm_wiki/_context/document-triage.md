# 문서 분류(triage) + 별표 승인 — 구현 캐논

> 업로드된 규정 문서를 **한 번 읽고 갈라주는** 단계. 조항의 성격·룰 생성 우선순위를
> 매기고, 별표를 판정 임계값 후보로 뽑는다.
> 코드: `apps/ai/app/rag/triage.py` · `apps/core/domain/policies/table_proposals.py`
> 화면: 규정 문서 관리(S-05) — `TableProposalPanel.tsx` · `ClauseAccordion.tsx`
> 최종 갱신: 2026-08-22 · 구현 완료

---

## 1. 무엇을 푸는 문제인가

적재까지는 됐지만 그 다음이 비어 있었다.

| 증상 | 구현 전 상태 |
|---|---|
| 조항이 평평하다 | 「목적」·「정의」·「시행일」이 한도·금지 조항과 **같은 무게**로 늘어섰다. 담당자가 전부 열어봐야 무엇이 규칙이 될지 안다 |
| 별표가 화면에 없다 | 별표는 조에 속하지 않아 `build_clauses`가 조항 행으로 만들지 않는다. **임계값의 원천인데 보이지도 않았다**(경고 한 줄로만 남았다) |
| 임계값을 넣을 경로가 없다 | `PolicyTable`에 행을 만드는 코드가 `tiger_tables.upsert_all()` 하나뿐이었다. 고객이 규정을 올리면 **룰은 생기는데 그 룰이 비교할 숫자가 없다** |
| 자동 생성이 문서를 안 본다 | `rule_trigger`가 scope 기본 질의(`DEFAULT_QUERIES`)로만 돌아, 방금 올린 문서에 무엇이 있는지와 무관했다 |

## 2. 흐름

```
파싱 → 청킹 → 임베딩 → Chroma upsert
   └─► triage.run()
         ├ classify_clauses()  조항 → kind(RULE/INFO/ANNEX) + priority(AUTO/P1/P2/P3/SKIP)
         └ extract_tables()    별표 청크 → PolicyTable 후보
   └─► rule_trigger.trigger(auto_clauses=…)   AUTO 조항으로 질의를 만들어 자동 생성
   └─► core 콜백: PolicyClause.triage_* / PolicyTableProposal(PENDING)
                                             └─► 화면에서 승인 → PolicyTable
```

## 3. 결정 기록

**D-1. 분류는 제안이지 차단이 아니다.** `SKIP`으로 분류된 조항에서도 룰을 만들 수 있다
(`clause_generate_rule`, 화면의 「규칙 생성하기」는 모든 상태에서 뜬다). 모델이 못 알아본
규칙이 반드시 있고, 통로가 없으면 분류가 틀린 순간 그 조항은 **영영** 룰이 되지 못한다.
AI 분류(`triage_*`)와 사람의 결정(`decision`)을 **다른 컬럼**에 둔 것도 같은 이유 — 한 칸에
섞으면 "AI가 제외로 봤다"와 "사람이 제외로 정했다"를 구분할 수 없고, 재분류가 사람의 판단을
덮어쓴다.

**D-2. 분류는 매 적재마다 새로 온다.** 사람의 결정과 달리 이월하지 **않는다**. 문서가
바뀌었는데 옛 분류를 물려주면 그게 곧 틀린 제안이 된다. 반대로 `decision`·별표 제안의
승인/반려는 이월한다(같은 검토를 반복하지 않게).

**D-3. 별표 후보는 `PolicyTable`이 아니라 별도 모델이다.** `load_tables()`가 필터 없이
전부 읽어 `ctx.policy.*`로 선해소하므로, 한 테이블에 미승인 행을 섞으면 status 필터를 잊은
한 곳 때문에 검증 안 된 임계값이 판정에 들어간다. 모델을 갈라 두면 그 실수가 **불가능**하다.

**D-4. 승인이 강제하는 것은 축뿐이다.** 스키마에 없는 축은 거부(경고가 아니라). 경고는
읽고 넘길 수 있고, 넘기면 `strict_keys=False` 표가 조용히 `"*"`로 폴백한다 — 값도 나오고
에러도 플래그도 없는 가장 잡기 어려운 결함이다(`category.scope`가 실제로 그랬다).
값이 원문과 맞는지는 시스템이 알 수 없으므로 **표 원문을 나란히** 띄우고 사람이 대조한다.

**D-5. 축은 세 겹으로 거른다.** ① 프롬프트에 고를 수 있는 축을 싣고 ② ai가 목록 밖 축을
버리며(버린 사실은 메모에 남긴다) ③ core가 승인에서 다시 막는다. 축 목록의 출처는
**`domain/context` 카탈로그 하나**다 — ai가 사본을 들면 보여준 축이 승인에서 거부되는데
사람은 왜 막혔는지 알 수 없다.

**D-6. 회사 규정(`policy_docs`)만 분류한다.** 법령(`tax_refs`)은 조항이 수백 개인데 우리
회사의 규칙이 아니라 참조 근거이고, 조직도(`org_docs`)는 판정이 검색조차 하지 않는다.
건너뛴 사실은 결과 경고에 남긴다(조용한 누락 금지).

**D-7. `AUTO`가 하나도 없으면 자동 생성을 하지 않는다**(`SKIPPED_NO_AUTO_CLAUSE`).
조건이 명확한 조항이 없다는 뜻이고, 그 상태에서 만든 초안은 사람이 어차피 전부 고친다.
분류가 화면 장식이 아니라 **실제로 무엇을 만들지 정하게** 하는 자리다.

**D-8. 실패는 적재를 되돌리지 않는다.** 배치 하나가 깨지면 그 배치만 잃고(60개 문서에서
1건 실패로 59건이 사라지면 안 된다), 분류가 통째로 터져도 결과를 돌려준다. 문서는 이미
검색 가능하고, 분류가 없으면 화면이 예전처럼 평평하게 보일 뿐이다.

## 4. 구현 중 실측으로 잡은 결함 2건

1. **`normalize_scope("")`가 `"GLOBAL"`을 돌려준다.** 정규화한 뒤에 비었는지 보면, 비용분류를
   안 고른 요청이 **조용히 전역 게이트 룰**을 만든다. 게이트는 모든 정산이 먼저 통과하는
   자리라 가장 위험한 기본값이다 → 원문으로 먼저 판단하게 고쳤다(회귀로 고정).
2. **`PolicyDocViewSet.http_method_names`가 PATCH를 의도적으로 뺐다**(문서는 제자리 수정
   대상이 아니다). 제안 수정을 PATCH로 두면 405다. 새 엔드포인트 하나를 위해 그 제약을
   넓히면 문서 자체에도 PATCH가 열리므로 **좁은 쪽에 맞춰** POST로 갔다.

## 6. 남은 것

- **실 문서로 end-to-end 미검증.** LLM 호출이 필요해 도커·API 키가 있어야 한다. 분류
  품질(우선순위가 실제로 유용한가)·별표 추출 정확도는 실측 후 프롬프트 조정이 필요하다.
- **비용**: 조항 배치(12개씩) + 별표 1개당 1회. 조항 60개·별표 5개 문서면 약 10회.
  법령을 제외한 근거가 여기 있다(207조항 = 18회 + 값어치 없음).
- 표가 `TABLE_TEXT_LIMIT`(6,000자)를 넘으면 잘린다 — 그 표는 사람이 직접 만들어야 하는데,
  **지금은 잘렸다는 사실이 화면에 안 뜬다**.
- 승인된 별표를 참조하는 룰을 다시 만들지 않는다 — 임계값이 생겨도 기존 DRAFT는 그대로다.
