# 결정 사례 데이터 (case_history) — 구현 캐논

> 회계 담당자가 **AI·룰과 다르게 판단했을 때** 그 판단과 사유를 사례로 남겨,
> 이후 Risk Review 2차 검증이 근거로 끌어 쓰게 하는 파이프라인.
> 코드: `apps/core/domain/risk/{models,decision_cases,case_index}.py` + `apps/ai/app/rag/case_store.py`
> 최종 갱신: 2026-08-21 · 기틀 구현 완료

---

## 1. 무엇을 푸는 문제인가

`case_history` 컬렉션은 Risk Review 2차 검증의 **유사 과거 사례** 근거다. 그런데 실 결정이력을
적재하는 경로가 없어서, 지금까지 내용물은 시연용 골든 시드 10건
(`apps/ai/app/rag/golden_cases.py`)뿐이었다 — 그 파일 docstring도 "실제 결정 이력 적재
파이프라인이 생기면 이 파일은 폐기한다"고 적어 두고 있었다.

이 문서가 그 파이프라인이다.

---

## 2. 무엇을 사례로 남기는가

### 「다르게 판단한 것」만 남긴다

AI 권고대로 처리한 건은 새로 배울 게 없다. 사례의 가치는 **"AI는 이렇게 봤는데 사람은
다르게 판단했다, 그 이유는 이것이다"** 에 있다.

전부 남기면 검색이 **다수결에 묻힌다**: 대부분은 권고와 일치하므로 유사도 상위가 전부
"권고대로 처리함"으로 채워지고, 정작 봐야 할 예외가 밀려난다.

### 무엇과 비교하나

| 우선순위 | 비교 대상 | 왜 |
|---|---|---|
| ① | `RiskReview.ai_recommendation` | 검토를 거친 건이라면 **사람이 실제로 마주한 제안**이 이것이다 |
| ② | `Settlement.rule_decision` (`PASS→APPROVE` 매핑) | AI가 안 돈 건(룰 통과 후 승인대기 직행)을 사람이 되돌린 것도 「다르게 판단한」 사례다 |

룰의 `REVIEW`는 **판단을 미룬 것**이라 비교 대상이 아니다 — 무엇과도 "다르다"고 말할 수 없다.

### 사유가 없으면 남기지 않는다

"왜 다르게 봤는지"가 사례의 핵심이다. 사유 없는 사례는 검색돼도 쓸모가 없다.
(승인은 사유 없이 결정할 수 있는데, 그때는 사례를 만들지 않는다.)

## 3. 데이터 틀

### 저장층 — `risk.DecisionCase`

| 필드 | 뜻 |
|---|---|
| `case_id` | Chroma 문서 id. **적재 멱등성의 키**(재적재해도 중복 안 됨) |
| `outcome` | 사람의 최종 결정 (`APPROVE`/`RETURN`/`REJECT`) |
| `diverged_from` | 무엇과 달랐나 — `AI` / `RULE` |
| `expected` | 기계가 내놨던 결론 |
| `ai_recommendation` · `rule_decision` · `rule_flags` | 그때의 기계 판단 전부 |
| **`reason`** | **회계 담당자가 쓴 사유** — 사례의 핵심 |
| **`text`** | **임베딩 대상 본문(스냅샷)** |
| `facts` | 결정 시점 사실 요약(금액·가맹점·업종·목적…). 감사용, 임베딩 안 함 |
| `citation` | 표시용 출처(`과거 결정사례 #12`) |
| `indexed_at` · `index_error` | Chroma 적재 상태. 비어 있으면 아직 안 올라간 것 |

### 왜 스냅샷인가

`text`·`facts`는 **결정 시점의 사실을 얼려 둔 것**이다. 정산은 이후에도 고쳐진다
(보완요청 → 수정 → 재제출). 검색이 지금 값을 따라가면 "그때 왜 그렇게 판단했는가"를
설명할 수 없다 — `rule_hits.eval_context`가 판정 스냅샷을 남기는 것과 같은 이유다.
회귀로 고정: 정산의 가맹점명을 바꿔도 사례 본문은 그대로.

### 본문 형식 — 상황 → 판단 → 이유

골든 데이터와 같은 톤으로 맞춘다(같은 컬렉션에서 나란히 검색된다).

```
접대 380,000원, 강남 유흥주점(주점/유흥). 판정 사유: 금지 업종.
AI 권고는 보완요청이었으나 회계 담당자는 반려로 판단.
사유: 유흥업소 결제는 규정상 사후 보완이 불가하여 최종 반려합니다.
```

**자체로 완결돼야 한다** — 검색이 매칭하는 건 이 문장뿐이다. 조사는 받침에 맞춘다
(`보완요청이었으나`/`반려로`); 이 문장은 임베딩될 뿐 아니라 검토 화면 인용문으로도 노출된다.

## 4. 흐름

```
회계 담당자 결정 (services.review)
   │  ├─ 기계 결론과 같다 → 사례 없음
   │  └─ 다르다 + 사유 있음
   ▼
DecisionCase 생성 (전이 **전에** 판단 — 전이 후엔 맥락이 흐려진다)
   ▼  [커밋 후]
case_index.schedule → POST ai /embeddings/cases
   ▼
case_store.upsert_cases → Chroma `case_history`
   ▼
다음 검토에서 search_cases가 근거로 끌어옴
```

### 커밋 후에 적재하는 이유

임베딩은 OpenAI 왕복이라 수 초가 걸린다. 결정 트랜잭션 안에서 부르면 DB 커넥션을 붙들고,
적재가 실패하면 **결정까지 롤백된다** — 회계 담당자가 내린 판단이 AI 인프라 사정으로
사라지는 건 있을 수 없다(`evidence_extract`·`risk_review`와 같은 판단).

### 미적재는 사고가 아니라 상태다

`indexed_at`이 비면 아직 안 올라간 것이다. ai가 며칠 꺼져 있었어도 사례는 DB에 남는다.

```bash
docker compose exec core python manage.py reindex_cases --list   # 밀린 목록
docker compose exec core python manage.py reindex_cases          # 일괄 적재
```

## 5-a. 화면

### 사유 입력 — 승인도 받는다 (검토 화면)

**AI·룰과 다르게 판단할 때만** 사유를 받는다. 권고대로 승인하는 건 설명할 게 없으므로
그대로 처리한다(`divergesFromMachine`).

  · 승인 사유 선택지는 "왜 기계 판단을 따르지 않았는가"에 대한 답으로 구성된다 —
    `업무관련성 확인됨` · `증빙 별도 확인` · `규정상 예외 인정` · `AI 과탐지(오탐)` ·
    `경미하여 통과` · `기타`.
  · 모달 상단에 **무엇과 다른 판단인지** 먼저 띄운다(`AI 권고는 보완요청이었습니다 —
    다르게 판단하시는 이유를 남겨주세요`). 사유를 왜 받는지 모르면 형식적으로 채워진다.
  · 하단에 **처리자와 기록된다는 사실**을 명시한다. 기록되는 줄 모르고 쓴 문장과 알고 쓴
    문장은 다르다 — 이 글은 사례로 인용된다.
  · 승인 사유의 LLM 초안은 **감사 기록** 톤으로 쓴다(지출자에게 가는 안내가 아니다).
    근거가 부족하면 `detail`을 비운다 — 담당자만 아는 사실을 지어내면 안 된다.

**상태 변경 이력이 실데이터가 됐다.** 검토 화면의 타임라인은 하드코딩된 세 줄이었다
(`DRAFT → SUBMITTED` …). `events`를 목록 시리얼라이저로 올려(이미 prefetch돼 추가 쿼리 0)
**누가·언제·무슨 사유로** 처리했는지를 실제 이력으로 보여준다.

### 사례 열람 — 문서 관리의 「결정 사례」 (월별)

`GET /api/policy-docs/cases/?month=YYYY-MM` → 월 목록 + 그 달의 사례. 인가는 `rule_view`
(사례는 판정의 근거 코퍼스라 규정 문서와 같은 권한).

**`PolicyDoc`으로 만들지 않았다.** 사례는 이미 `case_history`에 적재돼 있어서 문서
파이프라인(파싱→청킹→임베딩→`policy_docs`)에 태우면 **같은 내용이 두 컬렉션에 이중 적재**되고
검색이 자기 자신과 겹친다. `PolicyDoc`은 파일 전제라 원문보기·재색인도 빈 껍데기가 된다.
그래서 트리에 자리만 만들고 내용은 `DecisionCase`를 직접 읽는다.

**월별로 묶은 이유**: 1건 = 1항목이면 트리가 금세 수백 줄이 되고, 전부 한 덩어리면
"언제 결정한 사례인가"를 못 고른다. 결정은 월 단위로 몰려 검토·집계된다(팀 통계·검토
이력이 이미 이번 달 기준이다). 월 목록은 **항상 전체 기준**으로 낸다 — 선택한 달만 보이면
다른 달로 넘어갈 수 없다. 미적재 건수를 월 옆에 표기한다(검색에 안 잡힌다는 뜻이라
숨기면 "왜 인용이 안 되지"를 아무도 못 본다).

## 7. 남은 것

- **골든 시드 폐기 시점**: 실 사례가 쌓이면 `golden_cases.py`를 뺀다. 지금은 둘이 같은
  컬렉션에 섞여 있고 `citation`(`과거 반려사례 #1123` vs `과거 결정사례 #12`)으로만 구분된다
  — 시연용 예시가 실 근거처럼 인용되지 않게 **메타데이터로 구분하는 편이 낫다**(미결).
- **개인정보**: `text`에 가맹점·금액·목적이 그대로 들어간다. 사내 시스템 전제라 지금은
  그대로 두지만, 외부 공유·장기 보존 정책이 정해지면 마스킹 규칙이 필요하다(미결).
- **품질 피드백**: 어떤 사례가 실제로 인용됐는지(2차 검증 `similar_cases`)를 되짚어
  쓸모없는 사례를 걷어내는 경로가 없다.

## 시드가 만드는 30건 (2026-08-26)

`seed_adopted`가 **실제 검토를 태워** 30건을 남긴다(손으로 쓰지 않는다 — `services.review()`가
「사람이 기계와 다르게 판단했다」고 보고 남기는 그 경로다).

**오랫동안 0건이었다.** 시드가 `RiskReview.ai_recommendation`을 결말에서 뽑아 써서 사람과
기계가 항상 같았고, `record()`는 다를 때만 남긴다. 185건을 돌려도 사례가 안 생겼고 **아무도
그걸 몰랐다** — 실패가 아니라 무행동이라 로그도 안 남는다. 지금은 끝에서 수를 대조해 경고한다.

| 패턴 | 전이 | 가르치는 것 |
|---|---|---|
| **A 소명 확인** | AI 반려 → 사람 승인 | **오탐 교정.** 형식 신호가 곧 위반이 아니다 |
| **B 놓친 실질** | AI 승인 → 사람 보완·반려 | **미탐 교정.** 통과 신호가 곧 정상이 아니다 |
| **C 수위 조정** | AI 반려 → 사람 보완요청 | **처리 등급.** `REJECT`는 재제출을 막는다 — 고칠 수 있으면 보완이다. 규정이 아니라 **이 회사가 일하는 방식**이라 문서에서 못 뽑는다 |

셋이 각각 판정을 낮추고·올리고·같은 위반을 다른 등급으로 처리한다. 하나만 쌓으면 검색이
그쪽으로 쏠린다. **달을 앞쪽에 몰았다**(11/10/9) — 도입 초기에 많이 뒤집고 룰이 쌓일수록
준다는 곡선이 데이터에 남는다.

### 사실은 「엔진이 실제로 REVIEW를 내는 것」에서만 고른다

사례는 검토를 거쳐야 생긴다. 처음엔 회식 1인당 한도 초과·심야 주말 결제로 짰는데 **30건 중
21건이 증발했다** — 전자는 `M-01`이 `RETURN`을 내고(보완요청이지 검토가 아니다) 후자는
게이트 v7에 그런 룰이 아예 없다. 그럴듯한 위반과 실제로 사람에게 오는 사실은 다르다.

실측으로 확인한 REVIEW 경로 셋:
  · **접대 청탁금지법 대상자 참석 + 1인당 법정 한도 초과**(`E-03`) — 법률 리스크라 자동 처리 안 함
  · **가맹점 업종 미확인** — 정본 어휘로 못 접으면 게이트 화이트리스트를 못 넘는다.
    `기타`로 밀지 않는 설계가 그대로 드러나는 자리다(모르면 사람에게).
  · **지출 목적 미기재** — 같은 화이트리스트에서 탈락

같은 이유로 **기존 시드의 기대값도 낡아 있었다**(「검토를 거쳐 승인」 2건·검토 큐 3건이 두 달
내내 성립하지 않았다). 경고는 매번 났지만 목록이 12줄에서 잘려 안 보였다.

### 사유 문장이 사례의 본체다

임베딩되는 `text`는 `상황 + "AI 권고는 X였으나 담당자는 Y로 판단" + 사유`이고 앞의 둘은 코드가
조립한다. **값어치는 전부 `reason`에 있다** — 무엇을 확인했는지·어느 조항인지를 문장에 담는다.
회귀가 40자 미만을 막는다.
