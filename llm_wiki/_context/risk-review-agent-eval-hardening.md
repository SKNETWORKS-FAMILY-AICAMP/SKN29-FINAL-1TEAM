## 1. 결함 ① — 권고 규칙이 코드에 연결돼 있지 않았다

### 무엇이 문제였나

v1 설계는 판단(위반 여부)과 처리방침(권고)을 분리하려고 액션 전용 LLM 호출
`_decide_action()`을 만들었고, 그 프롬프트에 규칙이 명시돼 있었다
(`NO_VIOLATION → APPROVE` 등). **그런데 이 함수는 어디서도 호출되지 않았다.**
실제 경로는 ①분류(`_classify`) → ②보고서(`_build_report`) 두 호출뿐이고, 최종
권고는 보고서가 낸 값을 그대로 썼는데 — **보고서 프롬프트에는 그 규칙이 없었다.**

결과(실측): 「위반 아님」 72건 중 **52건에 보완요청**. 모델이 지시를 어긴 게 아니라
**지시가 전달되지 않았다.**

왜 오래 안 드러났나: 회귀 테스트가 `_decide_action`을 **직접 import해서** 검증했다.
죽은 함수를 테스트가 살아 있는 것처럼 통과시켰다.

### 어떻게 고쳤나 — LLM 호출을 늘리지 않는다

죽은 호출을 되살리면 건당 ~14초·비용이 추가되는데, 규칙 자체가 결정론적이라 모델에게
물을 이유가 없다. 규칙표 하나를 **세 곳이 같이 보게** 했다.

```python
_ALLOWED_RECOMMENDATION = {          # 프롬프트·출력 스키마·서버 검증의 단일 출처
    "NO_VIOLATION":      ("APPROVE",),
    "VIOLATION":         ("REJECT", "SUPPLEMENT"),   # 수위는 정말로 판단의 영역
    "INSUFFICIENT_INFO": ("SUPPLEMENT",),
}
```

| 겹 | 구현 | 성격 |
|---|---|---|
| 출력 스키마 | verdict별로 `recommendation` enum을 좁힌 `RiskReport` 서브클래스 3종(`_REPORT_MODEL`) — 「위반 아님」이면 `APPROVE` 외에는 **낼 수 없다** | 보장 |
| 프롬프트 | 시스템 규칙 10번 신설 + 사용자 프롬프트에 허용 값 명시. 「‘확인해 보면 좋겠다’는 보완요청 사유가 아니다 — advisories에 쓰라」 | 확률 |
| 서버 정정 | `_validate_report()`가 어긋난 권고를 `_ACTION_FALLBACK`으로 되돌린다(기존 「보류인데 승인」 1케이스 정정을 일반화) | 보장 |

**낼 수 없어야 하는 값은 지시가 아니라 스키마에서 뺀다** — Rule Agent가 자동 통과를
스키마에서 뺀 것과 같은 장치다(CLAUDE.md §2).

### 정리한 것

- `_decide_action()` · `_ACTION_SYSTEM_PROMPT` · `_ACTION_USER_PROMPT_TEMPLATE` ·
  `ActionDecision` 모델 **삭제**(~60줄). 같은 값을 주는 창구가 둘이면 하나는 반드시
  뒤처진다 — 이번이 그 실례였다.
- `_ACTION_FALLBACK`(결정론적 폴백 매핑)은 유지 — 서버 정정과 `_fallback_report`가 쓴다.
- 죽은 함수를 검증하던 테스트 2건을 **실제 경로** 검증 6건으로 교체:
  폴백 매핑 · 서버 정정(`_validate_report`) · 재작성 사유(`_report_problems`) ·
  스키마 좁힘 · override 스위치. ai 전체 **525 passed / 13 skipped**.

## 2. 결함 ② — 등급 게이트가 검사 기회를 주지 않았다

100건 중 96건이 LOW(컷오프 0.011 미만)로 떨어져 **LLM 0회 + 승인 권고**로 나갔다
(850,000원 카지노 결제 포함). 컷오프의 근거가 위험 라벨 5건뿐이라 코드 주석 스스로
「분리점이 아니라 힌트」라고 적어둔 값이다.

### 임시 우회 — `RISK_TIER_OVERRIDE`

컷오프를 재산출할 때까지 등급을 강제 고정하는 env 스위치를 넣었다. `DOCLING_MOCK`과
같은 규율을 따른다:

- **호출 시점에 env를 읽는다** — `docker exec -e RISK_TIER_OVERRIDE=MEDIUM`으로
  프로세스 단위 지정, 스택 재시작 불요.
- **켜져 있으면 조용히 돌지 않는다** — WARNING 로그 + stage1 결과에
  `tier_forced: true`와 `note`(「점수로 정해진 등급이 아닙니다」)가 실린다.
- 오타 값은 조용히 무시하지 않고 **꺼진 것으로** 본다(`_tier_override()`).

근본 해소는 위험 라벨 확충 후 컷오프 재산출(`risk-review-agent-v2.md` §컷오프 결정 계획).

## 3. 보고서 검증 → 재작성 루프

`_build_report()`에 Rule Agent의 재생성 루프와 같은 모양의 루프를 넣었다
(최대 `MAX_REPORT_ATTEMPTS = 2`).

- 되돌려 보낼 사유는 `_report_problems()`가 모은다 — ① 분류와 어긋난 권고
  ② 근거 목록에 없는 id 인용 ③ 빈 요약 ④ (근거가 주어졌는데) 인용 0개.
- `_validate_report`와 역할이 다르다: 저쪽은 「그대로 쓸 수 없는 부분을 걷어내는」
  최종 방어, 이쪽은 「**다시 시킬 값어치가 있는가**」. 강등으로 해결되는 것(근거 없는
  finding → advisories)은 재시도 사유가 아니다.
- 2회 소진해도 **보고서를 버리지 않고** 서버 정정으로 넘긴다 — 담당자를 빈손으로
  두지 않는다(`_fallback_report`와 같은 원칙).
- ⚠️ 미완: 재작성 발동 횟수가 응답에 안 실려 이번 측정에서 효과를 분리하지 못했다.

## 4. 검증이 강제한 환경 복구 (평가 전 선행)

| | 발견 상태 | 조치 |
|---|---|---|
| Chroma `policy_docs` | 4개 규정 96청크 — **회식·식대 규정이 없음** | 파싱 덤프에서 6종 154청크 재적재(`app.rag.embedding.index --only ...`, 과금 토큰 48,205) |
| `PolicyDoc`(관계형) | **0행** → scope 필터가 상시 무력(fail-open으로 전체 검색) | 6행 생성(`rule_scope` 매핑: 업무추진비→접대, 법인카드→공통 등) |

관계형·벡터 **두 절반 중 한쪽만 있으면 에러 없이 반쪽**이 된다(CLAUDE.md §6 경고
그대로) — 지난 QA가 고쳤다는 카테고리 누수가 이 상태에서 재현되고 있었다. 복구 후
인용 scope 정합 **100/100** 확인.
