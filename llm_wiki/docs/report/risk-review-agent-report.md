# 검토 에이전트(Risk Review Agent) 검증 결과

_2026-08-28 · 대상: `apps/ai/app/agents/risk_review_agent.py::run()` · 검증셋 100건 E2E_

> **한 줄**: 검증셋 100건을 만들어 평가 → 결함 수정 → 재평가 루프를 돌렸다.
> 최종 **정확도 69% · 오탐(정상→되돌림) 6건 · 분류와 어긋난 권고 0건 · 인용 규정
> 정합 100%**. 남은 손실은 전부 「위반을 못 알아본」 미탐이며, 그 원인 셋이 특정됐다.

---

## 1. 무엇을 검증했는가

재는 것은 하나 — **「그래서 이 건을 어떻게 하라고 했는가」**, 최종 추천처리의 합리성이다.

에이전트는 건마다 승인(`APPROVE`) · 보완요청(`SUPPLEMENT`) · 반려(`REJECT`) 중 하나를
권고한다. 채점은 이 셋을 **두 값으로 접어서** 한다.

```
APPROVE            →  승인      (통과시켜도 된다)
SUPPLEMENT/REJECT  →  보완반려   (되돌려야 한다)
```

「보완인가 반려인가」는 담당자가 조정할 수 있는 수위의 문제지만, 「통과인가 되돌림인가」를
틀리면 **정산 결과 자체가 달라진다.** 실무 임팩트가 갈리는 축으로 잰다.

재지 않는 것 — 지어낸 조항 인용(서버가 검색 결과와 대조해 버린다), 보고서 문장 품질
(근거 없는 판단은 참고사항으로 강등된다)은 하네스가 구조적으로 막으므로 여기서 다시
재지 않는다. 다만 **인용이 분류에 맞는 규정을 봤는가**(scope 정합)는 함께 확인했다.

## 2. Agent Flow — 무엇을 평가한 것인가

```
정산 번호
   │
   ▼
[1차] 이상탐지 (비지도, 카드 이력 기반)
   │    anomaly_score → 위험 등급
   │
   ├─ LOW ──────────► LLM 0회 · 「검사하지 않음」 명시 + 승인 추천
   │
   ▼ MEDIUM(fast) / HIGH·미측정(heavy)
[2차-①] 분류 — 내규 위반인가?
   │    RAG 검색(분류별 규정으로 스코프 제한) + 근거 부족 시 자가 재검색
   │    → 위반 / 위반 아님 / 판단 보류
   │
   ▼
[2차-②] 보고서 — 담당자가 읽는 산출물
   │    요약·근거·권고. 권고는 ①의 분류가 허용하는 값만:
   │      위반 아님 → 승인 · 위반 → 반려/보완 · 보류 → 보완
   │    검증 → 재작성 루프(최대 2회) 후 서버가 인용 대조·권고 정정
   ▼
 승인 / 보완요청 / 반려  +  근거 보고서
```

이번 평가는 이 흐름의 **끝값(권고)**을 채점했고, 등급 게이트는 `MEDIUM` 고정으로 열어
**전건이 2차 검증을 받게 한 상태**에서 측정했다(게이트 컷오프 자체는 별도 과제 — §6).

## 3. 검증셋 — 100건

### 왜 새로 만들었나

룰엔진 검증용 골든 300건은 못 쓴다 — 그 셋은 판정 사실 묶음만 갖고 **정산 행이 없어**
카드 이력 기반 1차 탐지가 돌지 않고, 이 에이전트의 핵심 입력인 **지출 목적(자유서술)**이
아예 없으며, 「애매한 건 제외」라는 설계 원칙이 검토 에이전트가 투입되는 자리를 정확히
비워둔다. 그래서 실제 정산 행 100건을 실제 상태머신으로 생성했다(`manage.py seed_risk_eval`).

### 구성 (50 : 25 : 25)

| 라벨 | 건수 | 성격 |
|---|---|---|
| **승인** | 50 | 5개 분류 × 10건. 모든 요건이 갖춰진 정상 지출 |
| **보완반려 · 서류미비** | 25 | 사실관계는 정상이나 확인할 근거가 없다 — 사전승인 누락 7 · 인원 미기재 6 · 목적 미기재 6 · 증빙 누락 6 |
| **보완반려 · 규정위반** | 25 | 보완으로 해소되지 않는 위반 — 금지업종 10 · 현금성 5 · 1인당 한도 5 · 숙박비 상한 4 · 개인 목적 1 |

채점은 승인 vs 보완반려 2값. 서류미비/규정위반 구분은 수위 선택 경향을 따로 보기 위한
표시일 뿐 채점에 쓰지 않는다.

### 설계 원칙

- **위반은 한 건에 하나만** — 겹치면 어느 근거로 잡았는지 알 수 없다.
- **정상 건이 우연히 위반이 되지 않게** — 참석 인원을 금액에서 역산해 1인당 한도 안에 둔다.
- **신호가 실재하는 결함만** — 「참석자 명단 없음」은 요약 정보에 흔적이 없어 뺐다.
  못 맞히는 게 아니라 맞힐 수 없는 문제는 넣지 않는다.
- **카드 이력을 새로 만들지 않는다** — 기존 카드(거래 21~26건)에 얹어 1차 탐지가
  의미 있는 비교 대상을 갖게 한다.

### 예시

```
승인 · 회식        고기굽는집 판교 186,000원 · 6명 → 1인당 31,000원(한도 내) · 요건 전부 충족
서류미비 · 접대     한정식 소반 620,000원 · 50만 초과인데 사전승인 기록 없음 — 서류를 받으면 풀린다
규정위반 · 접대     강원랜드 카지노 850,000원 — 업종 신호가 가맹점 이름에만 있다
규정위반 · 회식     한우오마카세 640,000원 · 4명 → 1인당 160,000원 — 나눠 봐야 드러난다
규정위반 · 출장     그랜드호텔 420,000원 · 1박 — 상한(150,000)이 본문이 아니라 별표에 있다
```

참고로 **룰엔진도 같은 100건 중 보완반려 7건을 통과**시켰다(숙박비 상한 4 포함) —
검증셋이 어느 쪽에도 맞춰 설계되지 않았다는 방증이다.

## 4. 평가 수치

### 검증 → 개선 → 재검증

1차 측정이 결함 두 개(등급 게이트가 96건을 검사 없이 통과 · 권고 규칙 미배선)를
드러냈고, 수정 후 같은 셋으로 재측정했다. 개선 내용은
[`_context/risk-review-agent-eval-hardening.md`](../../_context/risk-review-agent-eval-hardening.md).

| 회차 | 정확도 | 오탐(정상→되돌림) | 미탐(위반→승인) |
|---|---|---|---|
| 1차 (수정 전) | 54 / 100 | 0건 | 46건 — 대부분 「검사 자체를 안 받음」 |
| **최종 (수정 후)** | **69 / 100** | **6건** | **25건** |

### 최종 결과 상세

| 지표 | 값 |
|---|---|
| 정확도 (승인 vs 보완반려) | **69 / 100** |
| 오탐 — 정상인데 되돌림 | **6건** (판단 보류 4 · 오판 2) |
| 미탐 — 위반인데 승인 | **25건** |
| 분류와 어긋난 권고 | **0건** (수정 전 52건) |
| 인용 규정 scope 정합 | **100 / 100** |
| 지연 | 중앙 15.4초 · 최대 26.2초 (2차 검증 전건 수행 기준) |

```
분류 결과      →  권고
위반 아님  69건 →  승인 69            ← 전건 일치
위반      25건 →  반려 22 · 보완 3
판단 보류   6건 →  보완 6
```

### 결함 유형별 적중 (보완반려 50건)

```
사전승인 누락  7/7      현금성 자산  4/5      개인 목적    1/1
인원 미기재    3/6      목적 미기재  3/6      금지업종     4/10
1인당 한도    2/5      숙박비 상한  1/4      증빙 누락    0/6
```

## 5. 해설

### ① 권고는 이제 판단을 그대로 따른다

수정 전에는 「위반 아님」으로 판단한 건의 72%에 보완요청이 붙어, 같은 실행을 분류로
채점하면 68점인데 권고로 채점하면 58점이었다 — **10점이 권고 단계에서 새고 있었다.**
수정 후 두 수치가 69로 일치한다. 어긋난 권고 0건.

### ② 오탐 6건 — 넷은 신중함, 둘은 오류

접대 4건은 판단 보류(정보 부족을 이유로 보완 요청) — 방향이 안전한 쪽이다. 문제는
회식 2건으로, **214,000원·152,000원을 「30만원 초과」라며 되돌렸다.** 금액 기준 비교를
모델이 틀린 것이고, 수정 전에도 같은 오류가 재현됐다 — 임계값 비교를 모델에 맡기지
말고 사실로 주입해야 한다(§6-3).

### ③ 미탐 25건 — 원인이 셋으로 갈린다

**손실의 대부분이 여기이고, 전부 2차 분류(위반을 알아보는 능력)의 몫이다.**

- **전달 누락 (6건)** — 증빙 유무가 에이전트에게 가는 요약에 실리지 않아 증빙 누락
  6건을 전부 놓쳤다. 모델의 실패가 아니라 우리가 안 보낸 것이다.
- **이름 추측의 한계 (6건)** — 금지업종은 가맹점 이름으로만 알 수 있는데, 「유흥주점」
  「노래방」처럼 업종명이 그대로 있으면 잡고 「룸살롱」「가라오케」「CC」 같은 관용어는
  놓친다. 업종 판정 도구(`classify_merchant`)가 이미 있으나 Draft에만 연결돼 있다.
- **별표 값 미참조 (숙박비 4건 중 3건)** — 상한이 본문이 아니라 별표에 있다.
  **룰엔진도 같은 4건을 전부 통과시킨 자리**로, 두 계층이 같은 곳에서 뚫렸다.

### ④ 반려 권고는 남발되지 않는다

반려 22건 중 21건이 실제 보완반려 라벨 — 되돌릴 수 없는 최종반려를 정상 건에 잘못
내리는 일은 1건(위 ②의 214,000원 건)뿐이었다.

### ⑤ 검색 스코프는 정확하다

식대 건은 식대 규정을, 회식 건은 회식 규정을 봤다(100/100). 과거 QA의 「식대 건에
회식 규정 인용」 결함은 재현되지 않았다.

## 6. 남은 과제

| # | 무엇 | 방향 |
|---|---|---|
| 1 | 등급 게이트 컷오프 — 이번 표본에선 96건이 LOW로 떨어져 임시 고정(`RISK_TIER_OVERRIDE`)으로 우회했다 | 위험 라벨 확충 후 재산출 |
| 2 | 증빙 유무가 요약에 안 실린다 (미탐 6건) | 전달 항목 추가 |
| 3 | 금액 기준 비교를 모델이 틀린다 (오탐 2건) | 임계값 비교 결과를 사실로 주입 |
| 4 | 금지업종을 이름 추측에 맡긴다 (미탐 6건) | `classify_merchant` Risk 연동 |
| 5 | 숙박비 상한 — 룰·AI 공동 미탐 | 출장 입력칸(상태 보드 §3.7-3)과 함께 |

이번 검증이 답하지 못한 것: LOW 등급의 실제 안전성(표본 등급 쏠림), heavy 경로 품질
(HIGH 0건 — fast로만 측정).

## 7. 재현

```bash
# 검증셋 100건 (기존 실행분을 지우고 다시 만든다) — 라벨: apps/core/var/risk_eval_golden.json
docker compose exec core python manage.py seed_risk_eval

# 평가 — 등급 고정으로 전건 2차 검증 (켜지면 WARNING 로그·결과 note에 명시된다)
docker exec -e RISK_TIER_OVERRIDE=MEDIUM <ai> ...   # run(settlement_id) × 100
```

검증셋은 실제 정산 행이라 DB가 필요하다 — `seed_adopted`(또는 `seed`)가 먼저 돌아
카드 이력이 있어야 한다. 규정 코퍼스(6종 154청크)가 비어 있으면 먼저 적재할 것
(개선 기록 §4).
