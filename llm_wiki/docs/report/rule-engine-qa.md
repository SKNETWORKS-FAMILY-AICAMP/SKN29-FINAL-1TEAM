# 룰엔진 검증 결과 — 도입 타임라인 단계별 채점

_2026-08-25 · 대상: `domain/policies` 룰 그래프 전체(공통 게이트 + 과목별 4종)_

> **한 줄**: 회계가 규정을 쌓아 갈수록 **자동처리율은 26% → 100%**로 오르고,
> **오탐율은 0%를 유지**하다 최종 0%로 끝난다. 300건 검증셋을 7개 그래프 버전에
> 전부 돌려 잰 실측이다.

## 1. 무엇을 검증하려 했나

### 룰엔진은 분류기다

이 검증의 전제는 [[rule-engine-semantics]]다. 룰엔진은 「잘못된 지출을 찾는 탐지기」가
아니라 **규칙으로 결론 낼 수 있는 건을 골라내는 분류기**다.

```
       ┌─ PASS   (승인대기)  ─┐
정산 ──┼─ RETURN (보완요청)  ─┼─ 룰이 **확정**했다  → 자동처리
       ├─ REJECT (반려)      ─┘
       └─ REVIEW (검토)      ─── 룰이 **확정 못 했다** → 사람에게
```

- **검토는 실패가 아니다.** 회계가 아직 정의하지 않은 영역의 크기다.
- **승인대기는 적극적 결정이다.** 「이런 기준을 만족했으므로 승인해도 된다」이지
  「위반을 못 찾았다」가 아니다 — 그래서 게이트는 **화이트리스트**여야 한다.

### 재는 것 둘

| 지표 | 정의 | 왜 |
|---|---|---|
| **자동처리율** | 1 − (검토 / 전체) | 룰이 결론 낸 비율. 규칙이 촘촘해질수록 올라야 한다 |
| **오탐율** | 확정한 것 중 **틀린** 비율 | ① 되돌릴 건을 `PASS`로 ② 승인할 건을 `RETURN`으로 |

**미탐은 재지 않는다.** 「확정할 수 있었는데 검토로 넘김」은 곧 검토 비율이고,
자동처리율의 역이라 같은 수를 두 번 적는 셈이다.

### 검증 방식

`domain/policies/rule_timeline.py`의 7단계를 각각 스냅샷으로 만들어 300건에 돌린다.
`run_rule_engine(ctx, snapshot)`은 **외부 I/O가 없는 순수 함수**이므로 ACTIVE를 바꿔
끼울 필요도, DB도 필요 없다.

```bash
python manage.py rule_eval --md var/rule_eval.md --miss
```

`orchestrator.judge`와 **같은 순서**로 돈다 — 게이트 → (통과 시) 과목별.

`domain/policies/golden.py`. EvalContext를 직접 조립하고, **정답이 자명한 건만** 담는다.
검토가 정답인 케이스를 섞으면 「확정을 맞게 했는가」를 못 재기 때문이다.

| | 건수 | 구성 |
|---|---|---|
| **승인** | 180 | 6개 과목 × 30건. 금액·가맹점·시각만 흔들고 판정 사실은 전부 정상 |
| **보완반려** | 120 | 공통 40 · 접대 30 · 회식 30 · 출장 20 |

**위반은 하나만 뒤집는다.** 둘을 겹치면 어느 룰이 잡았는지 알 수 없고, 한 룰을 빼도
다른 룰이 가려 주어 결함이 안 드러난다.

### 특징적인 예시 셋

**① 정상 회식 — 인원이 한도를 가른다**

```
금액 285,000 · 참석 8명 → 1인당 35,625원 (한도 50,000 이하)
증빙 O · 목적 O · 분류 「회식」 · 업종 일반음식점 · 2차 아님
   → 기대: PASS
```

인원을 금액에서 역산해 **정상 건이 무작위로 한도 초과가 되지 않게** 했다. 인원을
금액과 무관하게 뽑으면 평범한 회식의 절반이 위반으로 둔갑한다.

**② 1인당 한도 초과 — 신고값이 아니라 확인값으로 잰다**

```
금액 420,000 · 참석 4명 → 1인당 105,000원
   → 기대: RETURN (M-01)
```

룰은 `tx.verified_per_person_amount`(문서로 확인된 인원)를 본다. 신고값으로 나누면
**인원을 부풀리는 것만으로 한도를 피할 수 있다.**

**③ 당일 출장 — 없는 사실로 걸지 않는다**

```
출장 구분 국내당일 · 숙박비 청구 없음(null)
   → 기대: PASS (T-01이 한도 검사를 건너뛴다)
```

숙박비는 출장계획서 첨부에서만 오고 화면 입력칸이 없어 **거의 전건 null**이다.
`is_null` 선분기가 없으면 미해소 가드가 당일 출장까지 검토로 보낸다.

### 검증셋에서 **뺀 것** — 청탁금지법

한도 초과 자체는 규칙으로 확정할 수 있지만, **법 위반 소지가 있는 건은 자동 반려도
자동 승인도 위험**해 `E-03`이 일부러 `REVIEW`를 낸다. 「확정을 맞게 했는가」를 재는
검증셋에 넣으면 그 정책적 선택이 오탐으로 잡히거나 자동처리율을 깎는다 — 재려는
것이 아니다.

## 3. 그래프 발전 이력

`domain/policies/rule_timeline.py`가 정본이다. `seed_rules._seed_timeline`이 이 7단계를
**실제 `RuleGraph` 버전**으로 심고 `activated_at`을 D-88 ~ D-4로 찍는다 — 룰 콘솔의
버전 이력이 곧 도입 서사다(v7만 ACTIVE, 나머지 ARCHIVED).

| 버전 | 시점 | 무엇이 늘었나 |
|---|---|---|
| v1 | D-88 | 제품 기본 게이트. 자동 통과는 **3만원 미만**만 |
| v2 | D-74 | 공용카드 실사용자 + 상한 10만 |
| v3 | D-60 | **업무추진비** 규정 — 증빙·사전승인·참석자 + 상한 30만 |
| v4 | D-46 | 업무추진비 **별표1**(청탁금지 대상자 한도) |
| v5 | D-32 | **회식** 규정 — 1인당 한도·2차 + 상한 50만 |
| v6 | D-18 | 회식 **제7조**(총액 30만 초과 사전승인) |
| v7 | D-4 | **출장** 규정 — 1박 상한 + 숙박 미청구 선분기. **금액 상한 제거** |

**자동 통과 금액 상한이 단계마다 넓어지는 것**이 핵심이다. 도입 직후에는 제품이 그 회사
규정을 모르므로 소액만 확정할 수 있고, 과목 규칙이 생기면 그 과목은 자기 그래프가
판단하므로 상한을 넓힐 수 있다.

## 4. 최종 그래프 구조 (v7)

### 공통 게이트 — 위반 검사 → 화이트리스트

```
G-01 금지업종        ─ MATCH → RETURN
G-02 현금성 자산      ─ MATCH → RETURN
G-03 실사용자 확인불가 ─ MATCH → REVIEW      (is_null — 모름은 통과시키지 않는다)
G-04 실사용자 미기재   ─ MATCH → RETURN
G-05 적격증빙 없음    ─ MATCH → RETURN
        ↓ NO_MATCH
G-PASS 자동 통과 요건 ─ MATCH    → PASS      증빙 ∧ 목적 ∧ 분류 ∧ 업종확인
                     └ NO_MATCH → G-REVIEW   ∧ 비금지업종 ∧ 실사용자기록
G-REVIEW 요건 미충족  ─ → REVIEW
```

> ⚠️ **`G-REVIEW`가 없으면 화이트리스트가 무력해진다.** 엔진은 다음 노드가 없을 때
> 「조건이 맞았는가」와 무관하게 그 노드의 액션을 돌려주므로, `G-PASS`(액션 `PASS`)를
> 단말로 두면 요건을 못 채운 건까지 `PASS`가 된다. 실측에서 금액 상한을 3만으로 좁혀도
> **자동처리율이 100% 그대로**였던 원인이다.

### 과목별

| 과목 | 노드 | 판정 |
|---|---|---|
| **접대** | E-01 기준액 초과 증빙 없음 | RETURN |
| | E-02 사전승인 기준액 초과 | RETURN |
| | E-03 청탁금지 대상 한도 초과 | **REVIEW** — 법률 리스크는 규칙이 확정하지 않는다 |
| | E-04 참석자 명단 없음 | RETURN |
| **회식** | M-01 1인당 식대 한도 초과 | RETURN |
| | M-02 2차 비용 | RETURN |
| | M-03 총액 30만 초과 사전승인 없음 | RETURN |
| **출장** | T-01 숙박비 청구 없음 | **PASS** — 없는 사실로 걸지 않는다 |
| | T-02 1박 상한 초과 | RETURN |

각 과목은 `*-PASS` 종단(`condition: True`)으로 끝난다.

## 6. 해설 — 핵심만

### ① 초기 게이트는 열려 있고, 대부분을 검토로 흘린다

v1의 검토 **221건(74%)**은 결함이 아니다. 제품이 그 회사 규정을 모르는 상태에서 확실히
말할 수 있는 것은 「3만원 미만 + 서류 완비면 승인해도 된다」와 「금지업종·현금성·증빙누락은
되돌려야 한다」뿐이다. **나머지는 「모른다」이고, 모름은 검토다.**

이때 오탐이 0%인 것이 중요하다 — **적게 확정하되 확정한 것은 틀리지 않는다.**

### ② 룰이 늘수록 처리율이 오른다 — 룰 수가 아니라 「판단 범위」 때문

26.3% → 50.3% → 81.3% → 88.0% → **100%**.

오르는 이유는 룰이 늘어서가 아니라, 늘어난 룰이 **게이트의 금액 상한을 넓힐 근거**가
되어서다. 접대 규칙이 생기면 30만원짜리 접대를 접대 그래프가 판단하므로 게이트가
그 구간을 열 수 있다.

### ③ 오탐은 일정 선을 유지하다 0으로 안정된다

전 구간 **최대 3.8%**, 최종 **0%**.

v5에서 잠깐 오른 것도 서사가 있다 — 게이트 상한을 50만으로 넓힌 순간 **회식 총액 룰이
아직 없어서** 30만 초과 회식 10건이 통과했다. v6에서 제7조를 넣자 0으로 돌아왔다.

> **넓히기가 먼저고 룰이 나중이면 그 틈이 오탐이다.** 반대 순서였다면 오탐은 내내 0이지만
> 자동처리율도 안 올랐을 것이다.

### ④ v4는 수치를 바꾸지 않는다 — 그게 정상이다

청탁금지 룰(`E-03`)은 `REVIEW`를 내므로 확정 건수에 잡히지 않는다. **자동처리율을 올리는
것이 룰의 유일한 목적이 아니다** — 사람이 반드시 봐야 할 것을 골라내는 것도 룰의 일이다.

## 7. 시연 시드 반영 (`seed_adopted`)

새 그래프를 실제 시연 데이터에 적용했다.

| | 이전(블랙리스트 게이트) | **지금(화이트리스트 + 타임라인)** |
|---|---|---|
| 자동처리율 | 92.3% | **97.3%** |
| `PASS` | 168 | 177 |
| `RETURN` | **0** | (보완 후 재제출로 해소) |
| `REVIEW` | 14 | **5** — 전부 청탁금지 법률 리스크 |

이전 92.3%는 **「위반을 못 찾았으니 승인」 122건(67%)**이 떠받치고 있었다. 지금 97.3%는
전건이 요건을 실제로 통과해서 나온 수치다 — **같은 숫자가 아니다.**

검토로 남는 5건은 전부 `KICKBACK_LAW_RISK`다. 규칙이 확정하지 않기로 한 영역이 정확히
그만큼 남는다.

### 회귀

`domain/policies/tests/test_seed_adopted.py` 13건 통과. 특히:

- **검토로 간 건에는 사유가 붙어 있다** — 사유 없이 검토 큐에 오면 담당자가 빈손으로 받는다
- **미해소 강등으로 검토에 온 건이 없다** — `UNRESOLVED_*`는 「사실이 없어서 판정을 못 했다」는
  뜻이라 적용 완료 회사엔 없어야 한다
- **지난달은 끝나 있다** — 미결이 지난달에 남으면 「적용 완료」가 아니라 「밀린 회사」다
