# 멀티에이전트 협업 기반 — 주제 정합 논거와 발전 계획

> 작성 2026-08-25 · 대상: 프로젝트 대주제(**멀티에이전트 협업 기반**)와 현 구현 사이의 간극에
> 대한 설명 자료. 인용한 수치는 이 저장소 실측값.

---

## 0. 문제 제기

지적은 타당하다. 지금 만든 것은 **"다양한 워크플로우를 시스템적으로 잘 엮어냈다"**에 가깝다.
정산 입력 → 룰 판정 → 이상탐지 → 검토 → 확정 → 전표까지 흐름은 촘촘하지만, 그 각 단계는
대부분 **정해진 순서대로 도는 파이프라인**이고, "여러 에이전트가 자율적으로 협업한다"는
대주제의 그림과는 결이 다르다.

이 문서는 세 가지를 정리한다.

1. **왜 그 노선을 택했는가** — 도메인이 강제한 선택이었고, 그 선택 자체가 결과물이다.
2. **그럼에도 이것은 멀티에이전트 협업이다** — 어떤 근거로 그렇게 부를 수 있는가.
3. **어디를 더하면 논쟁의 여지가 없어지는가** — 실제로 남은 작업.

---

## 1. 노선 선택 — 왜 완전 자율 에이전트가 아니라 워크플로우인가

### 1.1 도메인이 요구한 제약

법인카드 정산은 **돈이 나가고, 세무·감사 대상이 되고, 틀리면 사람이 책임지는** 업무다.
이 도메인에는 자율 에이전트가 잘 못 지키는 요구사항 넷이 있다.

| 요구사항 | 왜 필요한가 | 자율 에이전트에서 어려운 이유 |
|---|---|---|
| **결정의 재현** | 같은 건은 같은 판정이 나와야 하고, 3개월 뒤 감사에서 "그때 왜 통과됐나"를 되짚어야 한다 | LLM 추론은 같은 입력에도 다르게 나온다. 근거를 남겨도 "그 근거면 그 결론"이 보장되지 않는다 |
| **상태 전이의 통제** | 정산은 여러 상태를 오가고, 각 전이에는 권한(누가)·조건(무엇이 충족돼야)이 붙는다 | 에이전트가 상태를 직접 바꾸면 권한 우회·순서 위반을 코드로 막을 수 없다 |
| **기록 추적** | 모든 판정과 결정은 누가·언제·무엇을 근거로 했는지 남아야 한다 | 자율 루프는 "왜 그 도구를 그때 불렀는가"까지 남기기 어렵고, 남겨도 사후에 읽히지 않는다 |
| **사람의 최종 확정** | 확신 통과 건도 회계 담당자 확정 없이는 확정될 수 없다 | 에이전트에게 종결 권한을 주지 않는 순간, 자율성의 상당 부분이 의미를 잃는다 |

한 문장으로: **"AI가 틀려도 시스템은 틀리면 안 된다"**가 이 도메인의 전제다.

### 1.2 그래서 택한 아키텍처

> **자율 에이전트를 워크플로우 안에 배치하되, 에이전트끼리는 공유 저장소를 통해 협업하는 구조.**

- **판정은 코드가** — 룰 엔진은 3단 파이프라인(사실 스냅샷 조립 → 그래프 선택 → 결정론적 순회).
  순회 중 외부 I/O는 0회이므로 같은 스냅샷이면 항상 같은 결과가 나온다. 조건은 JSON-Logic
  부분집합 DSL(`and`/`or`/`not`, `==`/`!=`/`>`/`>=`/`<`/`<=`/`in`, `is_null`)로 **임의 코드 금지**.
- **모델은 사람 말로 옮긴다** — "이 건이 왜 보완요청인가"를 LLM이 예측하지 않는다. 엔진이 이미
  답을 갖고 있고, 모델은 그 결과를 서술한다. 모델이 낼 수 없어야 하는 값은 지시가 아니라
  **출력 스키마에서 뺀다.**
- **AI가 만드는 것은 전부 제안** — 룰은 `DRAFT`로 저장되고 사람이 `ACTIVE`로 승격한다. 규정
  별표의 한도 수치도 별도 제안 모델에 들어가 승인 전에는 판정에 새어들 수 없다.

이건 타협이 아니라 **설계 결정**이다. 자율성을 줄인 만큼 얻은 것이 있다 — 판정 재현, 감사 추적,
그리고 "AI가 통과라 했는데 반려됨"이라는 사용자 경험의 제거.

## 2. 그럼에도 이것은 멀티에이전트 협업이다

### 2.1 개별 에이전트 — 무엇이 에이전트인가

판별 기준을 통용되는 다섯으로 두자.
**① 목표만 주면 스스로 계획한다 ② 도구를 스스로 고른다 ③ 결과를 보고 다시 시도한다
④ 상태를 기억한다 ⑤ 다른 주체와 소통한다.**

#### Rule Agent — 논쟁의 여지 없이 에이전트다

규정 문서를 주면 **"이 문서에서 룰을 만들어라"**라는 목표 하나로 다음을 스스로 한다.

- **자율 검색 루프** — MCP 툴콜링 멀티턴. 근거가 부족하다고 스스로 판단하면 `search_policy`를
  다시 부른다. 몇 번 부를지, 무엇으로 부를지는 모델이 정한다.
- **자기 산출물 검증과 재시도** — 만든 룰 그래프가 구조 검증(DAG·도달 가능성·변수 실재)에
  실패하면 오류를 되받아 고친다. 그래도 실패하면 자기가 추가한 노드만 롤백한다.
- **상태 기억** — 진행 중인 `DRAFT`가 있으면 읽고 **이어 붙인다**. 이미 만든 룰과 그 근거 조항을
  프롬프트로 받아 같은 조항으로 중복 생성하지 않는다.
- **사람과의 대화형 협업** — 룰 콘솔에서 "이 조건 22시로 바꿔줘"라고 하면 `create_node`·
  `update_node` 도구를 골라 실제 그래프를 수정한다. 대화 이력도 유지한다.

다섯 기준 중 ①②③④를 모두 만족하고, ⑤는 사람과 성립한다.

#### Risk Review Agent — 지금은 "조건 분기가 있는 파이프라인"에 가깝다

**갖춘 것.** 이상탐지 점수로 **스스로 검사 깊이를 정한다** — `LOW`는 LLM을 아예 안 부르고,
`MEDIUM`은 경량, `HIGH`는 정밀. 2차 검증은 MCP 멀티턴 툴콜링이라 근거가 부족하면 스스로
재검색한다. 판단(위반 여부)과 처리방침(권장 조치)을 별개 호출로 나눠, 근거 확보 루프가
정책적 선택을 오염시키지 않게 했다.

**모자란 것.** **계획을 세우지 않는다** — `1차 → (등급) → 2차 → 보고서`가 고정이고 모델이 이
순서를 바꿀 수 없다. 도구 선택 폭도 좁다(`search_policy`·`search_cases` 둘). 그리고 **다른
에이전트와 소통하지 않는다** — 검토 중 "이 조항에 해당하는 룰이 없다"를 알아내도 그 발견은
어디에도 남지 않고 사라진다.

②③은 부분적으로, ①④⑤는 없다. **지금 상태로 "에이전트다"라고 주장하면 반박당한다.**
무엇을 더하면 되는지는 §3에 적었다.

#### 그 밖

- **증빙자료 추출 Agent** — 첨부를 판독해 사실을 뽑고, 신뢰도 0.6 미만은 스스로 폐기한다.
  자율 판단은 있으나 단발이라 "도구"에 가깝다.
- **Draft Agent** — 사실을 모아 초안을 만들되 판정은 엔진에 위임한다(설계상 의도).
- **결정 사유 초안 Agent** — 선택지는 서버 정본, 문장만 LLM.

### 2.2 협업의 형태 — Blackboard

에이전트끼리 **서로를 직접 호출하지 않는다.** 대신 **공유 저장소에 쓰고, 다른 에이전트가 읽는다.**
이는 고전적 **Blackboard 아키텍처**(Hearsay-II)의 3요소와 정확히 대응한다.

```
        ┌──────────────────────── 흑판 (Blackboard) ─────────────────────────┐
        │  Postgres — EvalContext 스냅샷 · rule_hits · SettlementEvent        │
        │             RuleGraph(DRAFT/ACTIVE) · PolicyTable(+승인 제안)       │
        │             audit_logs · Notification                               │
        │  Chroma   — policy_docs · case_history · tax_refs                   │
        └─────────────────────────────────────────────────────────────────────┘
             ▲ 쓰기           ▲ 쓰기          ▲ 읽기·쓰기       ▲ 읽기
             │                │               │                 │
        [증빙 추출]      [Rule Agent]    [Risk Review]     [Draft Agent]
             │                │               │                 │
        └────────────────── 통제자 (Control) ───────────────────┘
             Django 서비스 레이어 — 상태머신 · 권한 · 룰 엔진 판정
```

| Blackboard 요소 | 이 프로젝트에서 |
|---|---|
| **Blackboard** (공유 문제 공간) | Postgres의 판정 스냅샷·룰 그래프·정산 상태 + Chroma의 문서 벡터 |
| **Knowledge Sources** (독립 전문가) | Rule / Risk Review / 증빙 추출 / Draft / 결정 사유 — 서로를 모른다 |
| **Control** (언제 누가 기여할지) | 상태머신과 룰 엔진. 에이전트가 아니라 **결정론적 코드**가 조율한다 |

**실제로 흑판을 통해 협업이 일어나는 예:**

- 증빙 추출 Agent가 첨부에서 뽑은 참석 인원이 **공유 사실 공간(EvalContext)에 올라가고**, 룰
  엔진이 그걸로 1인당 한도를 판정하며, Risk Review Agent는 **같은 스냅샷을 읽어** 신고 인원과의
  차이를 짚는다. 세 주체가 서로를 부르지 않고 같은 사실 위에서 일한다.
- Rule Agent가 만든 `DRAFT` 그래프를 사람이 `ACTIVE`로 올리면 **그 다음 판정부터 룰 엔진의 동작이
  바뀐다.** 한 에이전트의 산출물이 다른 구성요소의 행동을 바꾸는 것 — 이것이 협업이다.
- 규정 문서가 적재되면 Chroma에 들어가고, Rule Agent와 Risk Review Agent가 **각자 다른 목적으로**
  같은 코퍼스를 검색한다.

### 2.3 왜 직접 호출이 아니라 흑판인가 — 이게 오히려 이 도메인에 맞다

에이전트가 서로를 직접 부르는 방식(agent-to-agent 대화)은 **협업의 흔적이 대화 로그에만 남는다.**
정산은 감사 대상이라 "누가 어떤 근거로 무엇을 바꿨는가"가 **조회 가능한 데이터**로 남아야 한다.
흑판 방식은 모든 기여가 테이블의 행으로 남고, 판정 시점 스냅샷이 그대로 저장돼 재현된다.

**자율성을 통제와 맞바꾼 것이 아니라, 협업의 매개를 대화에서 기록으로 바꾼 것이다.**

## 3. 무엇을 더하면 논쟁이 끝나는가 — Risk Review Agent 고도화

비용 대비 효과가 가장 큰 지점이다. 넷 다 기존 구조를 건드리지 않는다.

### ① 스스로 멈추고 사람에게 넘긴다 (자율 종결 판단)

지금은 무조건 판정을 낸다. 근거를 못 찾아도 낸다.
→ **"근거 불충분"을 정식 산출로 추가**한다. 검색을 N회 돌고도 인용 가능한 조항이 없으면
`INSUFFICIENT_EVIDENCE`로 종결하고, 무엇이 없었는지를 남긴다.

**에이전트다움의 핵심은 "할 수 있다"가 아니라 "못 하겠다고 말할 수 있다"이다.**

### ② 다른 에이전트에게 일을 남긴다 (에이전트 간 통신)

검토 중 "이 조항에 해당하는 ACTIVE 룰이 없다"를 알아내도 지금은 그 발견이 사라진다.
→ **흑판에 `RuleGap` 노트를 쓴다**: `{조항, 왜 필요한가, 대상 정산 id}`.
Rule Agent가 다음 실행 때 이 노트를 읽어 룰 초안 후보로 삼는다.

**Risk가 발견하고 Rule이 만든다** — 서로를 모른 채 흑판으로 협업하는 완결된 사례가 생긴다.

### ③ 무엇을 더 볼지 스스로 고른다 (도구 확장 + 계획)

지금 2차가 쓰는 툴은 둘. MCP 서버에는 12개가 있다.
→ `classify_merchant`(업종 재판정) · `fetch_historical_tx`(과거 이력) · `build_rule_context`를 열고,
**"이 건을 판단하려면 무엇을 더 봐야 하는가"를 먼저 계획하게** 한다.
`classify_merchant`는 Draft Agent에만 연결돼 있어 어차피 연동이 필요한 항목이다.

### ④ 자기 판단과 사람 결정의 차이를 되읽는다 (메모리)

`case_history`는 이미 **"사람이 AI와 다르게 판단한 것"만** 적재한다.
→ Risk Review가 판정 전에 **자기가 과거에 틀렸던 유사 건을 먼저 검색**하게 한다.
학습은 아니지만 **경험을 참조하는 루프**가 생긴다.

> 넷을 더하면 다섯 기준이 모두 성립한다. **②가 특히 중요하다 — 에이전트 간 협업의 사례가
> 하나 완결되기 때문이다.**

## 4. 향후 발전 계획 — 스키마 제약을 에이전트로 푼다

### 4.1 지금의 한계

룰 엔진의 안정성을 위해 **판정에 쓰이는 사실을 고정 스키마로 못 박았다.**

- `EvalContext` — **56개 경로**(v6, 실측). 타입·설명·enum이 코드에 선언돼 있다.
- DSL — 연산자 화이트리스트. 룰 조건은 이 56개 경로만 참조할 수 있고, 없는 경로를 쓴 그래프는
  `ACTIVE` 승격이 거부된다.

**얻은 것**: 판정 재현, 오탈자 차단, 미해소 사실 자동 감지(모르는 값이 판정에 닿으면 검토로 강등).
**잃은 것**: **새 사실 하나를 늘리려면 코드 수정과 재배포가 필요하다.**
"우리 회사는 협력사 동반 여부로 한도가 갈린다"는 고객이 오면 개발이 나가야 한다.
확장성·유연성이 구조적으로 막혀 있다.

### 4.2 접근 — 자유 스키마는 늘리되, 판정 경계는 그대로 둔다

> **유연성은 자유 문서 저장소에서 얻고, 안정성은 "판정은 승격된 것만 본다"는 경계에서 지킨다.**

핵심은 **경계를 하나 긋는 것**이다. 문서 저장소는 무엇이든 담고, 판정은 승인된 것만 본다.
자유도가 판정 재현성을 갉아먹지 않는 이유가 여기에 있다.

```
  [자유 영역 — 에이전트가 관리]                │  [정본 영역 — 판정이 참조]
                                                │
  fact_documents (NoSQL)                        │   EvalContext 정본 스키마
   · 정산 건별 자유 스키마 JSON                 │    · 승격된 경로만
   · 값마다 봉투(출처·신뢰도·시각·근거)        │    · 타입·enum 확정
            │                                   │            ▲
            ▼                                   │            │
  Context Curator Agent ──[승격 제안]──▶  사람 승인 ─────────┘
   · 새 경로 발견 · 표기 정규화 · 중복 병합     │
                                                │
  ◀── 조회 툴 (fact_query / fact_schema) ────   │  ◀── 룰 엔진 (순회 중 외부 I/O 0)
```

### 4.3 구성요소

**(1) 사실 문서 저장소 `fact_documents` (NoSQL)**

정산 건 하나당 문서 하나. 스키마 제약 없음. 값은 **봉투(envelope)**로 감싼다.

```json
{
  "settlement_id": 1042,
  "facts": {
    "partner.company_name": {
      "value": "○○산업", "source": "EXTRACT", "confidence": 0.83,
      "observed_at": "2026-08-25T10:12:00", "evidence_ref": "attachment:88#p2"
    },
    "participants.verified_participant_count": {
      "value": 6, "source": "EXTRACT", "confidence": 0.91, "evidence_ref": "attachment:88#p1"
    }
  }
}
```

지금 `FactMerger`가 코드에 갖고 있는 우선순위(추출 < 사용자 입력 < SoR)를 **데이터로 승격**한
것이다. 출처·신뢰도가 값에 붙어 있으므로 충돌이 나도 어느 쪽을 왜 택했는지가 남는다.

**(2) Context Curator Agent — 스키마를 관리하는 에이전트**

- 새 문서가 들어오면 **아직 정본에 없는 경로**를 찾는다.
- 표기를 정규화하고 중복을 병합한다(`협력사명` · `partner_name` · `partner.company_name` → 하나).
- **관측 빈도와 신뢰도가 기준을 넘으면 정본 승격을 제안**한다 — 경로·타입·설명·enum 후보까지.
- **자동 승격은 하지 않는다.** 사람이 승인한다.

  → 지금 별표 승인(`PolicyTableProposal`)이 하는 일을 **사실 전반으로 확장**한 것이다.
    그 흐름은 이미 화면·검증·감사 로그까지 돌고 있어 패턴이 검증돼 있다.

**(3) 조회 툴 (스키마 무관, read-only)**

| 툴 | 하는 일 |
|---|---|
| `fact_query(settlement_id, path_glob)` | 봉투째 반환 — 값만이 아니라 출처·신뢰도까지 |
| `fact_schema(scope)` | 이 회사에서 실제로 관측된 경로 카탈로그 + 관측 빈도 |
| `fact_history(path, period)` | 특정 사실의 시계열 — 한도 근접·이상 패턴 탐지용 |

에이전트는 **툴로만 접근한다.** 지금 지키는 원칙("LLM/Tool의 Postgres 직접 SQL 금지")을 그대로
가져간다. 자유 스키마여도 **접근 경로가 좁으면 통제할 수 있다.**

**(4) 공유 컨텍스트 공간 — 흑판을 1급 객체로**

지금 흑판은 **암묵적**이다(여러 테이블에 흩어져 있다). 이를 명시적 객체로 만든다.

```
workspace(settlement_id)
  ├─ notes[]      : {author_agent, topic, payload, created_at, ttl}
  ├─ questions[]  : {asked_by, question, answered_by?, answer?}
  └─ unresolved[] : {path, why, blocking?}
```

- `post_note(topic, payload)` / `read_notes(topic)` — **직접 호출이 아니라 흑판에 남기는 방식을
  유지한다.** 감사 추적을 잃지 않기 위해서다(§2.3).
- §3-②의 `RuleGap` 노트가 여기 들어간다. Risk가 쓰고 Rule이 읽는다.
- `questions[]`는 에이전트가 **사람에게** 묻는 자리이기도 하다 — "이 건, 협력사 동반이 맞습니까?"

**(5) 안정성을 지키는 세 장치**

1. **판정 경로는 정본만 본다.** 자유 문서는 제안·설명·보고서에만 쓰인다. 승격되지 않은 사실이
   판정을 바꾸는 일은 구조적으로 불가능하다.
2. **승격에 사람 승인 게이트.** 별표 승인과 같은 흐름 — 정합 검사, 시행일, 감사 로그.
3. **판정 시점 스냅샷을 그대로 저장.** 스키마가 나중에 바뀌어도 과거 판정은 그대로 재현된다.
   지금 `rule_hits.eval_context`가 하는 일과 동일하다.

### 4.4 이 계획이 대주제에 답하는 방식

| 지금 | 이후 |
|---|---|
| 스키마는 개발자가 코드로 늘린다 | **Curator Agent가 관측하고 제안하고, 사람이 승인한다** |
| 에이전트가 서로의 발견을 모른다 | **workspace 노트로 남기고 읽는다 — 비동기 협업** |
| 새 고객사 = 재배포 | 새 고객사 = **문서를 올리면 사실·룰·한도가 자라난다** |

**"에이전트가 시스템의 스키마를 함께 키운다"** — 자율성을 판정이 아니라 **스키마 진화**에 쓰는
설계다. 판정 재현성은 그대로 두면서 확장성만 에이전트에게 넘긴다.

## 5. 정리

1. **완전 자율이 아닌 것은 회피가 아니라 도메인이 강제한 설계 결정이다.**
   재현 · 통제 · 추적 · 사람 확정 — 넷 중 하나도 포기할 수 없는 업무였다.
2. **현 구조는 Blackboard 기반 멀티에이전트 협업이다.** 에이전트는 서로를 직접 부르는 대신
   공유 사실 공간에 쓰고 읽으며, 조율은 결정론적 통제자가 한다. Rule Agent는 자율 검색 ·
   자기 검증 · 상태 기억 · 대화형 수정을 모두 갖춘 명백한 에이전트다.
3. **Risk Review Agent는 넷을 더하면 논쟁이 끝난다.** 자율 종결 판단 · 흑판을 통한 에이전트 간
   통신 · 도구 확장과 계획 · 경험 참조. 특히 두 번째가 **협업의 완결 사례**를 만든다.
4. **발전 방향은 자율성을 판정이 아니라 스키마 진화에 쓰는 것이다.** 자유 문서 저장소 +
   Curator Agent + 조회 툴 + 공유 작업 공간. 판정은 승격된 정본만 보므로 안정성은 유지된다.

> **우선순위**: §3은 기존 구조를 건드리지 않고도 주장을 성립시킨다 — 여기부터 한다.
> §4는 설계로 제시하고 구현은 다음 단계로 남긴다.
