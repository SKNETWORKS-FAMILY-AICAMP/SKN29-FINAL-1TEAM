## 1. 아키텍처 개요

### 1.1 설계 원칙

- **관심사 분리**: 트랜잭션/도메인(Django)과 AI 오케스트레이션(FastAPI)을 물리적으로 분리한다.
- **System of Record는 Postgres 하나**: 모든 확정 데이터의 단일 진실 원천(SoT)은 Django가 관리하는 PostgreSQL이다. AI는 제안(초안·스코어·근거)만 생성하고, 확정은 Django 도메인을 통해서만 이뤄진다.
- **Agent = LLM + Tools(MCP)**: 모든 Agent는 단일 FastMCP 서버로 노출된 표준 도구를 통해서만 데이터에 접근한다. (LLM의 직접 DB 접근 금지 → 감사·권한 일원화)
- **MVP는 동기 REST**: 별도 메시지 큐(Redis 등) 없이 동기 REST 호출로 처리한다. 문서 임베딩·모델 학습 등 무거운 작업은 관리자 트리거 배치(온디맨드)로 단순화한다.
- **사람 확정 원칙**: 자동 통과 건도 최종 확정은 사람이 수행한다. 시스템은 상태만 `승인대기`로 전이시킨다.

### 1.3 컴포넌트 책임 분담 (RACI 요약)

| 컴포넌트 | 책임 | 하지 않는 것 |
|---|---|---|
| **React** | 화면, 상태표시, 사용자 액션 | 비즈니스 규칙 판단 |
| **Django(DRF)** | 인증·RBAC, 도메인 CRUD, 정산 상태머신, ERP 전표(안), Postgres 소유 | LLM 직접 호출·ML 추론 |
| **FastAPI** | Agent 오케스트레이션, LLM/ML 호출, 비동기 파이프라인 | 확정 데이터 소유(제안만 반환) |
| **FastMCP** | Agent용 표준 도구 서버(검색·조회·Rule실행·OCR) | 자체 상태 저장(무상태 지향) |
| **Chroma** | 규정/사례 임베딩 저장·유사도 검색(RAG) | 트랜잭션 데이터 저장 |
| **PostgreSQL** | 모든 확정 데이터 SoT | 벡터 검색 |

> **왜 Django + FastAPI 둘 다?**
> Django는 인증·ORM·Admin·상태머신 등 정형 도메인에 강하고, FastAPI는 async·LLM/ML 서빙 등 AI 워크로드에 강하다. Django를 SoR로 고정하고 AI 작업만 FastAPI로 위임하면 책임 경계와 감사 지점이 명확해진다.

## 2. 기술 스택 상세

| 계층 | 기술 | 용도 | 선정 이유 |
|---|---|---|---|
| Frontend | React + TS + React Router, `fetch`/axios 직접 호출 | SPA UI, 역할별 대시보드 | 상태관리·차트는 별도 라이브러리를 두지 않는다 — 서버 상태는 Context(`SettlementsContext`/`AuthContext`/`RoleContext`)로 충분한 규모이고, 대시보드 시각화는 CSS/SVG 커스텀 컴포넌트로 직접 그린다 |
| Core API | Django 5 + DRF | 도메인/인증/상태머신/Admin | ORM·마이그레이션·RBAC·Admin 성숙 |
| AI API | FastAPI | Agent 오케스트레이션·ML 서빙 | async, pydantic, LLM 생태계 |
| Agent Tools | FastMCP (단일 서버) | 3개 Agent 공용 도구 노출 | MCP 표준화, tool 재사용/감사 |
| LLM/Vision | OpenAI (`gpt-4o-mini`/`gpt-5-mini` 등, 프로필로 관리) | 분류·근거 생성 + 영수증·증빙문서 이미지 직접 판독 | 별도 OCR 엔진 불필요(비전으로 대체). 모델명은 `app/config.py` 한 곳에서만 정하고 호출부는 `fast`/`heavy` 역할로만 부른다(§4.3) |
| Vector DB | Chroma | 규정/FAQ/사례 임베딩·RAG 검색 | 경량, 빠른 프로토타이핑 |
| RDB | PostgreSQL | 트랜잭션 SoT, 이력/라벨, 가맹점 업종 캐시 | JSONB·인덱싱·신뢰성 |
| 외부 API | 카카오 로컬(지도) API | 가맹점 업종(업태) 판별 → 비용분류 보조 | 자체 규정 외 가맹점 메타데이터 확보(캐시화) |

> **MVP 단순화**: 별도 OCR 엔진·메시지 큐(Redis/Celery)는 두지 않는다. 영수증은 OpenAI 비전 모델이 이미지에서 바로 필드 추출하고, 처리 흐름은 동기 REST로 통일한다.

| ERP | `erp_vouchers` | settlement_id, voucher_payload(JSONB), status(안/확정) |

| 룰 시뮬레이션 실행/결과 | `rule_simulation_runs`, `rule_simulation_results` | graph_version, 매칭건수·오탐율·검토감소량, 서술 보고서 |

`rule_hits`는 decision만 기록하고 별도의 확신도(confidence) 컬럼은 두지 않는다 — decision이 룰 노드 `action`에 직접 지정되는 결정론적 방식이기 때문이다. `risk_reviews.anomaly_score`(이상탐지 모델 출력)와 `merchant_categories.confidence`(업종 판별 신뢰도)는 이와 무관한 별개 파이프라인의 산출물로, 그대로 유지한다.

#### 3.1a 인가 모델 — 기능 단위(Capability) RBAC

권한은 역할(Role) 자체가 아니라 기능 단위 능력(Capability)으로 판정한다. 역할은 라벨·기본값 산정·화면 rank용으로만 남고, 실제 인가 단위는 아래 6개 Capability다.

| Capability | 게이트하는 기능 | 서버 강제 지점 |
|---|---|---|
| `team_aggregate` | 팀 취합(팀원 건 보완요청/반려/제출) | `POST /settlements/{id}/team-decision/` |
| `accounting_review` | 회계 검토(승인/보완/반려)·확정 | `POST /settlements/{id}/review/`·`/confirm/` |
| `rule_view` | 룰 콘솔 열람 | (프론트 메뉴 게이트 — 조회 API는 개방) |
| `rule_activate` | 룰 버전/그래프 생성·ACTIVE 전환·롤백 | `POST /rules/{id}/versions/`·`/rules/drafts/`·`/activate/`·`/rollback/` |
| `governance_view` | 거버넌스(임원) 대시보드 열람 | `GET /dashboard/EXECUTIVE/` |
| `ai_lab` | AI-LAB(AI 기능 독립 실행) 사용 | `/api/ai-lab/{subpath}` 프록시 |

- 유효 능력 = 역할 기본값(`ROLE_DEFAULT_CAPABILITIES`) ∪ 개인 추가부여(`users.extra_capabilities`). 슈퍼유저는 전체.
  - 역할 기본: EMPLOYEE=∅ · TEAM_LEAD=`team_aggregate` · ACCOUNTANT=`accounting_review`+`rule_view` · ACCOUNTANT_LEAD=`accounting_review`+`rule_view`+`rule_activate`+`ai_lab` · EXECUTIVE=`governance_view`.
  - 룰 콘솔은 회계 공통 열람(`rule_view`) / ACTIVE 전환만 회계팀장(`rule_activate`)으로 분리.
  - AI-LAB은 프롬프트·모델 내부가 그대로 보이고 LLM 호출 비용이 나가므로 기본은 회계팀장만 갖는다. 다른 사람에게 필요하면 admin에서 개별 부여한다.
- 구현: `domain.common.permissions.HasCapability` 파생 DRF Permission(`CanTeamAggregate`/`CanAccountingReview`/`CanViewRule`/`CanActivateRule`/`CanViewGovernance`/`CanUseAiLab`), `User.has_capability()`. `/api/me`·로그인 응답에 `capabilities` 포함(프론트 게이트용).
- 관리자 페이지: Django admin User 화면에서 `extra_capabilities`를 체크박스로 부여/회수, 유효 능력을 읽기전용 표시(`accounts/admin.py`).
- 프론트 화면 게이트(Sidebar 메뉴·팀 취합·검토·룰 활성)는 `useCan()` 훅으로 `capabilities`를 소비한다.

### 3.2 Chroma — 벡터 컬렉션(개요)

| 컬렉션 | 소스 | 용도 | 메타데이터 |
|---|---|---|---|
| `policy_docs` | 사내 회계 규정·매뉴얼·FAQ | Rule 생성 / Risk 근거 RAG | category, version, effective_date |
| `case_history` | 과거 승인·반려 사례 | 유사 사례 검색 | decision, category, amount_band |
| `tax_refs` | 세법·회계 기준 | 세무 근거 RAG | source, article |
| `org_docs` | 조직도·직급체계 등 도해 문서 | 화면·실험 참조 | doc_kind, title |

- **판정 경로가 인용할 수 있는 컬렉션은 앞 3종(`JUDGEMENT_COLLECTIONS`)뿐이다.** `org_docs`는 조직 구조를 담을 뿐 규범이 아니므로 Rule·Risk 검색 대상에서 제외한다 — 조직도를 근거로 든 판정은 "규정에 그렇게 적혀 있다"가 아니기 때문이다.
- 임베딩은 문서 업로드/갱신 시 비동기로 청킹→임베딩→upsert. Chroma에는 원문 조각 + 메타데이터만, 트랜잭션 데이터는 절대 넣지 않는다.

### 3.3 정산 상태 머신 (Django 관리)

4단계: **① 개인 보유 → ② 팀 취합 → ③ 회계 제출·룰엔진 → ④ 회계 검토·확정**
```
[① 개인]  DRAFT
   └─(팀에 올림)─► [② 팀] TEAM_COLLECTING
         ├─(팀 보완)─► TEAM_RETURNED ─(개인 수정)─► DRAFT
         ├─(팀 반려)─► TEAM_REJECTED ─(개인 수정)─► DRAFT
         └─(팀 제출)─► [③ 회계] SUBMITTED ─► RPA_JUDGED (룰엔진 분류)
               ├─(auto-pass)───► PENDING_CONFIRM ─(사람 확정)─► CONFIRMED → ERP_VOUCHER_DRAFTED
               ├─(auto-reject)─► RETURNED ─(재제출)─► SUBMITTED
               └─(needs-review)► IN_REVIEW ─► PENDING_CONFIRM / RETURNED / REJECT(최종)
```

- **상태 enum**(`settlements.status`): `DRAFT` · `TEAM_COLLECTING` · `TEAM_RETURNED` · `TEAM_REJECTED` · `SUBMITTED` · `RPA_JUDGED` · `PENDING_CONFIRM` · `RETURNED` · `IN_REVIEW` · `REJECT` · `CONFIRMED` · `ERP_VOUCHER_DRAFTED`
- 팀 수준(`TEAM_*`, 팀장)과 회계 수준(`RETURNED`/`REJECT`, 회계 담당자) 보완·반려는 별개 상태.
- 상태 전이는 Django 서비스 레이어에서만 수행, 모든 전이는 `settlement_events` + `audit_logs`에 기록.
- **제출 = 2단계 분리**: 개인 "올림"(`DRAFT→TEAM_COLLECTING`)과 팀 "제출"(`TEAM_COLLECTING→SUBMITTED`)은 별개 액션. 1인 팀(영업사원·임원 개인)도 동일 경로(개인 보유→팀 취합→제출)를 탄다 — 개인/조직 무관 일관 제출 경험.
- **계정과목=비용분류 정합**: 룰 `scope`는 `Category`를 SoT로 하며, 정식 회계 계정과목 테이블은 두지 않는다(세무는 RAG). 룰 명세서 과목명↔`Category` 매핑은 `policies/scope.normalize_scope()`가 제공한다: 기업업무추진비→접대. **회식은 식대와 별개의 독립 scope(회식)로 유지**하며, 두 카테고리를 흡수·통합하지 않는다.
- **규정 임계값(policy) 도메인**: 한도·기준액은 2층 구조로 관리한다 — 저장층(`policy_tables`, 별표 원본을 담는 자유 JSON payload)과 소비층(`ctx.policy.*`, DSL이 참조하는 고정 카탈로그). 조립기(`build_rule_context`)가 저장층을 소비층 스칼라로 선해소한다.

## 4. Agent 아키텍처 & Flow

### 4.0 공통: Agent 실행 모델

```
Django(도메인 이벤트) ──REST──► FastAPI(Agent Orchestrator)
                                    │
                                    ├─ LLM 호출 (프롬프트 + tool schema)
                                    ├─ FastMCP tool call (검색/조회/Rule/OCR)
                                    ├─ ML Serving (이상탐지 추론)
                                    └─ 결과(제안) ──REST──► Django (저장/상태전이)
```

모든 Agent 출력은 "제안"이며 Postgres에 결과 테이블로 적재되지만 확정 상태로 만들지 않는다. MVP는 동기 호출: Django가 FastAPI를 REST로 호출하고 응답을 그대로 받아 저장한다(별도 Job 큐 없음). LLM/도구 호출 trace는 로그로 남겨 감사·비용추적한다.

---

### 4.1 ① 초안 작성 Agent (Draft Agent)

**목적**: 정산 건의 분류·지출목적 초안을 자동 완성하고, 제출 전 예상 판정을 미리 보여준다.

**핵심 규율(§CLAUDE.md·`_context/draft-agent-v2.md`)**: **AI는 판정을 예측하지 않는다.** 「지금 제출하면 보완요청될까」는 결정론적 룰엔진이 이미 답을 갖고 있다(`orchestrator.judge(record=False)`로 dry-run). 룰 그래프를 LLM에 주고 순회를 흉내내게 하면 틀리고, 틀려도 티가 안 나며, 사용자에겐 "AI가 통과라 했는데 반려됨"이 된다. **엔진이 결정하고 모델은 사람 말로 옮긴다.** 모델이 낼 수 없어야 하는 값(업종·판정 결과 등)은 지시가 아니라 **출력 스키마에서 뺀다** — 조회값을 그대로 돌려주므로 지어낼 여지가 없다.

**Flow (정산 건 기준 — 정식 경로)**
```
1. 거래 수집(ERP, 멱등) 또는 신규 등록 ──► transactions/settlements 적재 (Django, 저장 먼저 → 비전 → 초안)
2. 영수증·증빙 업로드 ──► 업로드가 곧 판독 트리거 (read_receipt/read_evidence_document)
3. GET /api/internal/settlement-draft-context/{id}/ (Django, `draft_context.py`가 조립)
     ├─ 기본 내역(ERP 수집·영수증 비전·카드 원장)
     ├─ classify_merchant(가맹점)                 업종 판별(캐시→카카오→LLM 재분류, §7-1)
     ├─ 첨부 추출 사실 + EvalContext 스냅샷
     └─ **엔진 판정 미리보기**(judge dry-run)      REJECT/RETURN/REVIEW 사유를 사람 말로 옮길 재료
4. Draft Agent 실행 (FastAPI `/agent/draft/settlement`)
     ├─ core가 조립한 사실을 문장으로 편다(`draft_facts.py`) — 판정을 다시 계산하지 않는다
     ├─ LLM: 분류(category)·지출목적(purpose)만 생성. Structured Output(strict)으로 6개 분류 밖 값 자체가 나올 수 없다
     └─ 산출: {category, purpose, reasoning, notices(사유를 사람 말로), judgement(엔진 dry-run 그대로), returnContext}
5. 제출 직전 `/agent/draft/polish` — 지출목적 문체만 다듬는다. 서버가 사실이 늘었는지 기계적으로 대조해 지어낸 내용을 막는다
6. React: 초안 표시 → 사용자 보정 → 팀 취합(TEAM_COLLECTING) → 팀장 제출 → SUBMITTED
```

**입력**: settlement_id, instruction(수정 지시, 선택)
**출력**: category, purpose, reasoning(설명), notices(판정 사유 안내), judgement(엔진 dry-run 판정), returnContext(재작성 맥락)
**사용**: OpenAI(`gpt-4o-mini`, 구조화 출력), FastMCP `classify_merchant`, Django 조립 API(`get_draft_context`)
**분기**: 카드구분 공용→실사용자 지정 요청 / 후정산→증빙 필수 플래그
**실패 처리**: 사실 조회 실패는 감추지 않는다(200으로 덮지 않고 에러를 올린다) — 사실 없이 쓴 초안은 실패보다 나쁘다. LLM 호출만 실패하면 분류·목적을 비워 두되 판정 사유 안내는 그대로 보여준다(등록된 설명을 펴는 것이지 지어내는 게 아니므로)

> **폼 기반 옛 경로**(`/agent/draft`, `run`/`revise`)도 코드에 남아 있으나 정산 건과 분리된 레거시 경로다 — 위 흐름이 정식 경로다.

### 4.2 ② Rule Agent (생성 / 검증 / 적용)

**목적**: 규정을 실행가능 Rule로 만들고(생성), 과거 데이터로 검증하고(검증), 실거래를 1차 자동 판정(적용).

#### 룰 도메인 모델 (그래프/트리)
- **룰 그래프(RuleGraph) = 최종 상태 도메인**: 단건 룰(노드)들이 트리/DAG로 조립된 배포 단위. ACTIVE·버전관리·시뮬레이션·롤백은 모두 이 그래프 단위로 이뤄진다(개별 노드가 아님).
- **버전 저장 방식**: `rule_graphs` 한 행이 한 버전이고 같은 `family_key`가 버전 계열을 묶는다. 기존 그래프 수정은 원본을 복제한 `version+1` DRAFT 행을 만들어 현재 ACTIVE 버전과 병행한다. 새 그래프는 v1로 생성하며 scope는 `GLOBAL` 또는 정산 `Category` 실제 값만 허용한다. scope당 ACTIVE 1개를 조건부 UNIQUE 제약으로 강제한다.
- **룰(노드)**: `condition + action + next_routings`. `next_routings`는 평가 결과(MATCH/NO_MATCH/PASS/REJECT/REVIEW)별로 다음에 평가할 노드 방향(우선순위 포함).
- **엔진**: ACTIVE 그래프의 엔트리 노드에서 시작해 `next_routings`를 따라 단말 노드까지 결정론적 순회 → 최종 결정. 순회 경로는 `rule_hits.path`에 기록(감사/디버깅).

```
룰 그래프 예 (트리 순회)
        [entry] 금액 > 분류한도?
          │ MATCH               │ NO_MATCH
     [접대 세부 룰]          [분류 = 식대?]
       │ REJECT                 │ MATCH → [1인 한도 초과?] → PASS / REVIEW
     RETURNED                   │ NO_MATCH → REVIEW(Risk 이관)
```

#### Rule 콘솔 화면 구조 — 그래프 단위

Rule 콘솔은 그래프 중심으로 구성한다:
- **룰 그래프 보기/초안 편집**: 실제 그래프를 scope 단위로 묶고 각 버전을 Active/수정중 상태로 표시한다. Active v1에서 노드 추가 또는 세부 수정을 시작하면 같은 `family_key`의 v2 DRAFT를 복제해 편집하며, 실행 콘텐츠가 원본과 다시 같아지면 작업본을 폐기하고 v1 Active 표현으로 복귀한다. 전체/수정건 필터, 노드 즉시 추가/삭제를 지원한다. 그래프 삭제는 평상시 선택 UI를 숨기고 상단 삭제 모드 진입 시 각 행의 노드 추가를 삭제 액션으로 교체한다. 확인창 후 비ACTIVE 버전만 삭제하며 ACTIVE 클릭 시 삭제 불가 안내를 표시한다. 노드에는 초안/대기/검증완료/활성 상태를 먼저 표시한다. 상세는 제목·설명·DSL에서 프론트가 동적으로 생성한 다중 조건 자연어 표현("이 Rule이 하는 일")·액션(decision/severity/flag/note/approver)·평가 우선순위·카드형 라우팅과 하단 full-width 추가 액션·생성 이유/관련조항 링크로 구성한다. 저장 요청은 매 입력마다 보내지 않고 필드 이탈·버튼 작업·노드/화면 전환 시 수행하며, 장기 편집 보호를 위해 변경분을 1분 주기로 저장한다. 초안 완료 시 검증 대기로 전환하고 다시 초안으로 되돌릴 수 있다. 초안 작성은 `rule_view`, ACTIVE/롤백은 `rule_activate` 권한으로 분리한다.
- **신규 룰 생성**: 모달에서 ① 기존 룰그래프 선택 → 현재 버전을 복제한 다음 버전(v2, v3…) DRAFT에 빈 노드 추가, 또는 ② 실제 비용분류 scope를 선택해 빈 v1 그래프 생성 → 빈 룰 노드가 상세에 올라옴 → 세부설정.
- **시뮬레이션**: 검증할 그래프를 선택해 과거 이력으로 시뮬(매칭/오탐율/검토감소·분류차이·Agent 보고서) → 그래프를 승인대기로 전환.
- **Active 그래프**: 그래프별 버전 이력·승인대기 승인(ACTIVE 전환)·롤백. 전환/롤백은 `rule_activate` 권한(§3.1a).

#### (a) 생성 Flow
```
관리자: 규정문서 업로드 ─► 비동기 임베딩 ─► Chroma(policy_docs)
Rule Agent(생성):
  ├─ FastMCP:search_policy(query)  RAG로 규칙화 가능 조항 추출
  ├─ LLM: 단건 룰(노드) 초안 생성 (condition DSL + action) + next_routings 제안
  └─ 노드들을 룰 그래프(트리)로 조립 ─► rule_graphs(status=DRAFT) + rules(노드) + rule_routings 저장
```

#### (b) 검증 Flow (적용 전 필수) — 그래프 단위
```
Rule Agent(검증):
  ├─ FastMCP:fetch_historical_tx(기간, 필터)   과거 거래 로드
  ├─ Rule Engine: 후보 그래프를 엔트리부터 순회하며 과거 거래에 시뮬레이션
  ├─ 지표 산출: 매칭건수 / 오탐율 / 예상 검토감소량 (+ 노드별 커버리지)
  └─ rule_graph_versions.snapshot + sim_result 저장 ─► 관리자 검토·승인 화면
관리자 승인 시에만 해당 그래프 버전이 ACTIVE(is_active=true) 전이 — 직전 ACTIVE 버전은 ARCHIVED
(롤백: 이전 승인 버전을 즉시 ACTIVE로 복원. 동시에 ACTIVE인 그래프 버전은 스코프당 하나)
```

#### (c) 적용 Flow (RPA 1차 판정) — 3단 파이프라인
```
① 컨텍스트 조립 (I/O · FastAPI 오케스트레이션)
   FastMCP:build_rule_context(tx_id) → EvalContext(facts JSON) 스냅샷
     └ tx·card·user(직책/근무시간)·evidence·history(이력집계)·policy·merchant(업종)·derived(심야/영업일경과)
② 그래프 선택 (필수 게이트 → 과목별)
   ⓐ 공통/필수 게이트 그래프(scope=GLOBAL): 금지업종·증빙·사전승인·기한 → 확실 REJECT/REVIEW 우선
   └ 통과 시 ⓑ 계정과목별 그래프(scope = tx.category, 예: 접대/회식/식대/출장…): 과목 특화 세부룰
③ 결정론적 순회 (순수함수 · 외부 I/O 없음)
   run_rule_engine(eval_context, graph): 엔트리 → condition(DSL) 평가 → next_routings → 단말 결정
     ├─ 단말 노드 action.decision == PASS    ─► PENDING_CONFIRM (상세검토 생략, 사람 최종확정 대기)
     ├─ 단말 노드 action.decision == REJECT  ─► RETURNED (보완요청 자동 안내)
     └─ 미매칭/저신뢰(REVIEW)               ─► Risk Review Agent로 이관
rule_hits(path, eval_context 스냅샷, graph_version, decision, flags) 기록
```
> 엔진은 EvalContext만 참조한다(외부 I/O 0). 모든 데이터 접근은 ① 조립 단계에서만 수행 → 엔진은 순수함수 → 재실행/시뮬/감사 결과 동일(재현성). ①은 유연(무엇이든 조립), ③은 엄격(결정론).

> **구현 위치**: ①~③과 `rule_hits` 기록·상태 전이는 **Django 안에서 한 트랜잭션**으로 돈다(`policies/orchestrator.py` + `settlements/services.judge`). 적용 단계는 LLM이 개입하지 않고(FR-RA-06) 관계형 데이터만 쓰므로 AI가 중간에서 할 일이 없고, 판정·로그·전이가 갈라지면 "판정은 남았는데 상태는 안 바뀐" 상태가 생긴다. FastMCP의 `run_rule_engine` tool은 Agent가 같은 판정을 조회할 수 있게 하는 **위임 창구**다. 판정 트리거는 제출(`POST /api/settlements/submit/`)이며, 재판정은 `POST /api/settlements/{id}/judge/`.
>
> 결정 → 상태 매핑에서 **엔진은 `REJECT` 상태를 만들지 않는다**: 노드 `action.decision`이 `REJECT`여도 정산 상태는 `RETURNED`다(위 표대로). `REJECT`는 재제출 불가 단말이라 규칙이 자동으로 내리면 되돌릴 수 없고, 최종반려는 회계 담당자의 검토(`review`)만 내릴 수 있다("사람 확정 원칙"). ACTIVE 그래프가 하나도 없으면 통과가 아니라 `IN_REVIEW`로 보낸다(플래그 `NO_ACTIVE_RULE_GRAPH`).

**입력**: 규정문서(생성), 과거거래(검증), 제출정산+EvalContext(적용)
**출력**: 룰 그래프(노드+라우팅) 초안, 그래프 단위 시뮬레이션 지표, 거래별 판정+순회 path
**사용 Tool**: `search_policy`(생성) · `fetch_historical_tx`(검증) · `build_rule_context`·`run_rule_engine`(적용)
**decision 결정 방식**: PASS/REJECT/RETURN/REVIEW는 노드 생성 시점에 `action.decision`으로 직접 지정되며, 판정 시점에 별도의 확신도 계산이나 임계치 비교를 거치지 않는다. severity(CRITICAL/HIGH/MEDIUM/LOW/INFO)와 decision의 매핑 규칙은 별도 시드 계획 문서를 따른다.
**중요**: Rule은 결정론적 엔진 실행이 원칙, LLM은 생성 단계에서만 사용(적용 단계는 재현성 확보). ACTIVE·버전관리·롤백은 룰 그래프(최종 상태 도메인) 단위.

#### (d) 룰 평가 컨텍스트(EvalContext) & 조건 DSL

**EvalContext**(스키마 v6) = 판정 시점에 조립된 facts 스냅샷. 조건은 이 경로만 참조하며, `rule_hits.eval_context`에 저장되어 재현·감사의 근거가 된다. **16개 네임스페이스 · 54필드**:

| 네임스페이스 | 필드 |
|---|---|
| `tx` (5) | amount · per_person_amount · verified_per_person_amount · payment_time · payment_method |
| `card` (3) | card_type · actual_user_recorded · actual_user_is_spender |
| `user` (4) | **job_title · job_title_rank** · team · bu |
| `merchant` (4) | merchant_type · merchant_info_resolved · industry_confidence · forbidden |
| `category` (3) | value · confidence · item_type |
| `evidence` (6) | has_valid_receipt · expense_purpose_missing · has_meeting_minutes · has_participant_list · has_trip_plan · has_contract |
| `approval` (1) | pre_approval_obtained |
| `participants` (5) | participant_count · **verified_**participant_count · external_participant_count · **verified_**external_count · has_kickback_law_target |
| `trip` (3) | trip_type · region_grade · lodging_amount_per_night |
| `dining` (2) | includes_alcohol · is_secondary_venue |
| `history` (3) | same_vendor_count · daily_cumulative_amount · monthly_cumulative_amount |
| `policy` (8) | preapproval_threshold · position_daily/monthly_limit · kickback_limit · lodging_limit · evidence_threshold · dining_per_person_limit · settlement_deadline_days |
| `derived` (2) | business_days_since_expense · is_weekend |
| `tables` · `conflicts` | 감사용 **동적** 섹션(고정 목록 없음) — 실제 사용한 별표 원본, 같은 경로에 다른 값이 도착했을 때의 채택/폐기 기록. DSL은 참조하지 않는다 |
| `meta` (5) | tx_id · settlement_id · schema_version · builder_version · built_at |

**설계 규율**

- **결재권·한도의 축은 직책(`user.job_title`)이며 직급이 아니다.** 규정이 "결재 권한 및 법인카드 사용한도는 직책 기준으로 부여한다"고 못박고 별표1도 직급과 무관함을 명시한다 — 같은 '이사'라도 부서장 겸직이냐에 따라 한도가 갈리므로 직급으로는 정할 수 없다. `job_title_rank`(숫자 서열)를 함께 두는 이유는 "부서장 이상"을 이름 비교 없이 표현하기 위해서다(DSL은 스칼라 비교만 한다).
- **신고와 확인을 다른 필드로 가른다**: `participant_count`(화면 입력)와 `verified_participant_count`(문서 추출)는 별개다. 정확도 요구가 다른 판정이 같은 사실을 쓰면 안 된다.
- **필드명에 상수를 넣지 않는다.** `biz_days_over_7`·`*_3m`처럼 숫자가 이름에 박히면 규정 개정이 스키마 변경이 된다 — "무엇을 재는가"만 이름에, "얼마인가"는 `policy.*`에 둔다.
- **파생 불린을 두지 않고, 룰 조건에 상수를 허용한다.** 조립기가 `is_late_night`(22~06) 같은 판단 기준을 코드에 박아 불린으로 접어 주면 그 숫자를 바꾸려고 재배포해야 하고, 그 상수는 룰 콘솔에도 판정 스냅샷에도 안 보인다. 그래프가 `tx.payment_time >= "22:00"`으로 직접 비교한다. **예외 셋만 조립기가 접는데, 취향이 아니라 DSL의 구조적 한계다** — ① null 여부(미해소 가드가 값 평가 전에 강등해 `x == null`을 룰로 못 쓴다) ② 별표 선해소(DSL에 룩업 연산자가 없다) ③ 산술·날짜(연산자·요일 함수가 없다). 남기는 불린은 왜 예외인지를 필드 설명에 적는다.
- **접근 경로**: 관계형 = Django 내부 read API 경유, 업종 = `classify_merchant`, 별표 = `PolicyTable` 선해소, 파생 = 조립기 계산. 전부 ① 단계에서 스냅샷 → 엔진은 Postgres를 모른다(§5.1 원칙 유지).
- **미해소 가드**: 순회 경로에서 **실제로 참조된** 경로에 `None`이 있으면 판정을 신뢰할 수 없으므로 REVIEW로 강등하고 사유 플래그를 남긴다(`UNRESOLVED_POLICY_VAR` = 별표 미적재 → 표를 채우면 해결 / `UNRESOLVED_FACT` = SoR에 원천이 없음 → 입력 화면·모델이 필요). 이 가드가 없으면 미조립 필드를 참조하는 룰이 **에러 없이 미발동**하고 판정은 통과로 보인다.

**조건 DSL** = 임의 코드 금지, JSON-Logic류 화이트리스트 연산자(`and/or/not · ==/!=/>,>=,<,<= · in · var · is_null`). `var`는 EvalContext 경로 접근.
```jsonc
// 접대비 3만 초과 + 적격증빙 없음 → REVIEW
{ "and": [ {"==":[{"var":"category.value"},"접대"]},
           {">" :[{"var":"tx.amount"},{"var":"policy.evidence_threshold"}]},
           {"==":[{"var":"evidence.has_valid_receipt"},false]} ] }
```
- **모름(null)은 어느 방향으로도 참을 만들지 않는다.** 비교·`in`·`not` 전부 거짓이고 `is_null`만이 예외다. 연산자마다 다르게 두면(`!=`·`not(var)`가 모를 때 참) **틀리는 방향이 「조용한 위반 판정」**이 된다 — 증빙을 확인하지 못한 건에 "증빙 없음" 사유가 붙는다. `is_null`이 감싼 경로는 미해소 가드에서 면제되지만(거기서는 `None`이 판단 불가가 아니라 묻고 있는 대상이다), 같은 경로가 `is_null` 밖에도 나오면 가드를 유지한다.
- 노드 `action` = `{decision: PASS|REJECT|REVIEW|RETURN, flag?, note?}`. condition 결과로 `next_routings`를 따라 이동, 단말에서 decision 확정. `PASS_THROUGH`는 "여기서 걸 게 없으면 통과"를 뜻하는 특수 종단값이다.
- **재현성**: 같은 `(eval_context, graph_version)` → 항상 같은 `decision·path`. LLM은 생성 단계에서 DSL을 만들 뿐, 적용은 결정론적.

### 4.3 ③ Risk Review Agent (단순 이상탐지 1차 + RAG 내규 검증 2차)

**목적**: Rule로 안 걸러진 미매칭·불확실 건에 검토 우선순위와 근거를 부여.

**"미매칭 정산 ─► Risk Review Agent" 연결고리(FR-RA-04) 구현 상태**: `domain/policies/orchestrator.py::judge()`가 GLOBAL(ACTIVE) 필수 게이트 → 계정과목별 scope 그래프 순서로 실제 Rule 엔진을 실행하고 `rule_hits`를 남긴다. 결과가 REVIEW이거나 매칭되는 ACTIVE 그래프 자체가 없으면 `IN_REVIEW`로 전이되고, Django `SettlementViewSet.judge` 액션이 그 즉시 `/agent/risk-review`(FastAPI)를 호출해 이 Agent의 2단계 파이프라인을 실행·저장한다. PASS/REJECT/RETURN 판정 건은 Risk Review로 넘어가지 않는다.

**Flow (MVP: 2단계 · 등급이 2차의 깊이를 가른다)**
```
미매칭 정산 ─► Risk Review Agent(FastAPI)
  [1차: 단순 이상거래 탐지]
  1. Feature 조립
       └─ FastMCP:get_tx_features(tx_id)  금액/시간/요일/가맹점/사용자패턴/이력
  2. 비지도 이상탐지 추론 (ML Serving)
       └─ Isolation Forest: anomaly_score + 피처기여 → risk_tier(HIGH/MEDIUM/LOW)
  [2차: RAG 내규 기반 검증 — 등급에 따라 분기]
       ├ LOW (채점됨)        ─► LLM 0회. 결정론적 고정 안내 + APPROVE
       ├ MEDIUM             ─► fast  프로파일로 심층 검증
       ├ HIGH               ─► heavy 프로파일로 심층 검증
       └ 미측정(no_model/error) ─► heavy (LOW로 접지 않는다)
  3. 근거 수집 (심층 검증 시)
       ├─ FastMCP:search_policy(query, scope=category)  해당 분류 규정·세법
       └─ FastMCP:search_cases(query)                   유사 승인·반려 사례
  4. LLM: 내규와 대조해 위반 여부 분류 + 구조화 보고서 생성
  5. 서버가 모델 출력을 대조·정정 → risk_reviews 저장 ─► 검토 워크스페이스
회계 담당자 결정 ─► decision_labels 적재(향후 지도학습용 데이터로 축적만)
```

**등급 분기의 근거**

- **【하】는 LLM을 부르지 않는다.** 비용·지연 0이고 고정 문구라 지어낼 여지가 없다. 문구의 핵심은 「검사해보니 문제없음」이 **아니라 「검사하지 않음」이라고 말하는 것**이다 — "이상탐지에서 특이 신호가 발견되지 않아 내규 심층 검증은 수행하지 않았습니다. 규정 대조를 거치지 않은 건입니다."
- **미측정을 LOW로 접지 않는다.** 모델이 없어 등급이 없는 건을 「일반 거래」로 처리하면 **검사를 못 한 것이 검사해보니 안전한 것**이 된다(FR-RR-04a). 그래서 `stage1_status`를 등급과 별도 축으로 저장한다.
- **LLM 프로파일은 역할로 부른다**(`fast`/`heavy`) — 모델 이름은 설정 한 곳에서만 정하고 호출부는 역할만 안다. 모델별 파라미터 제약(일부 계열은 `temperature` 커스텀 값을 거부)은 어댑터가 흡수한다.

**2차 산출물 = 구조화 보고서**(마크다운 한 덩어리가 아니다) — 요약·권고·특징(highlights)·근거+판단(findings)·추가안내(advisories). 마크다운으로는 화면이 미리보기와 자세히를 가를 수 없고, 근거와 판단이 따로 놀면 어느 조항이 어느 판단을 뒷받침하는지 되짚을 수 없다.

**서버가 모델 출력을 대조한다** — 프롬프트 지시만으로는 부족하다:

| 검증 | 왜 |
|---|---|
| 근거 id가 실제 검색 결과에 없으면 **버린다** | 지어낸 인용 차단 |
| 인용 라벨·발췌를 **서버 원본으로 덮는다** | 모델이 옮겨 적다 바꿔도 화면엔 실제 검색 결과가 뜬다 |
| 근거가 전멸한 판단은 **추가안내로 강등** | 「근거는 없지만 확인해 보세요」는 유효한 안내지만 **판단으로 제시되면 안 된다** |
| `INSUFFICIENT_INFO`인데 권고가 `APPROVE`면 **보완요청으로 정정** | 배너는 「판단 보류」인데 본문이 승인을 권하면 서로 다른 말을 한다 |

보고서 생성이 실패해도 **분류 결과를 버리지 않는다** — 분류는 근거 검색까지 마쳐 비용을 이미 지불했고, 여기서 예외를 올리면 `RiskReview` 행이 아예 안 남아 검토자 화면엔 「AI가 아무것도 안 했다」만 남는다.

**입력**: 미매칭 정산 + 파생 feature
**출력**: anomaly_score·risk_tier·stage1_status, 이상사유(피처기여), 규정·사례 근거(출처 조항), 구조화 보고서, AI 권장의견
**사용 Tool**: `get_tx_features`, `ml_infer`, `search_policy`, `search_cases`
**모델 운영(MVP)**: 라벨 불필요한 비지도 이상탐지 온라인 추론(실시간). 등급 임계값·모델 갱신은 관리자 온디맨드.

> **확장(post-MVP)**: 라벨이 충분히 쌓이면 지도학습 모델(검토필요확률 `review_probability`, 반려/보완 라벨 학습)과 `decision_labels` 기반 자동 재학습 피드백 루프를 추가한다. MVP는 지도학습·재학습 루프를 포함하지 않는다.

이 Agent의 `anomaly_score`(이상탐지 모델 출력)는 Rule Agent의 decision 결정 방식(§4.2(c))과 무관한 별개 파이프라인의 산출물이다. 이상탐지 스코어 컷오프는 §11.2 Open Issue로 남는다.

| `search_cases` | query | similar_cases[] | Chroma 직접(`case_history`) | Risk |
| `read_receipt` | file_ref | extracted(사용내역+판정사실), warnings[] | OpenAI 비전(FastAPI 내) | Draft |
| `read_evidence_document` | file_ref, kind | extracted, field_confidence, evidence_spans, extraction_status | OpenAI 비전(FastAPI 내) | Rule, Risk |
| `fetch_historical_tx` | period, filters | tx[] | Postgres(via Django) | Rule(검증) |
| `build_rule_context` | settlement_id | eval_context(facts JSON 스냅샷) | Postgres(via Django) + `classify_merchant` | Rule(적용) |
| `run_rule_engine` | settlement_id | decision, path[], flags[] | 내부 Rule 엔진(순수·그래프 순회) | Rule(적용) |
| `get_tx_features` | tx_id | feature_vector(원-핫 인코딩 후 24컬럼 — 원본 15개 피처 중 3개 저카디널리티 범주형(거래요일_한글·시간대구간·일시불할부구분코드)을 원-핫 전개, 학습된 모델의 `feature_columns` 순서에 정렬) | Postgres(via Django, `transactions/features.py::build_tx_features`가 카드별 과거 거래 집계까지 전담) | Risk |
| `ml_infer` | feature_vector | anomaly_score, contribs *(MVP: 비지도 이상탐지만. review_prob는 post-MVP)* | ML 모델(FastAPI 내) | Risk |

- **판정 대상은 `settlement_id`로 넘긴다**(`tx_id`가 아니다). 판정 사실은 거래 원문만이 아니라 사용자가 채운 내역·첨부 추출까지 합쳐 만들어지고, 그 묶음의 단위가 정산 건이다. `get_tx_features`만 거래 단위인데, 이상탐지가 보는 것이 카드 사용 패턴 자체이기 때문이다.
- **`search_policy`의 `scope`는 카테고리 격리 장치다.** 유사도만으로 전 규정을 검색하면 회식 규정이 식대 질의에 새어 들어온다 — `scope`를 주면 Django `PolicyDoc.rule_scope`로 문서명을 좁혀 검색한다(해당 scope 문서가 없으면 빈 목록으로 fail-open해 공통 규정만 남는다).
- **`read_evidence_document`의 관측 계약**: 경로가 있으면 관측한 것, 없으면 안 본 것이다(→ `None` → 미해소 가드). 「확인했는데 없음」을 「안 봤음」과 섞지 않는 것이 이 도구의 핵심이다.
- `run_rule_engine`은 decision·path·flags만 반환하며 별도 confidence 필드는 없다(§4.2(c)). `classify_merchant`의 confidence(업종 판별 신뢰도), `ml_infer`의 anomaly_score는 각기 다른 파이프라인의 산출물이므로 혼동하지 않는다.

### 5.1 Tool의 데이터 접근 경로

Tool은 무상태 함수처럼 보이지만, LLM이 넘기는 인자만으로는 부족하다. 예) `get_tx_features(tx_id)`는 인자로 `tx_id` 하나만 받지만, 실제로는 그 거래의 상세·사용자의 최근 이력·동일 거래처 누적액까지 조회해야 feature가 만들어진다. 이때 "인자 외 원본 데이터를 어디서 가져오느냐"가 데이터 접근 경로다.

**원칙: 데이터 종류에 따라 접근 경로를 이원화한다.**

```
┌──────────────── FastMCP Tool 구현체 ────────────────┐
│                                                     │
│  관계형 데이터(거래·이력·규정·정산·카드)             │
│     └─► Django 내부 조회 API (read-only REST) ──► Postgres
│         · Postgres를 만지는 것은 Django 하나 (SoR 유지)
│         · ORM·권한·스키마를 Django에 일원화
│                                                     │
│  벡터 데이터(규정/사례 임베딩)                       │
│     └─► Chroma 클라이언트 직접 ──► Chroma            │
│         · Chroma는 Django가 소유하지 않으므로 직접 접근
│                                                     │
└─────────────────────────────────────────────────────┘
```

| 데이터 | 접근 경로 | 이유 |
|---|---|---|
| 관계형(Postgres) | Django 내부 read API 경유 | Postgres 접근점을 Django로 단일화(SoR·권한·감사) |
| 벡터(Chroma) | Chroma 직접 | Django가 소유하지 않는 저장소, 홉 최소화 |
| ML 추론 | FastAPI 프로세스 내부 호출 | 별도 서비스 불필요(MVP) |

즉, LLM/Tool은 절대 Postgres에 직접 SQL을 쏘지 않는다. 관계형 데이터가 필요하면 반드시 Django 내부 API를 거친다. Chroma·ML만 tool이 직접 접근한다.

**설계 규칙**
- Tool은 무상태, 인자·반환은 pydantic 스키마로 엄격 정의.
- 관계형 데이터 접근은 Django 내부 API 경유(LLM에 raw DB 노출 금지).
- 모든 tool call은 로그로 기록(감사·비용·디버깅).

## 7. 위험 검토 파이프라인 (MVP: 이상탐지 1차 + RAG 내규 검증 2차)

MVP는 라벨이 충분히 축적되기 전(콜드스타트)이므로 지도학습에 의존하지 않는 2단계 구조로 단순화한다.

```
[1차 · 단순 이상탐지 (비지도, 라벨 불필요)]
  [학습]  transactions ──► Feature 생성 ──► 비지도 이상탐지 학습(Isolation Forest)
         ──► 모델 레지스트리(버전관리) ──► ML Serving 배포
  [추론]  실시간(동기): get_tx_features → ml_infer → anomaly_score/피처기여
         ──► risk_tier(HIGH/MEDIUM/LOW) 판정 + stage1_status(채점 성공 여부) 기록
[2차 · RAG 내규 검증 (등급이 깊이를 가른다)]
  LOW      ──► LLM 0회, 「심층 검증 미수행」 고정 안내
  MEDIUM   ──► fast  프로파일 ─┐
  HIGH·미측정 ──► heavy 프로파일 ─┴─► search_policy(scope)/search_cases(RAG)
         ──► LLM 내규 대조 ──► 서버측 근거 대조·정정 ──► risk_reviews 저장
[피드백] 회계 결정 → decision_labels 적재만 (MVP는 재학습 안 함, 향후 지도학습용)
```

**Feature 예시**: 금액·정규화금액, 시간대/요일/심야여부, 가맹점/업종, 사용자·부서, 최근 N일 빈도, 동일거래처 누적, Rule 적용결과, 증빙 유무.
**평가지표**: 이상탐지 검토 적중률·AUC, RAG 근거 정확도, 검토량 감소율. (목표치 §11.2 Open Issue)

> **확장(post-MVP)**: 라벨이 쌓이면 지도 검토필요확률 분류기(XGBoost/LogReg 등)와 `decision_labels` 기반 온디맨드 재학습 루프를 추가한다.

## 7-1. 가맹점 업종 구분 파이프라인 (Merchant Classification)

가맹점명만으로는 비용분류가 모호한 경우가 많아, 가맹점의 업종(업태)을 별도로 판별해 Draft Agent의 비용분류 제안과 Risk 이상탐지 feature('가맹점/업종')를 보강한다. 외부 조회 비용·지연을 줄이기 위해 자체 DB 캐시를 1차 소스로 두는 캐스케이드 구조다.

```
가맹점명(+장소 힌트)
  0. 정규화        지점명·특수문자·체인 접미 제거 → 조회 키 생성
  1. [캐시]         merchant_categories(자체 DB) 히트 & 유효(TTL 30일) → 반환        source=CACHE
  2. [카카오 지도]   로컬 키워드검색 → category_group_code/category_name(원시 업종) 조회
  3. [LLM 재분류]   가맹점명 + 카카오 원시 카테고리 → **정본 업종 어휘**로 재분류
  4. [확정+캐시]     업종·신뢰도·source·조회일 upsert → 이후 동일 가맹점 재사용            source=KAKAO
```

카카오 원시 `category_group_code`/`category_name`은 장소·마케팅 분류라 **그대로 쓰지 않는다** —
예를 들어 일반 식당과 유흥주점이 둘 다 `FD6`(음식점)로 묶여 있어 비용분류·리스크 판단 힌트로는
어휘가 안 맞는다. **LLM이 가맹점명과 카카오 원시 카테고리를 함께 보고** 아래 고정 어휘로
재분류한다:

```
일반음식점 · 카페 · 주점/유흥 · 노래연습장 · 사행성업종 · 숙박 · 골프장 · 레저
마트/편의점 · 면세점 · 이·미용 · 문구/사무용품 · 주유/교통 · 전자/가전 · 기타
```

**이 어휘가 곧 판정 사실 `merchant.merchant_type`이다** — 룰 DSL의 `in [...]` 비교와
금지업종 별표(제9조②)의 키가 같은 표기여야 한다. 정본은 core
`apps/core/domain/transactions/industry.py`이고, ai는 `apps/ai/app/schemas.py`가 미러한다
(`Category`와 같은 관례). 어긋나면 캐시 적재 API가 400으로 거부한다.
어휘 통일의 배경·이관 내역은 `llm_wiki/_context/merchant-industry-vocabulary.md`.

> **어휘의 세분화 기준은 "규정이 가르는가"다.** 골프장·노래연습장·사행성업종·이·미용업을
> 각각 독립 항목으로 두는 이유는 금지업종 별표와 주의업종 룰이 **바로 그 구분으로 판정**하기
> 때문이다 — 어휘가 못 가르면 룰을 아무리 잘 써도 판정할 수가 없다. 반대로 규정이 구분하지
> 않는 업태는 묶는다.

`주점/유흥`을 `일반음식점`과 분리한 게 핵심 — 카카오 group code만으로는 못 가르고 회사 규정이
금지 업종으로 정한 구분이라 LLM 프롬프트에 명시적으로 지시한다(노래연습장·사행성업종·이·미용도
각각 별도 항목이다 — 규정이 다르게 다루므로 묶지 않는다). 카카오에서 못 찾거나 LLM 재분류
자체가 실패해도(키 없음·타임아웃·거부) **원시 카카오 라벨로 새지 않고** 업종은 미확정
(industry_code/label 공란)으로 남긴다 — 웹검색 등 추가 폴백은 두지 않는다. 비용분류 제안은
업종 없이 다른 신호(가맹점명·금액·시간·패턴)만으로 진행한다. **미확정을 `기타`로 밀지 않는
이유**: 금지업종 별표가 `"*" → False`(금지 아님)로 폴백해, 확인하지 않은 것을 안전하다고
단정하게 된다. 미확정이면 `merchant.merchant_info_resolved=False`로 남아 사람이 본다.

- **출력**: `{ industry_code, industry_label, confidence, source }` — `industry_code`/`industry_label`은
  카카오 원시값이 아니라 **LLM이 재분류한 우리 서비스 어휘**(예: `BAR_ENTERTAINMENT`/`주점/유흥`).
  카카오 원시 응답은 감사·재현용으로 `merchant_categories.raw`(JSONB)에 그대로 보존한다.
- **활용**: ① Draft Agent 비용분류 제안(가맹점+업종 → 분류) ② Risk 이상탐지 feature 보강(업종-분류 불일치, 유흥업종 접대 등)
- **캐시(자체 DB)**: 관계형이므로 Django 소유(`merchant_categories`). 외부 API(카카오 지도) 호출과
  LLM 재분류는 FastAPI(ai)에서 수행하고, 결과만 Django 경유로 캐시 적재한다(§5.1 원칙 준수).
- **세무/회계 부적합**: LLM 재분류 업종도 여전히 장소·업태 기반 추정이라 세무 계정과목과
  불일치할 수 있다. 비용분류 보조 힌트로만 사용하고, 세무 판단은 규정/세법 RAG(`tax_refs`)에 위임한다.
- **확장(post-MVP)**: 카드사 제휴로 MCC(Merchant Category Code) 확보 시 표준 업종코드로 대체·보강한다(§11.2).
- **Draft Agent 연동**: `agents/draft_agent._resolve_industry`가 초안 LLM 호출 **전에** 이 tool을
  부르고, 결과를 사용자 프롬프트에 사실로 넣은 뒤 `merchantIndustry`/`merchantIndustryCode`를
  **조회값 그대로** 반환한다. **업종은 LLM 출력 스키마에 두지 않는다** — 스키마에 있으면 모델이
  조회 결과를 무시하고 지어낼 수 있고, 지어낸 값도 조회값과 구별되지 않는다(§4.1의
  "모델이 낼 수 없어야 하는 값은 지시가 아니라 스키마에서 뺀다"). 화면(S-01)이 저장 시 함께
  올려 `Settlement.merchant_industry(_code)`에 남고, 조립기가 정본 어휘로 접어
  `merchant.merchant_type` 판정 사실로 올린다.
- **단계별 타임아웃**(캐시 3s·카카오 4s·재분류 LLM 8s·캐시적재 4s): Draft는 사용자가 기다리는
  경로라 각 단계에 상한을 둔다 — Django `/agent/draft` 호출 타임아웃 40s가 이 최악 합을 담는다.

## 8. RAG 파이프라인

```
문서 업로드 ─► 파싱(docling) ─► 프로파일·교정 ─► 청킹(조 단위) ─► 임베딩 ─► Chroma upsert
                                                                      │
                                                              문서 분류(triage, 제안이지 차단 아님)
                                                                      ▼
                                                          scope 지정 시 룰 자동 생성 트리거
질의 시    ─► 쿼리 임베딩 ─► Chroma 유사도 검색(top-k, scope 필터) ─► LLM rerank(선택) ─► LLM 컨텍스트 주입
```

- **자르는 단위는 조(條)** — 분할이 더 필요하면 조→항→호→문장→문자 순 사다리를 탄다. 표는 독립 청크.
- 버전/유효일 메타로 최신 규정 우선. 규정 개정 시 재임베딩(비동기).
- 근거 표시 시 출처(문서·조항) 함께 반환하여 회계 담당자가 검증 가능하게.
- **검색은 카테고리(scope)로 필터링한다** — `search_policy(scope=...)`가 `PolicyDoc.rule_scope`로 문서명을 좁힌다. scope 없이 유사도만으로 전체 규정을 검색하면 회식 규정이 식대 질의에 새어 들어오는 문제가 실측됐다(QA, `docs/qa/_summary.md`).
- **rerank는 「관련 없음」과 「호출 실패」를 구분**한다 — 실패 시 원본 top-k로 fail-open한다(안 그러면 하류가 "근거가 원래 없었다"로 오인).
- 임베딩 모델은 `text-embedding-3-large @ dimensions=1024`로 확정(MRR 실측 기반, `_context/embedding-strategy.md`).

## 11. 확정 사항 및 남은 이슈

### 11.1 MVP 확정 사항

- **Django ↔ FastAPI 통신**: 동기 REST (메시지 큐 없음)
- **비동기 스택**: 미도입 (Redis/Celery 없이 동기 처리, 무거운 작업은 관리자 온디맨드 배치)
- **영수증 처리**: 별도 OCR 없이 OpenAI 비전 모델로 이미지 직접 판독
- **FastMCP**: 단일 서버로 3 Agent 공용
- **Tool 데이터 접근**: 관계형=Django 내부 API 경유, 벡터=Chroma 직접 (§5.1)
- **가맹점 업종 구분**: 자체 DB 캐시 → 카카오 지도 API 캐스케이드로 판별, 비용분류 보조 힌트로만 사용(세무 판단 아님). MCC는 post-MVP (§7-1)
- **Rule decision 결정 방식**: PASS/REJECT/RETURN/REVIEW는 노드 생성 시 `action.decision`으로 직접 지정한다. 판정 시점의 확신도 계산·임계치 비교 방식은 채택하지 않는다(§4.2(c))
- **계정과목 scope 매핑**: 기업업무추진비→접대. 회식은 식대와 별개의 독립 scope로 유지한다(§3.3)

### 11.2 남은 확정 필요 사항

1. **이상탐지 모델 재학습** — 등급 임계값(`RISK_TIER_*`)은 배포 모델 실측 분포에서 잡은 고정 상수라 재학습하면 다시 잡아야 한다. 배포된 pkl은 `feature_stats`를 갖지 않는 세대여서 **`feature_contribs`가 항상 빈 배열**이고(파이프라인은 구현돼 있어 재학습하면 채워진다), sklearn 버전도 학습(1.8.0)과 서빙 컨테이너(1.5.2)가 어긋나 있다 — 재학습 시 버전 고정이 함께 필요하다. 이상탐지 스코어 축은 Rule Agent decision 결정 방식과 무관한 별개 파이프라인이다
2. (post-MVP) 지도학습(review_probability) 도입 시점·필요 라벨량·자동 재학습 주기
3. 임베딩 모델(OpenAI vs 로컬) 및 Chroma 영속·백업 전략
4. ERP 전표(안) 스키마: MVP 산출물 포맷(연동은 범위 외)
5. 멀티테넌시: 테넌트별 데이터·모델·규정 격리 범위(MVP 필요 여부 포함)
6. OpenAI 모델 선정(비전·LLM) 및 프롬프트·비용 관리 방식
7. 가맹점 업종 — 캐시 정책(TTL 30일·정규화 휴리스틱)은 §7-1로 확정. 남은 것: Risk Review Agent의 `classify_merchant` 연동(현재 Draft만 연결), Agent가 업종을 비용분류 제안에 반영하는 가중치
8. (확장) 카드사 제휴 MCC 확보: 세무·회계 기준 업종코드(MCC) 도입 방식·시점 — 카카오 업종을 대체·보강
9. 룰 그래프 정합성: next_routings 사이클 방지·도달 불가 노드 검출, 동일 결과 다중 라우팅 시 우선순위 규칙, 그래프 스코프(전사/분류/본부) 정의
10. 카드번호·개인정보 전송/저장 구간 암호화 — 현재는 카드번호를 마스킹 값(`number_masked`)만 SoR에 두는 것으로 노출을 줄였을 뿐, 별도 필드 암호화(예: Fernet)는 구현되지 않았다

## 12. 서비스 기획 — 문제 정의 · 화면 · 대시보드

> 이 절은 §1~11의 기술 구조가 **무엇을 풀기 위한 것인지**와 그 결과가 사용자에게 어떤 화면으로 닿는지를 다룬다. 화면 목업은 정보 구조·우선순위를 정하기 위한 것이며 픽셀 매칭 대상이 아니다(실제 구현 기준은 `화면설계서/`). 목업의 비용분류 표기는 §3.3의 `Category` 정본(접대·회식·회의·식대·출장·기타)을 따른다.

### 12.1 문제 정의 (Problem)

법인카드 정산을 모든 조직이 매달 반복하지만, 누구도 본업으로 여기지 않는 잡무다. 그럼에도 입력부터 회계·상부까지 모두의 시간을 잡아먹는다.

**역할별 Pain Point**
```
임직원        영수증 챙기고 · 분류 고르고 · 사유 적는 게 일보다 번거롭다
   │           │ 애매함에 몰아서 입력, 자주 반려 → 재작성
   ▼
팀장          팀원 지출을 취합·검토해 올리는 데 반나절
   │           │ 뭐가 문제인지 건건이 열어봐야 한다
   ▼
회계 담당자    수백 건을 규정과 대조하며 전 건을 검토
   │           │ 대부분 정상인데 다 봐야 하고, 정말 매핑할 건은 시간 없음
   ▼
회계/운영 상부  예산이 어디서 새는지, 규정이 맞는지 데이터가 없다
              → 감(感)으로 정책을 결정한다
```

**핵심 문제 3가지**

| # | 문제 | 결과 |
|---|---|---|
| ① | 입력이 번거롭다(분류·증빙·사유) | 지연 제출, 반복 반려, 본업 방해 |
| ② | 검토가 전 건 일일이다 | 회계 시간의 대부분이 "정상 건 확인"의 소모 |
| ③ | 의사결정 근거가 없다 | 예산·규정 정책을 데이터 없이 감으로 판단 |

> **관통하는 문제**: 정산의 부가가치가 낮은데도 모두의 시간을 잡아먹는다.
> → 본 서비스는 ① 입력을 AI가 도와주고 ② 확실한 건을 규칙으로 자동 처리하며 ③ 애매한 건만 근거와 함께 골라주고 ④ 결정 근거를 대시보드로 제공하여 이 문제를 푼다.

### 12.2 화면(UI) 구체화 — 역할별 주요 화면

**[임직원] 내 지출 / 증빙 제출**

### 12.3 대시보드 고도화 — 역할별 지표·인사이트·정책 추천

> **원칙**: 자동화·정책을 막지 않는다. 대시보드가 현황과 위험을 보여주고, 상부가 정책을 결정하도록 근거·추천을 제공한다.

**역할별 대시보드 (관심사가 다르다)**

| 역할 | 핵심 관심 | 대표 지표 |
|---|---|---|
| **임직원** | 내 처리 상태 | 미제출·보완요청·평균 승인 소요 |
| **팀장** | 팀 취합 효율 | 팀 이상건율·제출 리드타임·반복 반려 사유 |
| **회계 담당자** | 검토 부하 | 자동처리율·검토 대기·평균 검토 시간 |
| **회계/운영 상부** | 정책 결정 | 분류별 지출 추세·예산 잠식·정책 위반 패턴·리스크 |

**상부용 거버넌스 대시보드 (정책 결정 지원)**

```
┌ 비용 거버넌스 (2026 Q3) ───────────────────────────────────────┐
│ 자동처리율 82% ▲   회계 검토시간 -41% ▲   반복반려 -28% ▲ │
├─────────────────────────────┬───────────────────────────────┤
│ 분류별 지출·예산 잠식        │ 정책 인사이트 (추천)             │
│ 접대     ████████ 잠식 96%    │   🟡 접대비, 3개월 연속 예산 임박  │
│ 출장     ████████ 잠식 61%    │   한도 재검토 or 예산 재배분     │
│ 식대     ████████ 잠식 48%    │ 🟡 '야근 식대' 반복 승인 320건    │
│ 회의     ████████ 잠식 73%    │   자동승인 Rule 정교화 추천      │
│                             │ 🟡 접대비 한도-1만원 반복 분할결제  │
│                             │   12건 → 편법 회피 패턴 점검     │
└─────────────────────────────┴───────────────────────────────┘
```

**대시보드가 제공하는 3종 인사이트**
1. **예산 지표(모니터링)**: 분류/팀/기간별 소진율·초과 위험 → 경고만, 차단 없음
2. **정책 인사이트(추천)**: "이 패턴은 Rule로 만들 만하다 / 이 한도는 재검토가 필요하다"
3. **리스크 인사이트(취합)**: 반복 반려율 분포, 특정 분류 급증 등 상부가 봐야 할 신호

> 상부는 이 화면을 근거로 규정 개선 · 예산 재배분 · 신규 Rule 도입을 판단한다. 시스템은 추천하고, 결정은 사람이 한다.

**운영 KPI (시간 절감 중심)**: 자동 처리율/회계 검토 건수·시간 감소율 · 정산 제출→승인 평균 리드타임 · 반복 반려 감소율/증빙 누락 사전 예방 건수 · 신규 Rule 발굴·적용 건수 및 절감 효과

### 12.4 카드 구분 × 분류에 따른 흐름 분기

| 상황 | 흐름 상 다른 지점 |
|---|---|
| **공용 카드** | Draft Agent가 실사용자·목적 지정 단계 삽입 |
| **후정산** | 증빙 첨부 검증 강화, 영수증 없으면 제출 차단(안내) |
| **접대 분류** | 한도·거래처·세무 리스크 → Risk Review 우선순위 영향 |
| **출장 분류** | 출장 신청/일정과 대조, 증빙(교통·숙박) 매칭 |
| **소액·정형 사용** | Rule Agent PASS 판정 → 상세검토 생략, 사람 최종확인 후 확정 |
