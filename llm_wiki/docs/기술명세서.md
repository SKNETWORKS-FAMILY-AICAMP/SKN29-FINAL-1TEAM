## 1. 아키텍처 개요

### 1.1 설계 원칙

- **관심사 분리**: 트랜잭션/도메인(Django)과 AI 오케스트레이션(FastAPI)을 물리적으로 분리한다.
- **System of Record는 Postgres 하나**: 모든 확정 데이터의 단일 진실 원천(SoT)은 Django가 관리하는 PostgreSQL이다. AI는 제안(초안·스코어·근거)만 생성하고, 확정은 Django 도메인을 통해서만 이뤄진다.
- **Agent = LLM + Tools(MCP)**: 모든 Agent는 단일 FastMCP 서버로 노출된 표준 도구를 통해서만 데이터에 접근한다. (LLM의 직접 DB 접근 금지 → 감사·권한 일원화)
- **MVP는 동기 REST**: 별도 메시지 큐(Redis 등) 없이 동기 REST 호출로 처리한다. 문서 임베딩·모델 학습 등 무거운 작업은 관리자 트리거 배치(온디맨드)로 단순화한다.
- **사람 확정 원칙**: 자동 통과 건도 최종 확정은 사람이 수행한다. 시스템은 상태만 `승인대기`로 전이시킨다.

### 1.3 컴포넌트 책임 분담 (RACI 요약)

| 컴포넌트 | 책임 | 하지 않는 것 |
|---|---|---|
| **React** | 화면, 상태표시, 사용자 액션 | 비즈니스 규칙 판단 |
| **Django(DRF)** | 인증·RBAC, 도메인 CRUD, 정산 상태머신, ERP 전표(안), Postgres 소유 | LLM 직접 호출·ML 추론 |
| **FastAPI** | Agent 오케스트레이션, LLM/ML 호출, 비동기 파이프라인 | 확정 데이터 소유(제안만 반환) |
| **FastMCP** | Agent용 표준 도구 서버(검색·조회·Rule실행·OCR) | 자체 상태 저장(무상태 지향) |
| **Chroma** | 규정/사례 임베딩 저장·유사도 검색(RAG) | 트랜잭션 데이터 저장 |
| **PostgreSQL** | 모든 확정 데이터 SoT | 벡터 검색 |

> **왜 Django + FastAPI 둘 다?**
> Django는 인증·ORM·Admin·상태머신 등 정형 도메인에 강하고, FastAPI는 async·LLM/ML 서빙 등 AI 워크로드에 강하다. Django를 SoR로 고정하고 AI 작업만 FastAPI로 위임하면 책임 경계와 감사 지점이 명확해진다.

## 3. 데이터 아키텍처

### 3.1 PostgreSQL — 주요 테이블(개요)

| 도메인 | 테이블(예) | 핵심 컬럼 |
|---|---|---|
| 조직/사용자 | `users`, `teams`, `team_members`, `roles` | role, team_id(제출단위), extra_capabilities(JSON: 개인 추가부여 기능권한) |
| 카드 | `cards` | card_type(개인/팀/공용/후정산/선불), owner_id |
| 거래 | `transactions` | merchant, amount, ts, card_id, raw_payload(JSONB) |
| 가맹점 업종 캐시 | `merchant_categories` | normalized_name(idx), place_id, industry_code, industry_label, source(CACHE/KAKAO/WEB), confidence, resolved_at, raw(JSONB) |
| 증빙 | `receipts` | file_ref, ocr_text, matched_tx_id, status |
| 정산 | `settlements` | tx_id, category, status(상태머신), submitted_by |
| 정산 상태이력 | `settlement_events` | from_state, to_state, actor, reason, ts |
| 규정 별표(임계값) | `policy_tables` | key(`lodging_limit_table` 등), title, key_axes(JSONB: 룩업 축을 EvalContext 경로로 선언), payload(JSONB: 별표 원본 — 축 개수·깊이가 별표마다 달라 고정 컬럼 금지), source_doc_id, source_clause, effective_date, superseded_date. 개정은 UPDATE 아닌 INSERT(과거 판정 재현 보존) |
| 규정 문서(RAG 소스) | `policy_docs` | title, category, version, effective_date, file_ref |
| 추가 증빙 첨부 | `attachments` | settlement_id, kind(RECEIPT/PRE_APPROVAL/MEETING_MINUTES/PARTICIPANT_LIST/TRIP_PLAN/CONTRACT/OTHER), file_ref, extracted(JSONB: EvalContext dot-path→값), field_confidence(JSONB), evidence_spans(JSONB), extraction_status, extractor_version |
| 룰 그래프 버전(최종 상태 도메인) | `rule_graphs` | family_key(그래프 계열), name, scope(`GLOBAL` 또는 실제 `Category` 값), status(DRAFT/SIMULATED/ACTIVE/ARCHIVED), version, entry_node_key(VARCHAR — `rules.node_key` 문자열 참조), sim_result(JSONB), approved_by, activated_at. 한 행이 한 버전이며 (family_key, version) 유일, ACTIVE는 scope당 DB에서 하나만 허용 |
| 룰 그래프 승인 스냅샷 | `rule_graph_versions` | graph_id, version, snapshot(JSONB), approved_by, approved_at, is_active — 승인 당시 재현·감사용 스냅샷 |
| 룰(노드) | `rules` | graph_id, node_key, condition(JSON/DSL), action, priority |
| 룰 라우팅(next_routings) | `rule_routings` | from_node_key, on_result(MATCH/NO_MATCH/PASS/REJECT/REVIEW), to_node_key, priority |
| Rule 판정로그 | `rule_hits` | tx_id, graph_id, graph_version, path(JSONB: 방문 노드), eval_context(JSONB: 판정 시점 facts 스냅샷 — 재현·감사), decision, flags(JSONB) |
| Risk 결과 | `risk_reviews` | tx_id, anomaly_score, reasons(JSONB: 1차 feature_contribs), stage2_verdict(JSONB: 2차 RAG 검증 LLM 구조화 출력 원본 — violation_verdict/review_reasons/recommendation/citations/similar_cases), rag_refs(JSONB: 근거 인용 {title,source,kind} 형태 — S-03 화면 기존 계약과 정합), ai_recommendation(APPROVE/RETURN/REJECT — stage2_verdict.recommendation의 SUPPLEMENT는 RETURN으로 매핑) *(review_prob 컬럼은 post-MVP 지도학습 도입 시)* |

`rule_hits`는 decision만 기록하고 별도의 확신도(confidence) 컬럼은 두지 않는다 — decision이 룰 노드 `action`에 직접 지정되는 결정론적 방식이기 때문이다. `risk_reviews.anomaly_score`(이상탐지 모델 출력)와 `merchant_categories.confidence`(업종 판별 신뢰도)는 이와 무관한 별개 파이프라인의 산출물로, 그대로 유지한다.

#### 3.1a 인가 모델 — 기능 단위(Capability) RBAC

권한은 역할(Role) 자체가 아니라 기능 단위 능력(Capability)으로 판정한다. 역할은 라벨·기본값 산정·화면 rank용으로만 남고, 실제 인가 단위는 아래 4개 Capability다.

| Capability | 게이트하는 기능 | 서버 강제 지점 |
|---|---|---|
| `team_aggregate` | 팀 취합(팀원 건 보완요청/반려/제출) | `POST /settlements/{id}/team-decision/` |
| `accounting_review` | 회계 검토(승인/보완/반려)·확정 | `POST /settlements/{id}/review/`·`/confirm/` |
| `rule_view` | 룰 콘솔 열람 | (프론트 메뉴 게이트 — 조회 API는 개방) |
| `rule_activate` | 룰 버전/그래프 생성·ACTIVE 전환·롤백 | `POST /rules/{id}/versions/`·`/rules/drafts/`·`/activate/`·`/rollback/` |
| `governance_view` | 거버넌스(임원) 대시보드 열람 | `GET /dashboard/EXECUTIVE/` |

- 유효 능력 = 역할 기본값(`ROLE_DEFAULT_CAPABILITIES`) ∪ 개인 추가부여(`users.extra_capabilities`). 슈퍼유저는 전체.
  - 역할 기본: EMPLOYEE=∅ · TEAM_LEAD=`team_aggregate` · ACCOUNTANT=`accounting_review`+`rule_view` · ACCOUNTANT_LEAD=`accounting_review`+`rule_view`+`rule_activate` · EXECUTIVE=`governance_view`.
  - 룰 콘솔은 회계 공통 열람(`rule_view`) / ACTIVE 전환만 회계팀장(`rule_activate`)으로 분리.
- 구현: `domain.common.permissions.HasCapability` 파생 DRF Permission(`CanTeamAggregate`/`CanAccountingReview`/`CanActivateRule`/`CanViewGovernance`), `User.has_capability()`. `/api/me`·로그인 응답에 `capabilities` 포함(프론트 게이트용).
- 관리자 페이지: Django admin User 화면에서 `extra_capabilities`를 체크박스로 부여/회수, 유효 능력을 읽기전용 표시(`accounts/admin.py`).
- 프론트 화면 게이트(Sidebar 메뉴·팀 취합·검토·룰 활성)는 `useCan()` 훅으로 `capabilities`를 소비한다.

### 3.3 정산 상태 머신 (Django 관리)

4단계: **① 개인 보유 → ② 팀 취합 → ③ 회계 제출·룰엔진 → ④ 회계 검토·확정**
```
[① 개인]  DRAFT
   └─(팀에 올림)─► [② 팀] TEAM_COLLECTING
         ├─(팀 보완)─► TEAM_RETURNED ─(개인 수정)─► DRAFT
         ├─(팀 반려)─► TEAM_REJECTED ─(개인 수정)─► DRAFT
         └─(팀 제출)─► [③ 회계] SUBMITTED ─► RPA_JUDGED (룰엔진 분류)
               ├─(auto-pass)───► PENDING_CONFIRM ─(사람 확정)─► CONFIRMED → ERP_VOUCHER_DRAFTED
               ├─(auto-reject)─► RETURNED ─(재제출)─► SUBMITTED
               └─(needs-review)► IN_REVIEW ─► PENDING_CONFIRM / RETURNED / REJECT(최종)
```

- **상태 enum**(`settlements.status`): `DRAFT` · `TEAM_COLLECTING` · `TEAM_RETURNED` · `TEAM_REJECTED` · `SUBMITTED` · `RPA_JUDGED` · `PENDING_CONFIRM` · `RETURNED` · `IN_REVIEW` · `REJECT` · `CONFIRMED` · `ERP_VOUCHER_DRAFTED`
- 팀 수준(`TEAM_*`, 팀장)과 회계 수준(`RETURNED`/`REJECT`, 회계 담당자) 보완·반려는 별개 상태.
- 상태 전이는 Django 서비스 레이어에서만 수행, 모든 전이는 `settlement_events` + `audit_logs`에 기록.
- **제출 = 2단계 분리**: 개인 "올림"(`DRAFT→TEAM_COLLECTING`)과 팀 "제출"(`TEAM_COLLECTING→SUBMITTED`)은 별개 액션. 1인 팀(영업사원·임원 개인)도 동일 경로(개인 보유→팀 취합→제출)를 탄다 — 개인/조직 무관 일관 제출 경험.
- **계정과목=비용분류 정합**: 룰 `scope`는 `Category`를 SoT로 하며, 정식 회계 계정과목 테이블은 두지 않는다(세무는 RAG). 룰 명세서 과목명↔`Category` 매핑은 `policies/scope.normalize_scope()`가 제공한다: 기업업무추진비→접대. **회식은 식대와 별개의 독립 scope(회식)로 유지**하며, 두 카테고리를 흡수·통합하지 않는다.
- **규정 임계값(policy) 도메인**: 한도·기준액은 2층 구조로 관리한다 — 저장층(`policy_tables`, 별표 원본을 담는 자유 JSON payload)과 소비층(`ctx.policy.*`, DSL이 참조하는 고정 카탈로그). 조립기(`build_rule_context`)가 저장층을 소비층 스칼라로 선해소한다.

## 4. Agent 아키텍처 & Flow

### 4.0 공통: Agent 실행 모델

```
Django(도메인 이벤트) ──REST──► FastAPI(Agent Orchestrator)
                                    │
                                    ├─ LLM 호출 (프롬프트 + tool schema)
                                    ├─ FastMCP tool call (검색/조회/Rule/OCR)
                                    ├─ ML Serving (이상탐지 추론)
                                    └─ 결과(제안) ──REST──► Django (저장/상태전이)
```

모든 Agent 출력은 "제안"이며 Postgres에 결과 테이블로 적재되지만 확정 상태로 만들지 않는다. MVP는 동기 호출: Django가 FastAPI를 REST로 호출하고 응답을 그대로 받아 저장한다(별도 Job 큐 없음). LLM/도구 호출 trace는 로그로 남겨 감사·비용추적한다.

---

### 4.1 ① 초안 작성 Agent (Draft Agent)

**목적**: 거래·영수증을 받아 정산 초안(분류·증빙매칭·규정힌트)을 자동 완성.

**Flow**
```
1. 거래 수집 (카드사 원천/업로드) ──► transactions 적재 (Django)
2. 영수증 이미지 업로드 ──► settlements 첨부 (Django)
3. Draft Agent 실행 (FastAPI)
     ├─ OpenAI 비전: 영수증 이미지 → 필드 추출(가맹점/금액/일시/품목) + 거래 매칭
     ├─ FastMCP:classify_merchant(가맹점)        업종 판별(캐시→카카오 지도→웹검색, §7-1)
     ├─ LLM: 분류 추론 (merchant/업종/amount/time/pattern → category)
     ├─ FastMCP:get_policy(category)             분류별 규정·필요증빙 조회
     ├─ FastMCP:get_card_context(card_id)        카드구분별 필요입력 판정
     └─ 산출: {category, merchant_industry, matched_receipt, missing_evidence[], policy_hints[]}
4. 결과 ──► settlements(DRAFT) 초안 저장 (Django)
5. React: 임직원 화면에 초안(DRAFT) 표시 → 사용자 보정 → 팀 취합(TEAM_COLLECTING) → 팀장 제출 → SUBMITTED
```

**입력**: transaction, receipt 이미지, card_type, 사용자/팀 컨텍스트
**출력**: category(추천), merchant_industry(업종), 증빙 판독·매칭결과, 누락 증빙 목록, 규정 힌트
**사용**: OpenAI 비전(영수증 판독·매칭), FastMCP `classify_merchant`·`get_policy`·`get_card_context`
**분기**: 카드구분 공용→실사용자 지정 요청 / 후정산→증빙 필수 플래그

### 4.2 ② Rule Agent (생성 / 검증 / 적용)

**목적**: 규정을 실행가능 Rule로 만들고(생성), 과거 데이터로 검증하고(검증), 실거래를 1차 자동 판정(적용).

#### 룰 도메인 모델 (그래프/트리)
- **룰 그래프(RuleGraph) = 최종 상태 도메인**: 단건 룰(노드)들이 트리/DAG로 조립된 배포 단위. ACTIVE·버전관리·시뮬레이션·롤백은 모두 이 그래프 단위로 이뤄진다(개별 노드가 아님).
- **버전 저장 방식**: `rule_graphs` 한 행이 한 버전이고 같은 `family_key`가 버전 계열을 묶는다. 기존 그래프 수정은 원본을 복제한 `version+1` DRAFT 행을 만들어 현재 ACTIVE 버전과 병행한다. 새 그래프는 v1로 생성하며 scope는 `GLOBAL` 또는 정산 `Category` 실제 값만 허용한다. scope당 ACTIVE 1개를 조건부 UNIQUE 제약으로 강제한다.
- **룰(노드)**: `condition + action + next_routings`. `next_routings`는 평가 결과(MATCH/NO_MATCH/PASS/REJECT/REVIEW)별로 다음에 평가할 노드 방향(우선순위 포함).
- **엔진**: ACTIVE 그래프의 엔트리 노드에서 시작해 `next_routings`를 따라 단말 노드까지 결정론적 순회 → 최종 결정. 순회 경로는 `rule_hits.path`에 기록(감사/디버깅).

```
룰 그래프 예 (트리 순회)
        [entry] 금액 > 분류한도?
          │ MATCH               │ NO_MATCH
     [접대 세부 룰]          [분류 = 식대?]
       │ REJECT                 │ MATCH → [1인 한도 초과?] → PASS / REVIEW
     RETURNED                   │ NO_MATCH → REVIEW(Risk 이관)
```

#### Rule 콘솔 화면 구조 — 그래프 단위

Rule 콘솔은 그래프 중심으로 구성한다:
- **룰 그래프 보기/초안 편집**: 실제 그래프를 scope 단위로 묶고 각 버전을 Active/수정중 상태로 표시한다. Active v1에서 노드 추가 또는 세부 수정을 시작하면 같은 `family_key`의 v2 DRAFT를 복제해 편집하며, 실행 콘텐츠가 원본과 다시 같아지면 작업본을 폐기하고 v1 Active 표현으로 복귀한다. 전체/수정건 필터, 노드 즉시 추가/삭제를 지원한다. 그래프 삭제는 평상시 선택 UI를 숨기고 상단 삭제 모드 진입 시 각 행의 노드 추가를 삭제 액션으로 교체한다. 확인창 후 비ACTIVE 버전만 삭제하며 ACTIVE 클릭 시 삭제 불가 안내를 표시한다. 노드에는 초안/대기/검증완료/활성 상태를 먼저 표시한다. 상세는 제목·설명·DSL에서 프론트가 동적으로 생성한 다중 조건 자연어 표현("이 Rule이 하는 일")·액션(decision/severity/flag/note/approver)·평가 우선순위·카드형 라우팅과 하단 full-width 추가 액션·생성 이유/관련조항 링크로 구성한다. 저장 요청은 매 입력마다 보내지 않고 필드 이탈·버튼 작업·노드/화면 전환 시 수행하며, 장기 편집 보호를 위해 변경분을 1분 주기로 저장한다. 초안 완료 시 검증 대기로 전환하고 다시 초안으로 되돌릴 수 있다. 초안 작성은 `rule_view`, ACTIVE/롤백은 `rule_activate` 권한으로 분리한다.
- **신규 룰 생성**: 모달에서 ① 기존 룰그래프 선택 → 현재 버전을 복제한 다음 버전(v2, v3…) DRAFT에 빈 노드 추가, 또는 ② 실제 비용분류 scope를 선택해 빈 v1 그래프 생성 → 빈 룰 노드가 상세에 올라옴 → 세부설정.
- **시뮬레이션**: 검증할 그래프를 선택해 과거 이력으로 시뮬(매칭/오탐율/검토감소·분류차이·Agent 보고서) → 그래프를 승인대기로 전환.
- **Active 그래프**: 그래프별 버전 이력·승인대기 승인(ACTIVE 전환)·롤백. 전환/롤백은 `rule_activate` 권한(§3.1a).

#### (a) 생성 Flow
```
관리자: 규정문서 업로드 ─► 비동기 임베딩 ─► Chroma(policy_docs)
Rule Agent(생성):
  ├─ FastMCP:search_policy(query)  RAG로 규칙화 가능 조항 추출
  ├─ LLM: 단건 룰(노드) 초안 생성 (condition DSL + action) + next_routings 제안
  └─ 노드들을 룰 그래프(트리)로 조립 ─► rule_graphs(status=DRAFT) + rules(노드) + rule_routings 저장
```

#### (b) 검증 Flow (적용 전 필수) — 그래프 단위
```
Rule Agent(검증):
  ├─ FastMCP:fetch_historical_tx(기간, 필터)   과거 거래 로드
  ├─ Rule Engine: 후보 그래프를 엔트리부터 순회하며 과거 거래에 시뮬레이션
  ├─ 지표 산출: 매칭건수 / 오탐율 / 예상 검토감소량 (+ 노드별 커버리지)
  └─ rule_graph_versions.snapshot + sim_result 저장 ─► 관리자 검토·승인 화면
관리자 승인 시에만 해당 그래프 버전이 ACTIVE(is_active=true) 전이 — 직전 ACTIVE 버전은 ARCHIVED
(롤백: 이전 승인 버전을 즉시 ACTIVE로 복원. 동시에 ACTIVE인 그래프 버전은 스코프당 하나)
```

#### (c) 적용 Flow (RPA 1차 판정) — 3단 파이프라인
```
① 컨텍스트 조립 (I/O · FastAPI 오케스트레이션)
   FastMCP:build_rule_context(tx_id) → EvalContext(facts JSON) 스냅샷
     └ tx·card·user(직책/근무시간)·evidence·history(이력집계)·policy·merchant(업종)·derived(심야/영업일경과)
② 그래프 선택 (필수 게이트 → 과목별)
   ⓐ 공통/필수 게이트 그래프(scope=GLOBAL): 금지업종·증빙·사전승인·기한 → 확실 REJECT/REVIEW 우선
   └ 통과 시 ⓑ 계정과목별 그래프(scope = tx.category, 예: 접대/회식/식대/출장…): 과목 특화 세부룰
③ 결정론적 순회 (순수함수 · 외부 I/O 없음)
   run_rule_engine(eval_context, graph): 엔트리 → condition(DSL) 평가 → next_routings → 단말 결정
     ├─ 단말 노드 action.decision == PASS    ─► PENDING_CONFIRM (상세검토 생략, 사람 최종확정 대기)
     ├─ 단말 노드 action.decision == REJECT  ─► RETURNED (보완요청 자동 안내)
     └─ 미매칭/저신뢰(REVIEW)               ─► Risk Review Agent로 이관
rule_hits(path, eval_context 스냅샷, graph_version, decision, flags) 기록
```
> 엔진은 EvalContext만 참조한다(외부 I/O 0). 모든 데이터 접근은 ① 조립 단계에서만 수행 → 엔진은 순수함수 → 재실행/시뮬/감사 결과 동일(재현성). ①은 유연(무엇이든 조립), ③은 엄격(결정론).

**입력**: 규정문서(생성), 과거거래(검증), 제출정산+EvalContext(적용)
**출력**: 룰 그래프(노드+라우팅) 초안, 그래프 단위 시뮬레이션 지표, 거래별 판정+순회 path
**사용 Tool**: `search_policy`(생성) · `fetch_historical_tx`(검증) · `build_rule_context`·`run_rule_engine`(적용)
**decision 결정 방식**: PASS/REJECT/RETURN/REVIEW는 노드 생성 시점에 `action.decision`으로 직접 지정되며, 판정 시점에 별도의 확신도 계산이나 임계치 비교를 거치지 않는다. severity(CRITICAL/HIGH/MEDIUM/LOW/INFO)와 decision의 매핑 규칙은 별도 시드 계획 문서를 따른다.
**중요**: Rule은 결정론적 엔진 실행이 원칙, LLM은 생성 단계에서만 사용(적용 단계는 재현성 확보). ACTIVE·버전관리·롤백은 룰 그래프(최종 상태 도메인) 단위.

#### (d) 룰 평가 컨텍스트(EvalContext) & 조건 DSL

**EvalContext** = 판정 시점에 조립된 facts 스냅샷(네임스페이스). 조건은 이 경로만 참조하며, `rule_hits.eval_context`에 저장되어 재현·감사의 근거가 된다.
```
tx{amount,ts,merchant} · card{card_type,owner} · user{position(직책),dept,is_working_hours}
· category{ai,confidence} · merchant{industry_code,forbidden} · evidence{has_receipt,fields{거래처,참석자,목적,일시}}
· policy{preapproval_threshold = min(30만, 별표1[직책]), position_limit} · history{same_merchant_7d,late_submit_count}
· derived{days_since_expense,biz_days_over_7,is_late_night,is_weekend}
```
- **접근 경로**: 관계형(tx/card/user/evidence/history/policy) = Django 내부 read API 경유, 업종 = `classify_merchant`(캐시→카카오→웹), 파생 = 조립기 계산. 전부 ① 단계에서 스냅샷 → 엔진은 Postgres를 모른다(§5.1 원칙 유지).
- **계산은 조립기가 파생 필드로 미리 산출**(예: `min(30만, 직책별)`, 영업일 경과, 심야 여부) → DSL은 단순 비교만.

**조건 DSL** = 임의 코드 금지, JSON-Logic류 화이트리스트 연산자(`and/or/not · ==/!=/>,>=,<,<= · in · var`). `var`는 EvalContext 경로 접근.
```jsonc
// 제11조2항: 기업업무추진비 3만 초과 + 증빙없음 → REVIEW
{ "and": [ {"==":[{"var":"category.ai"},"기업업무추진비"]},
           {">" :[{"var":"tx.amount"},30000]},
           {"==":[{"var":"evidence.has_receipt"},false]} ] }
```
- 노드 `action` = `{decision: PASS|REJECT|REVIEW|RETURN, flag?, note?}`. condition 결과(MATCH/NO_MATCH)로 `next_routings`를 따라 이동, 단말에서 decision 확정.
- **재현성**: 같은 `(eval_context, graph_version)` → 항상 같은 `decision·path`. LLM은 생성 단계에서 DSL을 만들 뿐, 적용은 결정론적.

### 4.3 ③ Risk Review Agent (단순 이상탐지 1차 + RAG 내규 검증 2차)

**목적**: Rule로 안 걸러진 미매칭·불확실 건에 검토 우선순위와 근거를 부여.

**"미매칭 정산 ─► Risk Review Agent" 연결고리(FR-RA-04) 구현 상태**: `domain/policies/orchestrator.py::judge_settlement()`가 GLOBAL(ACTIVE) 필수 게이트 → 계정과목별 scope 그래프 순서로 실제 Rule 엔진을 실행하고 `rule_hits`를 남긴다. 결과가 REVIEW이거나 매칭되는 ACTIVE 그래프 자체가 없으면 `IN_REVIEW`로 전이되고, Django `SettlementViewSet.judge` 액션이 그 즉시 `/agent/risk-review`(FastAPI)를 호출해 이 Agent의 2단계 파이프라인을 실행·저장한다. PASS/REJECT/RETURN 판정 건은 Risk Review로 넘어가지 않는다.

**Flow (MVP: 2단계)**
```
미매칭 정산 ─► Risk Review Agent(FastAPI)
  [1차: 단순 이상거래 탐지]
  1. Feature 조립
       └─ FastMCP:get_tx_features(tx)  금액/시간/요일/가맹점/사용자패턴/이력
  2. 비지도 이상탐지 추론 (ML Serving)
       └─ 단순 이상탐지 모델(Isolation Forest): anomaly_score + 피처기여
       └─ 컷오프 이상 건만 "이상 후보"로 1차 선별
  [2차: RAG 내규 기반 검증 — 이상 후보 한정]
  3. 근거 수집 (RAG)
       ├─ FastMCP:search_policy(category, features)   관련 규정·세법
       └─ FastMCP:search_cases(tx)                    유사 승인·반려 사례
  4. LLM: 내규와 대조해 위반 여부 검증 → 검토사유 + 권장의견(승인/보완/반려) 생성
  5. risk_reviews 저장 ─► 회계 검토 워크스페이스(우선순위순 정렬)
회계 담당자 결정 ─► decision_labels 적재(향후 지도학습용 데이터로 축적만)
```

**입력**: 미매칭 정산 + 파생 feature
**출력**: anomaly_score, 이상사유(피처기여), 규정·사례 근거(출처 조항), AI 권장의견
**사용 Tool**: `get_tx_features`, `ml_infer`, `search_policy`, `search_cases`
**모델 운영(MVP)**: 라벨 불필요한 비지도 이상탐지 온라인 추론(실시간). 컷오프·모델 갱신은 관리자 온디맨드.

> **확장(post-MVP)**: 라벨이 충분히 쌓이면 지도학습 모델(검토필요확률 `review_probability`, 반려/보완 라벨 학습)과 `decision_labels` 기반 자동 재학습 피드백 루프를 추가한다. MVP는 지도학습·재학습 루프를 포함하지 않는다.

이 Agent의 `anomaly_score`(이상탐지 모델 출력)는 Rule Agent의 decision 결정 방식(§4.2(c))과 무관한 별개 파이프라인의 산출물이다. 이상탐지 스코어 컷오프는 §11.2 Open Issue로 남는다.

## 5. FastMCP 도구(Tool) 명세

단일 FastMCP 서버가 3개 Agent의 도구를 모두 노출한다(Agent별 분리 안 함 — MVP 단순화). 영수증 판독은 별도 tool이 아니라 OpenAI 비전 모델을 Draft Agent가 직접 호출한다.

| Tool | 인자(LLM이 넘김) | 출력 | 데이터 원천 | 사용 Agent |
|---|---|---|---|---|
| `get_policy` | category, as_of? | limit, required_evidence, refs | Postgres `policy_tables`(via Django, `effective_date` 기준 시점 조회) | Draft, Rule, Risk |
| `get_card_context` | card_id | card_type, required_inputs | Postgres(via Django) | Draft |
| `classify_merchant` | merchant, place_hint? | industry_code, industry_label, confidence, source | 캐시=Postgres(via Django), 미스 시 카카오 지도/웹검색 | Draft, Risk |
| `search_policy` | query, filters | chunks[] | Chroma 직접 | Rule, Risk |
| `search_cases` | tx / query | similar_cases[] | Chroma 직접 | Risk |
| `fetch_historical_tx` | period, filters | tx[] | Postgres(via Django) | Rule(검증) |
| `build_rule_context` | tx_id | eval_context(facts JSON 스냅샷) | Postgres(via Django) + `classify_merchant` | Rule(적용) |
| `run_rule_engine` | eval_context, graphs(GLOBAL+scope) | decision, path[], flags[] | 내부 Rule 엔진(순수·그래프 순회) | Rule(적용) |
| `get_tx_features` | tx_id | feature_vector(원-핫 인코딩 후 24컬럼 — 원본 15개 피처 중 3개 저카디널리티 범주형(거래요일_한글·시간대구간·일시불할부구분코드)을 원-핫 전개, 학습된 모델의 `feature_columns` 순서에 정렬) | Postgres(via Django, `transactions/features.py::build_tx_features`가 카드별 과거 거래 집계까지 전담) | Risk |
| `ml_infer` | feature_vector | anomaly_score, contribs *(MVP: 비지도 이상탐지만. review_prob는 post-MVP)* | ML 모델(FastAPI 내) | Risk |

`run_rule_engine`은 decision·path·flags만 반환하며 별도 confidence 필드는 없다(§4.2(c)). `classify_merchant`의 confidence(업종 판별 신뢰도), `ml_infer`의 anomaly_score는 각기 다른 파이프라인의 산출물이므로 혼동하지 않는다.

### 5.1 Tool의 데이터 접근 경로

Tool은 무상태 함수처럼 보이지만, LLM이 넘기는 인자만으로는 부족하다. 예) `get_tx_features(tx_id)`는 인자로 `tx_id` 하나만 받지만, 실제로는 그 거래의 상세·사용자의 최근 이력·동일 거래처 누적액까지 조회해야 feature가 만들어진다. 이때 "인자 외 원본 데이터를 어디서 가져오느냐"가 데이터 접근 경로다.

**원칙: 데이터 종류에 따라 접근 경로를 이원화한다.**

```
┌──────────────── FastMCP Tool 구현체 ────────────────┐
│                                                     │
│  관계형 데이터(거래·이력·규정·정산·카드)             │
│     └─► Django 내부 조회 API (read-only REST) ──► Postgres
│         · Postgres를 만지는 것은 Django 하나 (SoR 유지)
│         · ORM·권한·스키마를 Django에 일원화
│                                                     │
│  벡터 데이터(규정/사례 임베딩)                       │
│     └─► Chroma 클라이언트 직접 ──► Chroma            │
│         · Chroma는 Django가 소유하지 않으므로 직접 접근
│                                                     │
└─────────────────────────────────────────────────────┘
```

| 데이터 | 접근 경로 | 이유 |
|---|---|---|
| 관계형(Postgres) | Django 내부 read API 경유 | Postgres 접근점을 Django로 단일화(SoR·권한·감사) |
| 벡터(Chroma) | Chroma 직접 | Django가 소유하지 않는 저장소, 홉 최소화 |
| ML 추론 | FastAPI 프로세스 내부 호출 | 별도 서비스 불필요(MVP) |

즉, LLM/Tool은 절대 Postgres에 직접 SQL을 쏘지 않는다. 관계형 데이터가 필요하면 반드시 Django 내부 API를 거친다. Chroma·ML만 tool이 직접 접근한다.

**설계 규칙**
- Tool은 무상태, 인자·반환은 pydantic 스키마로 엄격 정의.
- 관계형 데이터 접근은 Django 내부 API 경유(LLM에 raw DB 노출 금지).
- 모든 tool call은 로그로 기록(감사·비용·디버깅).

## 7. 위험 검토 파이프라인 (MVP: 이상탐지 1차 + RAG 내규 검증 2차)

MVP는 라벨이 충분히 축적되기 전(콜드스타트)이므로 지도학습에 의존하지 않는 2단계 구조로 단순화한다.

```
[1차 · 단순 이상탐지 (비지도, 라벨 불필요)]
  [학습]  transactions ──► Feature 생성 ──► 비지도 이상탐지 학습(Isolation Forest)
         ──► 모델 레지스트리(버전관리) ──► ML Serving 배포
  [추론]  실시간(동기): get_tx_features → ml_infer → anomaly_score/피처기여
         ──► 컷오프 이상 건만 "이상 후보" 선별
[2차 · RAG 내규 검증 (이상 후보 한정)]
  이상 후보 ──► search_policy/search_cases(RAG) ──► LLM 내규 대조·검증
         ──► 검토사유·권장의견(출처 포함) ──► risk_reviews 저장
[피드백] 회계 결정 → decision_labels 적재만 (MVP는 재학습 안 함, 향후 지도학습용)
```

**Feature 예시**: 금액·정규화금액, 시간대/요일/심야여부, 가맹점/업종, 사용자·부서, 최근 N일 빈도, 동일거래처 누적, Rule 적용결과, 증빙 유무.
**평가지표**: 이상탐지 검토 적중률·AUC, RAG 근거 정확도, 검토량 감소율. (목표치 §11.2 Open Issue)

> **확장(post-MVP)**: 라벨이 쌓이면 지도 검토필요확률 분류기(XGBoost/LogReg 등)와 `decision_labels` 기반 온디맨드 재학습 루프를 추가한다.

## 7-1. 가맹점 업종 구분 파이프라인 (Merchant Classification)

가맹점명만으로는 비용분류가 모호한 경우가 많아, 가맹점의 업종(업태)을 별도로 판별해 Draft Agent의 비용분류 제안과 Risk 이상탐지 feature('가맹점/업종')를 보강한다. 외부 조회 비용·지연을 줄이기 위해 자체 DB 캐시를 1차 소스로 두는 캐스케이드 구조다.

```
가맹점명(+장소 힌트)
  0. 정규화        지점명·특수문자·체인 접미 제거 → 조회 키 생성
  1. [캐시]         merchant_categories(자체 DB) 히트 & 유효(TTL) → 반환        source=CACHE
  2. [카카오 지도]   로컬 키워드검색 → category_group_code/category_name 매핑 → 반환  source=KAKAO
  3. [Web Search]   1·2 실패/모호 시 웹검색 → LLM이 스니펫 해석 → 업종 추론        source=WEB
  4. [확정+캐시]     업종·신뢰도·source·조회일 upsert → 이후 동일 가맹점 재사용
```

- **출력**: `{ industry_code, industry_label, confidence, source }`
- **업종→분류 매핑 예**: FD6 음식점→식대/회의 · CE7 카페→회의/식대 · AD5 숙박→출장 · 주류·유흥→접대(리스크↑) · 문구·전자→비품
- **활용**: ① Draft Agent 비용분류 제안(가맹점+업종 → 분류) ② Risk 이상탐지 feature 보강(업종-분류 불일치, 유흥업종 접대 등)
- **캐시(자체 DB)**: 관계형이므로 Django 소유(`merchant_categories`). 외부 API(카카오/웹검색) 호출은 FastAPI(ai)에서 수행하고, 결과만 Django 경유로 캐시 적재한다(§5.1 원칙 준수).
- **세무/회계 부적합**: 카카오·웹 기반 업종은 장소·마케팅 분류라 세무 계정과목과 불일치할 수 있다. 비용분류 보조 힌트로만 사용하고, 세무 판단은 규정/세법 RAG(`tax_refs`)에 위임한다.
- **확장(post-MVP)**: 카드사 제휴로 MCC(Merchant Category Code) 확보 시 표준 업종코드로 대체·보강한다(§11.2).

## 8. RAG 파이프라인

```

질의 시    ─► 쿼리 임베딩 ─► Chroma 유사도 검색(top-k, 메타 필터) ─► LLM 컨텍스트 주입
```

## 11. 확정 사항 및 남은 이슈

### 11.1 MVP 확정 사항

- **Django ↔ FastAPI 통신**: 동기 REST (메시지 큐 없음)
- **비동기 스택**: 미도입 (Redis/Celery 없이 동기 처리, 무거운 작업은 관리자 온디맨드 배치)
- **영수증 처리**: 별도 OCR 없이 OpenAI 비전 모델로 이미지 직접 판독
- **FastMCP**: 단일 서버로 3 Agent 공용
- **Tool 데이터 접근**: 관계형=Django 내부 API 경유, 벡터=Chroma 직접 (§5.1)
- **가맹점 업종 구분**: 자체 DB 캐시 → 카카오 지도 API → 웹검색 캐스케이드로 판별, 비용분류 보조 힌트로만 사용(세무 판단 아님). MCC는 post-MVP (§7-1)
- **Rule decision 결정 방식**: PASS/REJECT/RETURN/REVIEW는 노드 생성 시 `action.decision`으로 직접 지정한다. 판정 시점의 확신도 계산·임계치 비교 방식은 채택하지 않는다(§4.2(c))
- **계정과목 scope 매핑**: 기업업무추진비→접대. 회식은 식대와 별개의 독립 scope로 유지한다(§3.3)

### 11.2 남은 확정 필요 사항

1. (MVP 1차) 비지도 이상탐지 알고리즘·피처셋·컷오프 최종 선정 및 목표 성능치. 이상탐지 스코어 컷오프는 Rule Agent decision 결정 방식과 무관한 별개 이슈. **v0 현재 상태**: 컷오프(θ_anomaly) 미적용 — IN_REVIEW 전건이 2차 RAG 검증까지 그대로 진행된다. feature_contribs는 배포된 모델(pkl)에 feature_stats가 없는 세대라 항상 빈 배열(재학습 시 해소, 재학습 자체는 보류 결정). sklearn 버전 불일치(학습 pkl=1.8.0 vs 서빙 컨테이너=1.5.2, `InconsistentVersionWarning`)도 확인됐으나 조치는 보류
2. (post-MVP) 지도학습(review_probability) 도입 시점·필요 라벨량·자동 재학습 주기
3. 임베딩 모델(OpenAI vs 로컬) 및 Chroma 영속·백업 전략
4. ERP 전표(안) 스키마: MVP 산출물 포맷(연동은 범위 외)
5. 멀티테넌시: 테넌트별 데이터·모델·규정 격리 범위(MVP 필요 여부 포함)
6. OpenAI 모델 선정(비전·LLM) 및 프롬프트·비용 관리 방식
7. 가맹점 업종 캐시 정책: 카카오 API 키·쿼터, 캐시 TTL·정규화 규칙, 업종→분류 매핑 테이블 확정
8. (확장) 카드사 제휴 MCC 확보: 세무·회계 기준 업종코드(MCC) 도입 방식·시점 — 카카오/웹 업종을 대체·보강
